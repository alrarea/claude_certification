> **🔑️ പ്രധാന നിഗമനം:** വിശ്വസനീയമായ ഘടനാപരമായ ഔട്ട്പുട്ടിന് "respond in JSON" എന്ന ഗദ്യ നിർദേശമല്ല, JSON Schema സഹിതം `tool_use` ഉപയോഗിക്കുക — പക്ഷേ schema ഘടന മാത്രമേ ഉറപ്പാക്കുന്നുള്ളൂ, അർഥം ഒരിക്കലും ഉറപ്പാക്കുന്നില്ല എന്ന് ഓർക്കുക.

- `tool_use` + schema, നിങ്ങൾ നിശ്ചയിച്ച ഫീൽഡുകളോടും തരങ്ങളോടും ഒത്തുപോകുന്ന ഡാറ്റ തിരികെ നൽകാൻ API-യെ നിർബന്ധിക്കുന്നു — അധിക ടെക്സ്റ്റോ കോഡ് ഫെൻസുകളോ തകരാറുള്ള JSON-ഓ ഇല്ല.
- ഘടന vs. അർഥം: schema ഫീൽഡുകളുടെ പേര്, തരം, സാന്നിധ്യം എന്നിവ പരിശോധിക്കുന്നു; ഉള്ളടക്കം വസ്തുതാപരമായി ശരിയാണോ (തുകകൾ ചേരുന്നുണ്ടോ, തീയതികൾ യുക്തിസഹമാണോ) എന്ന് പരിശോധിക്കുന്നില്ല.
- Required ഫീൽഡുകൾ = സാധുവായ ഒരു extraction-ൽ എപ്പോഴും ഉണ്ടായിരിക്കണം.
- Nullable ഫീൽഡുകൾ (`["string", "null"]`) = ഉറവിടത്തിൽ ഇല്ലാതിരിക്കാവുന്ന ഡാറ്റയ്ക്ക് ഉപയോഗിക്കുക — ഒരു മൂല്യം കണ്ടുപിടിക്കുന്നതിനു പകരം "കണ്ടെത്തിയില്ല" എന്ന് പറയാൻ സാധുവായ ഒരു വഴി നൽകുന്നതിലൂടെ ഇത് hallucination തടയുന്നു.
- Enum-കൾ ഒരു ഫീൽഡിനെ നിശ്ചിത മൂല്യങ്ങളിലേക്ക് പരിമിതപ്പെടുത്തുന്നു — അസ്ഥിരമായ അക്ഷരരൂപങ്ങളും പര്യായങ്ങളും തടയുന്നു; പ്രതീക്ഷിക്കാത്ത സാഹചര്യങ്ങൾക്ക് ഒരു `"other"`-ഉം ഒരു വിശദാംശ ഫീൽഡും ചേർത്ത് ഉപയോഗിക്കുക.
- schema പരിശോധനയോടൊപ്പം എപ്പോഴും വേറിട്ട ഒരു അർഥ/ബിസിനസ് യുക്തി പരിശോധന ഘട്ടം ചേർക്കുക — schema validation കടന്നു എന്നത് ഡാറ്റ ശരിയാണെന്നതിന്റെ തെളിവല്ല.
