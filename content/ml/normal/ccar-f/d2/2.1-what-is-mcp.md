## എന്താണ് MCP?

MCP (Model Context Protocol) ഉണ്ടാകുന്നതിന് മുൻപ്, Claude-നെ ഒരു ബാഹ്യ സംവിധാനവുമായി — ഒരു ഡാറ്റാബേസ്, ഒരു ടിക്കറ്റിങ് സിസ്റ്റം, ഒരു കലണ്ടർ — സംസാരിപ്പിക്കണമെന്ന് ആഗ്രഹിക്കുമ്പോഴെല്ലാം, ആ കൃത്യമായ മാതൃക-സംവിധാന സംയോജനത്തിന് വേണ്ടി ആരെങ്കിലും ഒരു പ്രത്യേക integration എഴുതേണ്ടിയിരുന്നു. 5 ടൂളുകളും 3 വ്യത്യസ്ത AI ആപ്ലിക്കേഷനുകളും ഉണ്ടെങ്കിൽ, ഓരോന്നിനും അതിന്റേതായ പ്രത്യേകതകളുള്ള 15 വ്യത്യസ്ത glue കോഡ് ഭാഗങ്ങൾ വേണ്ടിവന്നേക്കാം.

ഒരു AI ആപ്ലിക്കേഷൻ ബാഹ്യ കഴിവുകളുമായി എങ്ങനെ സംസാരിക്കണം എന്നതിന് ഒരു **മാനദണ്ഡ രൂപം** നിർവചിച്ചാണ് MCP ഇത് പരിഹരിക്കുന്നത്. ഒരു സംവിധാനം ഒരു MCP സെർവറായി സ്വയം തുറന്നുകഴിഞ്ഞാൽ, *ഏതൊരു* MCP-അനുയോജ്യ ക്ലയന്റിനും (Claude ഉൾപ്പെടെ) പ്രത്യേക കോഡില്ലാതെ അത് ഉപയോഗിക്കാം. USB-C പോലെ കരുതുക: USB-C-ക്ക് മുൻപ് ഓരോ ഉപകരണത്തിനും അതിന്റേതായ ചാർജർ രൂപമുണ്ടായിരുന്നു. ഇപ്പോൾ എല്ലാവരും ഒരു മാനദണ്ഡത്തിൽ യോജിച്ചതിനാൽ ഒരൊറ്റ കണക്ടർ രൂപം എല്ലായിടത്തും പ്രവർത്തിക്കുന്നു.

### അടിസ്ഥാന ഘടകങ്ങൾ

ഒരു MCP സെർവറിന് Claude-ന് മൂന്ന് തരം കാര്യങ്ങൾ തുറന്നുകൊടുക്കാം:

1. **Tools** — `process_refund` അല്ലെങ്കിൽ `lookup_order` പോലെ Claude-ന് സജീവമായി വിളിക്കാവുന്ന പ്രവൃത്തികൾ. ഇവയാണ് മാതൃകയ്ക്ക് വിളിക്കാവുന്ന "ക്രിയകൾ", ഓരോന്നിനും ഒരു പേര്, ഒരു വിവരണം, ഒരു ഇൻപുട്ട് schema.
2. **Resources** — രേഖാ പേജുകൾ, ഡാറ്റാബേസ് schema-കൾ, തുറന്ന പ്രശ്നങ്ങളുടെ സംഗ്രഹം എന്നിവ പോലെ context-നായി Claude-ന് നോക്കാവുന്ന വായന-മാത്ര ഡാറ്റ. ഒരു ടൂൾ വിളിക്കുന്നതുപോലെ Claude ഒരു resource "വിളിക്കുന്നില്ല" — അത് വായിക്കുന്നു.
3. **Prompts** (മുകളിലെ പട്ടികയിൽ കാണിച്ചിട്ടില്ല, പക്ഷേ അതേ കുടുംബത്തിന്റെ ഭാഗം) — സാധാരണ ഇടപെടലുകൾ ക്രമപ്പെടുത്താൻ ഒരു സെർവറിന് നൽകാവുന്ന പുനരുപയോഗിക്കാവുന്ന prompt ടെംപ്ലേറ്റുകൾ.

### ഒരു ടൂൾ വിളി യഥാർഥത്തിൽ എങ്ങനെ ഒഴുകുന്നു

1. കണക്ഷൻ തുടങ്ങുമ്പോൾ MCP സെർവർ അതിന്റെ ടൂളുകൾ (വിവരണങ്ങളും schema-കളും സഹിതം) പരസ്യപ്പെടുത്തുന്നു.
2. ഉപയോക്താവിന്റെ അഭ്യർഥനയും ആ വിവരണങ്ങളും അടിസ്ഥാനമാക്കി, ഒരു ടൂൾ വിളിക്കണോ, ഏതെന്ന് Claude തീരുമാനിക്കുന്നു.
3. സെർവർ അടിസ്ഥാന പ്രവൃത്തി നടത്തുന്നു (ഉദാ: ഡാറ്റാബേസ് ചോദ്യം ചെയ്യുന്നു) എന്നിട്ട് ഒരു ഫലം നൽകുന്നു.
4. എന്തെങ്കിലും തെറ്റിയാൽ, വിളി പരാജയപ്പെട്ടെന്ന് Claude അറിയാൻ സെർവർ മറുപടിയിൽ `isError: true` സെറ്റ് ചെയ്യുന്നു — അല്ലാത്തപക്ഷം അസംബന്ധ ഔട്ട്പുട്ട് നിശ്ശബ്ദമായി ഒരു സാധുവായ ഉത്തരമായി കണക്കാക്കപ്പെടാം.

ആ `isError` ഫ്ലാഗ് കാണുന്നതിലും പ്രധാനമാണ്. വ്യക്തമായ ഒരു സൂചനയില്ലെങ്കിൽ, പരാജയപ്പെട്ട ഒരു ഡാറ്റാബേസ് ചോദ്യത്തിന്റെ പിഴവ് സന്ദേശം യഥാർഥ ഉപഭോക്തൃ ഡാറ്റയെന്ന മട്ടിൽ Claude വ്യാഖ്യാനിക്കുകയും ആത്മവിശ്വാസത്തോടെ തെറ്റായ വിവരം ഒരു ഉപയോക്താവിന് നൽകുകയും ചെയ്തേക്കാം.

> **🌍 യഥാർഥ ഉദാഹരണം:** ഒരു സോഫ്റ്റ്‌വെയർ കമ്പനിക്ക് ബില്ലിങ് ചോദ്യങ്ങൾക്ക് ഉത്തരം നൽകാൻ സപ്പോർട്ട് ഏജന്റുമാരെ Claude സഹായിക്കണം. Claude-ന് മാത്രമുള്ള ഒരു integration കൈകൊണ്ട് എഴുതുന്നതിന് പകരം, അവരുടെ ബില്ലിങ് ഡാറ്റാബേസ് പൊതിയുന്ന ഒരൊറ്റ MCP സെർവർ അവർ സ്ഥാപിക്കുന്നു, `get_invoice`, `lookup_payment_status` പോലുള്ള ടൂളുകളും അവരുടെ റീഫണ്ട് നയ രേഖ അടങ്ങിയ ഒരു resource-ഉം അത് തുറന്നുകൊടുക്കുന്നു. ഇപ്പോൾ സപ്പോർട്ട് കൺസോളിലെ Claude-ഉം, ഒരു ആന്തരിക Slack ബോട്ടും, ഭാവിയിലെ ഒരു ഇൻ-ആപ്പ് സഹായിയും അതേ MCP സെർവർ തന്നെ പുനരുപയോഗിക്കാം — ഓരോ ഇടത്തിനും വീണ്ടും integration വേണ്ട.

### ഒറ്റത്തവണ integration-നെക്കാൾ മാനദണ്ഡീകരണം എന്തുകൊണ്ട് മെച്ചം

| വശം | പ്രത്യേക, ഒറ്റത്തവണ integration | MCP അധിഷ്ഠിത integration |
|---|---|---|
| ഓരോ പുതിയ AI ആപ്പിനുമുള്ള ജോലി | integration പുതുതായി വീണ്ടും നിർമിക്കുക | നിലവിലുള്ള MCP സെർവർ അതേപടി പുനരുപയോഗിക്കുക |
| പിഴവ് കൈകാര്യത്തിന്റെ സ്ഥിരത | ഓരോ integration-ലും വ്യത്യസ്തം | മാനദണ്ഡ രൂപം (`isError`, ഘടനാപരമായ സന്ദേശങ്ങൾ) |
| കണ്ടെത്താനുള്ള എളുപ്പം | ഡെവലപ്പർ ടൂളുകൾ വെവ്വേറെ രേഖപ്പെടുത്തണം | സെർവർ ഏത് ക്ലയന്റിനും tools/resources സ്വയം വിവരിക്കുന്നു |
| പരിപാലനം | API മാറുമ്പോൾ N integration-കൾ പുതുക്കണം | ഒരു സെർവർ പുതുക്കിയാൽ മതി |

> **📝 പരീക്ഷാ ശ്രദ്ധ:** ഒരു **tool** (Claude സജീവമായി വിളിക്കുന്ന, പാർശ്വഫലങ്ങളോ തിരയലുകളോ ഉള്ള പ്രവൃത്തി) ഉം ഒരു **resource** (നിഷ്ക്രിയമായ, വായന-മാത്ര context) ഉം തമ്മിലുള്ള വ്യത്യാസം അറിയുക. വിവരിക്കുന്ന ഒരു കഴിവ് ഇവയിൽ ഏതായിരിക്കണം എന്ന് തിരിച്ചറിയാൻ കഴിയുമോ എന്ന് പരീക്ഷാ ചോദ്യങ്ങൾ പലപ്പോഴും പരിശോധിക്കുന്നു.
