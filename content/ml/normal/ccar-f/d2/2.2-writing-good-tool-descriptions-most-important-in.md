## നല്ല ടൂൾ വിവരണങ്ങൾ എഴുതൽ — ഈ ഡൊമെയ്നിലെ ഏറ്റവും പ്രധാനം

നിങ്ങളുടെ സോഴ്സ് കോഡോ, ആന്തരിക പേരിടൽ രീതികളോ, എൻജിനീയറിങ് ടീമുമായുള്ള സംഭാഷണമോ Claude-ന് ലഭ്യമല്ല. ഏത് ടൂൾ വിളിക്കണം എന്ന് തീരുമാനിക്കുമ്പോൾ അത് കാണുന്ന **ഒരേയൊരു** കാര്യം ടൂളിന്റെ പേര്, അതിന്റെ വിവരണം, അതിന്റെ ഇൻപുട്ട് schema എന്നിവയാണ്. ആ വിവരണം *തന്നെയാണ്* ഇടനില. അത് അവ്യക്തമാണെങ്കിൽ Claude-ന് ഊഹിക്കേണ്ടിവരും — ഊഹിക്കൽ എന്നാൽ തെറ്റുകൾ.

ഈ ഡൊമെയ്നിലെ ഏറ്റവും പ്രധാന വൈദഗ്ധ്യമായി ടൂൾ വിവരണ ഗുണനിലവാരം എടുത്തുപറയുന്നത് ഇതുകൊണ്ടാണ്: "Claude തെറ്റായ ടൂൾ ഉപയോഗിച്ചു" എന്ന പ്രശ്നങ്ങളിൽ ഭൂരിഭാഗത്തിന്റെയും മൂലകാരണം ഇതാണ്, മാത്രമല്ല പരിഹരിക്കാൻ ഏറ്റവും ചെലവ് കുറഞ്ഞതുമാണ്.

### അവ്യക്ത വിവരണങ്ങൾ എന്തുകൊണ്ട് പരാജയപ്പെടുന്നു

രണ്ട് ടൂളുകൾ പരിഗണിക്കുക: "Retrieves customer information" എന്ന് വിവരിച്ച `get_customer`, "Retrieves order details" എന്ന് വിവരിച്ച `lookup_order`. രണ്ട് വിവരണങ്ങളും സാങ്കേതികമായി കൃത്യമാണ്, പക്ഷേ ഒന്നിനെ മറ്റൊന്നിനെക്കാൾ *എപ്പോൾ* തിരഞ്ഞെടുക്കണമെന്ന് അവ Claude-നോട് പറയുന്നില്ല. "ഈ ഉപഭോക്താവ് കഴിഞ്ഞ മാസം എന്താണ് ഓർഡർ ചെയ്തത്?" പോലുള്ള ഒരു ചോദ്യം ഒരു ഉപഭോക്താവിനെക്കുറിച്ചും ഒരു ഓർഡറിനെക്കുറിച്ചും ആണെന്ന് വാദിക്കാം — വേർതിരിക്കുന്ന ഭാഷയില്ലാതെ, Claude-ന് പുറമേയുള്ള വാക്കുകൾ നോക്കി പൊരുത്തപ്പെടുത്തേണ്ടിവരും, ഗണ്യമായ ഒരു ഭാഗം സമയത്ത് അത് തെറ്റായി ഊഹിക്കും (ഈ കൃത്യമായ സാഹചര്യത്തിൽ ഏകദേശം 45% തെറ്റായ ടൂൾ തിരഞ്ഞെടുപ്പ് എന്ന് normal-mode പാഠഭാഗം ഉദ്ധരിക്കുന്നു).

### ശക്തമായ ഒരു വിവരണത്തിൽ യഥാർഥത്തിൽ എന്തുണ്ടാകണം

നിങ്ങളുടെ സിസ്റ്റം മുൻപ് ഒരിക്കലും കണ്ടിട്ടില്ലാത്ത, വളരെ അക്ഷരാർഥത്തിൽ വായിക്കുന്ന ഒരാൾക്ക് വേണ്ടി എഴുതിയ ഒരു ചെറു-സ്പെക്കായി ഒരു ടൂൾ വിവരണത്തെ കരുതുക. അതിൽ ഇവ ഉണ്ടാകണം:

- **ഉദ്ദേശ്യം** — ടൂൾ എന്ത് ചെയ്യുന്നു എന്ന് വിവരിക്കുന്ന വ്യക്തമായ ഒരു വാക്യം.
- **ഇൻപുട്ട് രൂപം** — ഏതൊക്കെ പാരാമീറ്ററുകൾ, ഏത് രൂപത്തിൽ പ്രതീക്ഷിക്കുന്നു (ഒരു ഇമെയിൽ? ഒരു ഐഡി? ഒരു തീയതി പരിധി?).
- **ട്രിഗർ ഉദാഹരണങ്ങൾ** — ഇവിടേക്ക് നയിക്കേണ്ട തരം ചോദ്യങ്ങളോ അഭ്യർഥനകളോ.
- **ഒഴിവാക്കലുകൾ / അതിർസാഹചര്യങ്ങൾ** — എപ്പോൾ ഇത് ഉപയോഗിക്കാൻ *പാടില്ല* എന്ന് വ്യക്തമായി പറയുക, പ്രത്യേകിച്ച് സമാന ടൂളുകളുമായി താരതമ്യപ്പെടുത്തി.
- **വേർതിരിവ്** — ആശയക്കുഴപ്പമുണ്ടാക്കാവുന്ന ടൂളുകളിൽ നിന്ന് ഇത് എങ്ങനെ വ്യത്യസ്തമാണെന്ന് നേരിട്ട് പറയുക.

മുൻ ഉദാഹരണം വീണ്ടും എഴുതിയാൽ: `get_customer` ഇങ്ങനെയാകുന്നു — "Gets customer profile (name, tier, contact). Use when the query is about WHO the customer IS. Input: customer email or ID." — `lookup_order` ഇങ്ങനെയും — "Gets order history, status, items. Use when the query is about what they BOUGHT or ORDER STATUS. Input: order number." ഇപ്പോൾ രണ്ട് ടൂളുകളും അവ്യക്തമായി കൂടിക്കുഴയുന്നതിന് പകരം പരസ്പരം ഒഴിവാക്കുന്ന മേഖലകൾ വിവരിക്കുന്നു.

> **🌍 യഥാർഥ ഉദാഹരണം:** ഒരു coding agent നിർമിക്കുന്ന ഒരു എൻജിനീയറിങ് ടീം Claude-ന് ഒരു `search_code` ടൂളും ("Searches the codebase") ഒരു `search_docs` ടൂളും ("Searches documentation") നൽകുന്നു. "retry policy എങ്ങനെ ക്രമീകരിക്കും?" പോലുള്ള രേഖാ ചോദ്യങ്ങൾ ചോദിക്കുമ്പോൾ Claude നിരന്തരം കോഡ് തിരയുന്നതായി ഡെവലപ്പർമാർ റിപ്പോർട്ട് ചെയ്യുന്നു. വിവരണങ്ങൾ "Searches source code files (.ts, .py, .go) for function/class definitions and usages — use for 'where is X implemented' questions" എന്നും "Searches markdown/docs for setup guides, configuration options, and how-to content — use for 'how do I configure/set up X' questions" എന്നും മാറ്റിയെഴുതിയശേഷം, ഒരു കോഡ് മാറ്റവുമില്ലാതെ തെറ്റായ വഴിതിരിവ് ഏതാണ്ട് പൂർണമായി ഇല്ലാതാകുന്നു.

### മോശം vs. നല്ല വിവരണങ്ങൾ ഒറ്റനോട്ടത്തിൽ

| | മോശം വിവരണ ശൈലി | നല്ല വിവരണ ശൈലി |
|---|---|---|
| ഉദ്ദേശ്യം | പൊതുവായ ക്രിയ + നാമം ("Retrieves X") | എന്ത് തിരികെ ലഭിക്കുന്നു എന്നതിന്റെ കൃത്യവും പരിധി നിർണയിച്ചതുമായ പ്രസ്താവന |
| വേർതിരിവ് | ഇല്ല — Claude ഊഹിക്കട്ടെ എന്ന് കരുതുന്നു | വ്യക്തമായ "use when..." മാർഗനിർദേശം |
| ഇൻപുട്ട് | വ്യക്തമാക്കിയിട്ടില്ല അല്ലെങ്കിൽ സൂചന മാത്രം | വ്യക്തമായി പ്രസ്താവിച്ചിരിക്കുന്നു (രൂപം, പ്രതീക്ഷിത മൂല്യങ്ങൾ) |
| സമാന ടൂളുകളുമായുള്ള കൂടിക്കുഴയൽ | പരിഗണിച്ചിട്ടില്ല | നേരിട്ട് എടുത്തുപറഞ്ഞിരിക്കുന്നു |
| ഫലം | ഇടയ്ക്കിടെ തെറ്റായ ടൂൾ തിരഞ്ഞെടുപ്പ് | Claude വിശ്വസനീയമായി ഉദ്ദേശിച്ച ടൂൾ തിരഞ്ഞെടുക്കുന്നു |

> **📝 പരീക്ഷാ ശ്രദ്ധ:** Claude തെറ്റായ ടൂൾ തിരഞ്ഞെടുക്കുന്നതായി ഒരു സാഹചര്യം വിവരിക്കുമ്പോൾ, പരീക്ഷയിൽ പ്രതീക്ഷിക്കുന്ന ആദ്യ പരിഹാരം മിക്കവാറും എപ്പോഴും **ടൂൾ വിവരണങ്ങൾ മെച്ചപ്പെടുത്തുക** എന്നതാണ് — ഒരു classifier-ഓ, ഒരു router-ഓ, കൂടുതൽ prompt നിർദേശങ്ങളോ മുകളിൽ ചേർക്കുകയല്ല. orchestration സങ്കീർണത കൂട്ടും മുൻപ് മൂലകാരണങ്ങൾ പരിഹരിക്കുക.
