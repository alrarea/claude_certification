## 12 ഔദ്യോഗിക മാതൃകാ ചോദ്യങ്ങളും വിശദീകരണങ്ങളും

ഈ ചോദ്യങ്ങൾ നേരിട്ട് Anthropic-ന്റെ ഔദ്യോഗിക പരീക്ഷാ ഗൈഡിൽ നിന്നുള്ളവയാണ്. യഥാർഥ പരീക്ഷയുടെ കൃത്യമായ ശൈലിയും ബുദ്ധിമുട്ടിന്റെ നിലവാരവും അവ കാണിക്കുന്നു. ഓരോ ഉത്തര വിശദീകരണവും വായിക്കുക — പരീക്ഷ എങ്ങനെ ചിന്തിക്കുന്നുവെന്ന് അവ വെളിപ്പെടുത്തുന്നു. ഓരോ വിശദീകരണത്തിനൊപ്പം, ചോദ്യം പരിശോധിക്കുന്ന പൊതു ന്യായവാദ മാതൃക ചൂണ്ടിക്കാണിക്കുന്ന ഒരു ചെറിയ കുറിപ്പുമുണ്ട്, കാരണം യഥാർഥ പരീക്ഷയിൽ വ്യത്യസ്ത സാഹചര്യങ്ങളിലായി അതേ മാതൃക വീണ്ടും വരാറുണ്ട്.

### സാഹചര്യം A: Customer Support Agent

**Q1 · ഡൊമെയ്ൻ 1 — Agentic Architecture**

12% കേസുകളിൽ നിങ്ങളുടെ agent `get_customer` പൂർണമായി ഒഴിവാക്കി, ഉപഭോക്താവ് പറഞ്ഞ പേര് മാത്രം ഉപയോഗിച്ച് `lookup_order` വിളിക്കുന്നതായി പ്രൊഡക്ഷൻ ഡാറ്റ കാണിക്കുന്നു — ഇത് ഇടയ്ക്കിടെ തെറ്റായി തിരിച്ചറിഞ്ഞ അക്കൗണ്ടുകളിലേക്കും തെറ്റായ റീഫണ്ടുകളിലേക്കും നയിക്കുന്നു. ഈ വിശ്വാസ്യതാ പ്രശ്നം ഏറ്റവും ഫലപ്രദമായി പരിഹരിക്കുന്ന മാറ്റം ഏതാണ്?

- A. `get_customer` പരിശോധിച്ച ഒരു ഉപഭോക്തൃ ID നൽകുംവരെ `lookup_order`, `process_refund` വിളികൾ തടയുന്ന ഒരു programmatic മുൻവ്യവസ്ഥ ചേർക്കുക.
- B. ഏത് ഓർഡർ പ്രവർത്തനത്തിനും മുൻപ് ഉപഭോക്തൃ പരിശോധന നിർബന്ധമാണെന്ന് system prompt-ൽ പറയുക.
- C. Agent എപ്പോഴും ആദ്യം `get_customer` വിളിക്കുന്നത് കാണിക്കുന്ന few-shot ഉദാഹരണങ്ങൾ ചേർക്കുക.
- D. ഓരോ അഭ്യർഥനാ തരത്തിനും ശരിയായ ടൂളുകൾ മാത്രം സാധ്യമാക്കുന്ന ഒരു routing classifier നടപ്പാക്കുക.

✅ **A എന്തുകൊണ്ട്:** നിർണായകമായ ബിസിനസ് യുക്തിക്ക് ഒരു ടൂൾ ക്രമം നിർബന്ധമാകുമ്പോൾ (റീഫണ്ടിനു മുൻപ് ഐഡന്റിറ്റി പരിശോധന), programmatic enforcement വേണം — ആദ്യത്തേത് പൂർത്തിയാകുംവരെ അടുത്ത ടൂൾ തടയുന്ന കോഡ്. B-യും C-യും Claude നിർദേശങ്ങൾ സാധ്യതാധിഷ്ഠിതമായി പാലിക്കുന്നതിനെ ആശ്രയിക്കുന്നു — അതായത് ചിലപ്പോൾ പാലിക്കില്ല. സാമ്പത്തിക പിഴവുകൾക്ക് യഥാർഥ പ്രത്യാഘാതങ്ങളുണ്ട്, അതിനാൽ "ചിലപ്പോൾ" സ്വീകാര്യമല്ല. D ടൂളിന്റെ ലഭ്യതയെ അഭിസംബോധന ചെയ്യുന്നു, യഥാർഥ പ്രശ്നമായ ടൂളിന്റെ ക്രമത്തെയല്ല.

*ന്യായവാദ മാതൃക: വലിയ പ്രത്യാഘാതമുള്ള ഒരു നടപടി ഒരു നിർബന്ധ ക്രമത്തെ ആശ്രയിക്കുമ്പോഴെല്ലാം, programmatic enforcement-ഉം സാധ്യതാധിഷ്ഠിതമായ (prompt അടിസ്ഥാന) പാലനവും വേർതിരിക്കൽ.*

**Q2 · ഡൊമെയ്ൻ 2 — Tool Design & MCP**

ഉപയോക്താക്കൾ ഓർഡറുകളെക്കുറിച്ച് ചോദിക്കുമ്പോൾ (ഉദാ: "എന്റെ ഓർഡർ #12345 പരിശോധിക്കൂ") `lookup_order` വിളിക്കുന്നതിനു പകരം agent പതിവായി `get_customer` വിളിക്കുന്നതായി പ്രൊഡക്ഷൻ log-കൾ കാണിക്കുന്നു. രണ്ട് ടൂളുകൾക്കും വളരെ കുറഞ്ഞ വിവരണങ്ങളേയുള്ളൂ. ഏറ്റവും ഫലപ്രദമായ ആദ്യ നടപടി ഏതാണ്?

- A. ശരിയായ ടൂൾ തിരഞ്ഞെടുക്കൽ മാതൃകകൾ കാണിക്കുന്ന 5-8 few-shot ഉദാഹരണങ്ങൾ ചേർക്കുക.
- B. ഓരോ ടൂളിന്റെയും വിവരണം വിപുലീകരിച്ച് ഇൻപുട്ട് രൂപങ്ങൾ, ഉദാഹരണ ചോദ്യങ്ങൾ, അതിർത്തി സാഹചര്യങ്ങൾ, സമാന ടൂളുകളിൽ നിന്ന് എപ്പോൾ ഇത് ഉപയോഗിക്കണമെന്ന് വിശദീകരിക്കുന്ന അതിരുകൾ എന്നിവ ചേർക്കുക.
- C. User ഇൻപുട്ട് പാഴ്‌സ് ചെയ്ത് keyword-കൾ നോക്കി ടൂൾ മുൻകൂട്ടി തിരഞ്ഞെടുക്കുന്ന ഒരു routing പാളി നടപ്പാക്കുക.
- D. രണ്ട് ടൂളുകളും ഒരൊറ്റ `lookup_entity` ടൂളായി ചേർക്കുക.

✅ **B എന്തുകൊണ്ട്:** ഒരു ടൂൾ തിരഞ്ഞെടുക്കാൻ Claude ഉപയോഗിക്കുന്ന പ്രധാന സംവിധാനം ടൂൾ വിവരണങ്ങളാണ്. കുറഞ്ഞ വിവരണങ്ങളാണ് മൂലകാരണം. ആദ്യം വേര് ശരിയാക്കുക — ഇത് കുറഞ്ഞ അധ്വാനവും വലിയ ഫലവുമാണ്. A അടിസ്ഥാന പ്രശ്നം പരിഹരിക്കാതെ token ഭാരം കൂട്ടുന്നു. C തകർന്ന ഒരു അടിത്തറയ്ക്കു മുകളിൽ routing സംവിധാനം ഉണ്ടാക്കുന്നു. D സാധുവായ ഒരു architecture തിരഞ്ഞെടുപ്പാണ്, പക്ഷേ ഒരു "ആദ്യ നടപടി" പരിഹാരത്തിന് വളരെ ഭാരമുള്ളതാണ്.

*ന്യായവാദ മാതൃക: ടൂൾ തിരഞ്ഞെടുക്കൽ പിഴവുകളുടെ മൂലകാരണമായി ടൂൾ വിവരണത്തിന്റെ ഗുണനിലവാരം കണക്കാക്കൽ, ഒപ്പം സംവിധാനം ചേർക്കും മുൻപ് ഏറ്റവും കുറഞ്ഞ അധ്വാനമുള്ള ഘടനാപരമായ പരിഹാരം തിരഞ്ഞെടുക്കൽ.*

**Q3 · ഡൊമെയ്ൻ 5 — Context Management & Reliability**

നിങ്ങളുടെ agent 55% first-contact resolution നേടുന്നു (ലക്ഷ്യം: 80%). നേരായ കേസുകൾ അത് മുകളിലേക്ക് കൈമാറുകയും സങ്കീർണമായവ സ്വയം കൈകാര്യം ചെയ്യാൻ ശ്രമിക്കുകയും ചെയ്യുന്നതായി log-കൾ കാണിക്കുന്നു. ഏറ്റവും ഫലപ്രദമായ പരിഹാരം ഏതാണ്?

- A. എപ്പോൾ കൈമാറണം, എപ്പോൾ സ്വയം പരിഹരിക്കണം എന്ന് കാണിക്കുന്ന few-shot ഉദാഹരണങ്ങളോടൊപ്പം വ്യക്തമായ കൈമാറ്റ മാനദണ്ഡങ്ങൾ system prompt-ൽ ചേർക്കുക.
- B. Agent ഒരു ആത്മവിശ്വാസ സ്കോർ (1-10) സ്വയം പറയട്ടെ, ഒരു പരിധിക്ക് താഴെയാകുമ്പോൾ കൈമാറട്ടെ.
- C. കൈമാറ്റം മുൻകൂട്ടി പ്രവചിക്കാൻ പഴയ ടിക്കറ്റുകളിൽ പരിശീലിപ്പിച്ച ഒരു പ്രത്യേക classifier വിന്യസിക്കുക.
- D. നിരാശ കണ്ടെത്താൻ sentiment analysis നടപ്പാക്കി ഒരു പരിധിക്ക് മുകളിൽ കൈമാറുക.

✅ **A എന്തുകൊണ്ട്:** അവ്യക്തമായ തീരുമാന അതിരുകളാണ് മൂലകാരണം — ഏതൊക്കെ കേസുകൾ കൈമാറണമെന്ന് agent-ന് അറിയില്ല. വ്യക്തമായ മാനദണ്ഡങ്ങളും few-shot ഉദാഹരണങ്ങളും ഇത് നേരിട്ട് പരിഹരിക്കുന്നു. B പരാജയപ്പെടുന്നു, കാരണം LLM സ്വയം പറയുന്ന ആത്മവിശ്വാസം മോശമായി calibrate ചെയ്യപ്പെട്ടതാണ്. C അമിതമായി നിർമിച്ചതാണ് — ആദ്യം prompting പരീക്ഷിക്കുക. D തീർത്തും വ്യത്യസ്തമായ ഒരു പ്രശ്നം പരിഹരിക്കുന്നു (നിരാശ ≠ സങ്കീർണത).

*ന്യായവാദ മാതൃക: സ്വയം പറയുന്ന ആത്മവിശ്വാസമോ വികാരമോ പോലുള്ള വിശ്വസിക്കാനാകാത്ത സൂചനകൾക്കു പകരം വ്യക്തവും പരിശോധിക്കാവുന്നതുമായ കൈമാറ്റ മാനദണ്ഡങ്ങൾ തിരഞ്ഞെടുക്കൽ.*

### സാഹചര്യം B: Code Generation with Claude Code

**Q4 · ഡൊമെയ്ൻ 3 — Claude Code**

നിങ്ങളുടെ ടീമിന്റെ സ്ഥിരം കോഡ് review ചെക്ക്‌ലിസ്റ്റ് പ്രവർത്തിപ്പിക്കുന്ന ഒരു ഇഷ്ടാനുസൃത `/review` slash command ഉണ്ടാക്കണം. Repository clone ചെയ്യുമ്പോൾ ഓരോ ഡെവലപ്പർക്കും ഇത് ലഭ്യമാകണം. ഈ command ഫയൽ എവിടെ ഉണ്ടാക്കണം?

- A. പ്രോജക്റ്റ് repository-യിലെ `.claude/commands/` ഡയറക്ടറിയിൽ
- B. ഓരോ ഡെവലപ്പറുടെയും ഹോം ഡയറക്ടറിയിലെ `~/.claude/commands/`-ൽ
- C. പ്രോജക്റ്റ് root-ലെ `CLAUDE.md` ഫയലിൽ
- D. ഒരു commands array ഉള്ള `.claude/config.json` ഫയലിൽ

✅ **A എന്തുകൊണ്ട്:** `.claude/commands/`-ലെ project പരിധിയുള്ള command-കൾ version control-ൽ വരുന്നു, clone-ലോ pull-ലോ എല്ലാ ഡെവലപ്പർമാർക്കും സ്വയമേവ ലഭ്യമാകുന്നു. B വ്യക്തിപരമാണ് — പങ്കിടുന്നില്ല. C നിർദേശങ്ങൾക്കാണ്, command നിർവചനങ്ങൾക്കല്ല. D നിലവിലില്ല.

*ന്യായവാദ മാതൃക: പങ്കിട്ട, version control-ൽ വരുന്ന Claude Code ക്രമീകരണം എവിടെ വേണമെന്നും വ്യക്തിപരമോ നിലവിലില്ലാത്തതോ ആയ സ്ഥാനങ്ങൾ ഏതെന്നും അറിയൽ.*

**Q5 · ഡൊമെയ്ൻ 3 — Claude Code**

ഒരു monolithic ആപ്ലിക്കേഷനെ microservices ആയി പുനഃക്രമീകരിക്കാൻ നിങ്ങളെ ചുമതലപ്പെടുത്തി — ഡസൻ കണക്കിന് ഫയലുകളിലായി മാറ്റങ്ങൾ, സേവന അതിരുകളെയും ആശ്രിതത്വങ്ങളെയും കുറിച്ചുള്ള തീരുമാനങ്ങൾ. ഏത് സമീപനം സ്വീകരിക്കണം?

- A. മാറ്റങ്ങൾ വരുത്തും മുൻപ് codebase പര്യവേക്ഷണം ചെയ്യാനും ആശ്രിതത്വങ്ങൾ മനസ്സിലാക്കാനും ഒരു നടപ്പാക്കൽ സമീപനം രൂപകൽപ്പന ചെയ്യാനും plan mode-ൽ പ്രവേശിക്കുക.
- B. നേരിട്ടുള്ള നിർവഹണത്തിൽ തുടങ്ങി ക്രമേണ മാറ്റങ്ങൾ വരുത്തുക, നടപ്പാക്കൽ സ്വാഭാവിക സേവന അതിരുകൾ വെളിപ്പെടുത്തട്ടെ.
- C. ഓരോ സേവനവും എങ്ങനെ ഘടനപ്പെടുത്തണമെന്ന് കൃത്യമായി വിശദീകരിക്കുന്ന സമഗ്ര മുൻകൂർ നിർദേശങ്ങളോടെ നേരിട്ടുള്ള നിർവഹണം ഉപയോഗിക്കുക.
- D. നേരിട്ടുള്ള നിർവഹണത്തിൽ തുടങ്ങി, അപ്രതീക്ഷിത സങ്കീർണത നേരിട്ടാൽ മാത്രം plan mode-ലേക്ക് മാറുക.

✅ **A എന്തുകൊണ്ട്:** Architecture തീരുമാനങ്ങളും പല സാധുവായ വഴികളുമുള്ള വലിയ തോതിലുള്ള മാറ്റങ്ങൾക്കാണ് plan mode രൂപകൽപ്പന ചെയ്തിരിക്കുന്നത് — കൃത്യം ഈ സാഹചര്യം. ആശ്രിതത്വങ്ങൾ വൈകി കണ്ടെത്തുമ്പോൾ B ചെലവേറിയ പുനർനിർമാണത്തിന്റെ അപകടമുണ്ടാക്കുന്നു. ശരിയായ ഘടന നിങ്ങൾക്ക് ഇതിനകം അറിയാമെന്ന് C കരുതുന്നു. സങ്കീർണത ജോലിയിൽ ഇതിനകം പറഞ്ഞിട്ടുണ്ടെന്ന് D അവഗണിക്കുന്നു.

*ന്യായവാദ മാതൃക: ഒരു ജോലിയുടെ വലുപ്പവും അവ്യക്തതയും, കോഡ് മാറ്റങ്ങൾക്കു മുൻപ് plan mode ആവശ്യപ്പെടുന്നുവെന്ന് തിരിച്ചറിയൽ.*

**Q6 · ഡൊമെയ്ൻ 3 — Claude Code**

നിങ്ങളുടെ codebase-ൽ React components (functional ശൈലി), API handlers (async/await പിഴവ് കൈകാര്യം), database models (repository pattern) എന്നിവയുണ്ട്. ടെസ്റ്റ് ഫയലുകൾ എല്ലായിടത്തും ചിതറിക്കിടക്കുന്നു (ഉദാ: `Button.tsx`-ന് അടുത്ത് `Button.test.tsx`). ഓരോ ഫയൽ തരത്തിനും ശരിയായ രീതികൾ Claude സ്വയമേവ പ്രയോഗിക്കുന്നുവെന്ന് ഉറപ്പാക്കാനുള്ള ഏറ്റവും പരിപാലിക്കാവുന്ന വഴി ഏതാണ്?

- A. ഫയൽ path-കൾ നോക്കി രീതികൾ വ്യവസ്ഥാപിതമായി പ്രയോഗിക്കാൻ glob മാതൃകകൾ പറയുന്ന YAML frontmatter-ഓടു കൂടിയ നിയമ ഫയലുകൾ `.claude/rules/`-ൽ ഉണ്ടാക്കുക
- B. ഓരോ മേഖലയ്ക്കും തലക്കെട്ടുകൾക്കു കീഴിൽ എല്ലാ രീതികളും root `CLAUDE.md`-ൽ ഒന്നിപ്പിക്കുക, ഏത് വിഭാഗം ബാധകമെന്ന് Claude ഊഹിക്കട്ടെ
- C. ഓരോ കോഡ് തരത്തിനും `.claude/skills/`-ൽ skill-കൾ ഉണ്ടാക്കുക
- D. ഓരോ ഉപഡയറക്ടറിയിലും പ്രത്യേകം `CLAUDE.md` വെക്കുക

✅ **A എന്തുകൊണ്ട്:** `**/*.test.tsx` പോലുള്ള glob മാതൃകകൾ ഡയറക്ടറി സ്ഥാനം നോക്കാതെ പ്രവർത്തിക്കുന്നു — codebase-ൽ ചിതറിക്കിടക്കുന്ന ടെസ്റ്റ് ഫയലുകൾക്ക് അത്യാവശ്യം. B ഊഹത്തെ ആശ്രയിക്കുന്നു — വിശ്വസനീയമല്ല. C കൈകൊണ്ട് വിളിക്കേണ്ടിവരുന്നു — "സ്വയമേവ" അല്ല. CLAUDE.md ഫയലുകൾ ഡയറക്ടറിയോട് ബന്ധിച്ചതായതിനാൽ പല ഡയറക്ടറികളിൽ ചിതറിയ ഫയലുകൾ D-ക്ക് കൈകാര്യം ചെയ്യാനാകില്ല.

*ന്യായവാദ മാതൃക: ഊഹത്തെയോ ഡയറക്ടറി ഘടനയെയോ ആശ്രയിക്കാതെ, ഫയൽ തരം അനുസരിച്ചുള്ള രീതികൾക്ക് path പരിധിയുള്ള, glob അടിസ്ഥാന നിയമങ്ങൾ ഉപയോഗിക്കൽ.*

### സാഹചര്യം C: Multi-Agent Research System

**Q7 · ഡൊമെയ്ൻ 1 — Agentic Architecture**

"സർഗാത്മക വ്യവസായങ്ങളിൽ AI-യുടെ ആഘാതം" എന്ന വിഷയത്തിൽ സിസ്റ്റം പ്രവർത്തിപ്പിച്ചപ്പോൾ ഓരോ subagent-ഉം വിജയകരമായി പൂർത്തിയാക്കുന്നു. പക്ഷേ അന്തിമ റിപ്പോർട്ടുകൾ ദൃശ്യകല മാത്രം ഉൾക്കൊള്ളുന്നു — സംഗീതം, എഴുത്ത്, സിനിമ എന്നിവ വിട്ടുപോകുന്നു. Coordinator log-കൾ കാണിക്കുന്നത് അത് വിഷയം ഇങ്ങനെ വിഭജിച്ചു എന്നാണ്: "ഡിജിറ്റൽ കലയിൽ AI," "ഗ്രാഫിക് ഡിസൈനിൽ AI," "ഫോട്ടോഗ്രാഫിയിൽ AI." ഏറ്റവും സാധ്യതയുള്ള മൂലകാരണം എന്താണ്?

- A. Coverage വിടവുകൾ കണ്ടെത്താനുള്ള നിർദേശങ്ങൾ synthesis agent-ന് ഇല്ല.
- B. Coordinator agent-ന്റെ task decomposition വളരെ ഇടുങ്ങിയതാണ് — subagent ചുമതലകൾ പ്രസക്തമായ എല്ലാ മേഖലകളും ഉൾക്കൊള്ളുന്നില്ല.
- C. വെബ് തിരച്ചിൽ agent-ന്റെ ചോദ്യങ്ങൾ വേണ്ടത്ര സമഗ്രമല്ല.
- D. രേഖാ വിശകലന agent ദൃശ്യേതര ഉറവിടങ്ങൾ ഒഴിവാക്കുന്നു.

✅ **B എന്തുകൊണ്ട്:** Coordinator-ന്റെ log-കൾ മൂലകാരണം തെളിയിക്കുന്നു — അത് ദൃശ്യകല ഉപജോലികൾ മാത്രമേ ഏൽപ്പിച്ചുള്ളൂ. Subagent-കൾ ഏൽപ്പിച്ചത് കൃത്യമായി ചെയ്തു. എന്ത് ഏൽപ്പിച്ചു എന്നതാണ് പ്രശ്നം. A, C, D എന്നിവ അവയുടെ പരിധിക്കുള്ളിൽ ശരിയായി പ്രവർത്തിച്ച തുടർ agent-കളെ കുറ്റപ്പെടുത്തുന്നു.

*ന്യായവാദ മാതൃക: ഏൽപ്പിച്ച പരിധിക്കുള്ളിൽ ശരിയായി പ്രവർത്തിച്ച agent-കളെ കുറ്റപ്പെടുത്തുന്നതിനു പകരം, ഒരു തുടർ ലക്ഷണത്തെ (അപൂർണമായ ഫലം) അതിന്റെ യഥാർഥ മുകൾത്തട്ട് മൂലകാരണത്തിലേക്ക് പിന്തുടരൽ.*

**Q8 · ഡൊമെയ്ൻ 5 — Context & Reliability**

ഒരു സങ്കീർണ വിഷയം ഗവേഷണം ചെയ്യുന്നതിനിടെ വെബ് തിരച്ചിൽ subagent timeout ആകുന്നു. ബുദ്ധിപരമായ വീണ്ടെടുക്കൽ സാധ്യമാക്കാൻ ഈ പരാജയം coordinator-ലേക്ക് എങ്ങനെ എത്തണം?

- A. പരാജയത്തിന്റെ തരം, ശ്രമിച്ച ചോദ്യം, ഏതെങ്കിലും ഭാഗിക ഫലങ്ങൾ, സാധ്യമായ ബദൽ സമീപനങ്ങൾ എന്നിവ ഉൾപ്പെടെ ഘടനാപരമായ പിഴവ് context coordinator-ന് നൽകുക.
- B. Subagent-നുള്ളിൽ exponential backoff-ഓടെ സ്വയമേവ retry ചെയ്യുക, എല്ലാ retry-കൾക്കും ശേഷം പൊതുവായ "search unavailable" നൽകുക.
- C. Timeout പിടിച്ച് ഒരു ശൂന്യ ഫല സെറ്റ് വിജയമായി അടയാളപ്പെടുത്തി നൽകുക.
- D. മുഴുവൻ ഗവേഷണ workflow-ഉം അവസാനിപ്പിക്കുന്ന ഒരു top-level handler-ലേക്ക് timeout exception കൈമാറുക.

✅ **A എന്തുകൊണ്ട്:** ഘടനാപരമായ പിഴവ് context, തീരുമാനിക്കാൻ coordinator-ന് വേണ്ടത് നൽകുന്നു: വ്യത്യസ്ത ചോദ്യത്തോടെ retry ചെയ്യണോ? ബദൽ പരീക്ഷിക്കണോ? ഭാഗിക ഫലങ്ങളുമായി മുന്നോട്ട് പോകണോ? B വിലപ്പെട്ട context ഒരു പൊതു സന്ദേശത്തിനു പിന്നിൽ മറയ്ക്കുന്നു. C പരാജയത്തെ വിജയമായി അടയാളപ്പെടുത്തുന്നു — coordinator ഇല്ലാത്ത ഡാറ്റയുമായി മുന്നോട്ട് പോകും. D ഒരു subagent പരാജയത്തിന് മുഴുവൻ ജോലിയും കൊല്ലുന്നു.

*ന്യായവാദ മാതൃക: പരാജയം മറയ്ക്കുകയോ അമിതമായി പ്രതികരിക്കുകയോ ചെയ്യുന്നതിനു പകരം, ഒരു മുകൾത്തട്ട് coordinator-ന് അറിവോടെ വീണ്ടെടുക്കൽ തീരുമാനം എടുക്കാൻ ഘടനാപരമായ പിഴവ് കൈമാറ്റത്തിൽ എന്ത് ഉണ്ടാകണമെന്ന് മനസ്സിലാക്കൽ.*

**Q9 · ഡൊമെയ്ൻ 2 — Tool Design & MCP**

ലളിതമായ വസ്തുതാ പരിശോധനകൾക്കായി (തീയതികൾ, പേരുകൾ, സ്ഥിതിവിവരക്കണക്കുകൾ) synthesis agent പതിവായി coordinator-ലേക്ക് നിയന്ത്രണം തിരികെ നൽകുന്നു, ഓരോ ജോലിക്കും 2-3 അധിക റൗണ്ട് ട്രിപ്പുകൾ (40% അധിക latency) ചേർക്കുന്നു. 85% ലളിതമായ പരിശോധനകളാണ്; 15%-ന് ആഴത്തിലുള്ള അന്വേഷണം വേണം. ഏറ്റവും ഫലപ്രദമായ സമീപനം ഏതാണ്?

- A. ലളിതമായ അന്വേഷണങ്ങൾക്ക് synthesis agent-ന് പരിധിയുള്ള ഒരു `verify_fact` ടൂൾ നൽകുക, സങ്കീർണ പരിശോധനകൾ coordinator വഴി തുടരട്ടെ.
- B. Synthesis agent എല്ലാ പരിശോധനാ ആവശ്യങ്ങളും ശേഖരിച്ച് അവസാനം ഒരു batch ആയി coordinator-ന് അയക്കട്ടെ.
- C. Synthesis agent-ന് എല്ലാ വെബ് തിരച്ചിൽ ടൂളുകളിലേക്കും പ്രവേശനം നൽകുക.
- D. Synthesis agent-ന് എന്ത് വേണ്ടിവരുമെന്ന് മുൻകൂട്ടി കണ്ട് വെബ് തിരച്ചിൽ agent അധിക context cache ചെയ്യട്ടെ.

✅ **A എന്തുകൊണ്ട്:** Least privilege — 85% വരുന്ന സാധാരണ സാഹചര്യത്തിന് വേണ്ടത് മാത്രം synthesis-ന് നൽകുക. 15% സങ്കീർണ കേസുകൾ coordinator കൈകാര്യം ചെയ്യുന്നു. B തടസ്സപ്പെടുത്തുന്ന ആശ്രിതത്വങ്ങൾ ഉണ്ടാക്കുന്നു, കാരണം synthesis ഘട്ടങ്ങൾ നേരത്തേ പരിശോധിച്ച വസ്തുതകളെ ആശ്രയിച്ചേക്കാം. C synthesis-ന് അമിതമായി നൽകുന്നു, ഉത്തരവാദിത്ത വേർതിരിവ് ലംഘിക്കുന്നു. D ഊഹാധിഷ്ഠിത caching ആണ്, എന്ത് വേണ്ടിവരുമെന്ന് വിശ്വസനീയമായി പ്രവചിക്കാനാകില്ല.

*ന്യായവാദ മാതൃക: least-privilege ടൂൾ രൂപകൽപ്പന പ്രയോഗിക്കൽ — ഒരു agent-ന്റെ യഥാർഥ, അളന്ന ഉപയോഗ രീതിയോട് ചേരുന്ന ഇടുങ്ങിയ പരിധിയുള്ള ഒരു ടൂൾ നൽകൽ.*

### സാഹചര്യം D: Claude Code for CI/CD

**Q10 · ഡൊമെയ്ൻ 3 — Claude Code**

നിങ്ങളുടെ pipeline സ്ക്രിപ്റ്റ് `claude "Analyse this pull request for security issues"` പ്രവർത്തിപ്പിക്കുന്നു, പക്ഷേ ജോലി അനന്തമായി തൂങ്ങിനിൽക്കുന്നു. Claude Code ഇടപെടൽ ഇൻപുട്ടിനായി കാത്തിരിക്കുന്നതായി log-കൾ കാണിക്കുന്നു. ശരിയായ പരിഹാരം എന്താണ്?

- A. `-p` flag ചേർക്കുക: `claude -p "Analyse this pull request for security issues"`
- B. പ്രവർത്തിപ്പിക്കും മുൻപ് `CLAUDE_HEADLESS=true` എന്ന environment variable നിശ്ചയിക്കുക
- C. stdin /dev/null-ലേക്ക് തിരിച്ചുവിടുക
- D. `--batch` flag ചേർക്കുക

✅ **A എന്തുകൊണ്ട്:** ഇടപെടലില്ലാത്ത മോഡിൽ Claude Code പ്രവർത്തിപ്പിക്കാനുള്ള രേഖപ്പെടുത്തിയ വഴിയാണ് `-p` (അല്ലെങ്കിൽ `--print`) flag. അത് prompt പ്രോസസ്സ് ചെയ്ത്, user ഇൻപുട്ടിനായി കാത്തിരിക്കാതെ പുറത്തുകടക്കുന്നു. B, C, D എന്നിവ നിലവിലില്ലാത്ത സൗകര്യങ്ങളോ ഇത് ശരിയായി പരിഹരിക്കാത്ത Unix കുറുക്കുവഴികളോ ആണ്.

*ന്യായവാദ മാതൃക: യുക്തിസഹമെന്ന് തോന്നിക്കുന്ന പക്ഷേ നിലവിലില്ലാത്ത കുറുക്കുവഴികളിലേക്ക് പോകാതെ, ഓട്ടോമേഷന് രേഖപ്പെടുത്തിയ, ശരിയായ ഒരേയൊരു ഇടപെടലില്ലാത്ത flag അറിയൽ.*

**Q11 · ഡൊമെയ്ൻ 4 — Prompt Engineering**

50% ചെലവ് ലാഭത്തിനായി (1) തടസ്സപ്പെടുത്തുന്ന ഒരു merge-നു മുൻപുള്ള പരിശോധനയും (2) ഒരു രാത്രി സാങ്കേതിക കട റിപ്പോർട്ടും Message Batches API-ലേക്ക് മാറ്റാൻ നിങ്ങളുടെ മാനേജർ നിർദേശിക്കുന്നു. ഇത് എങ്ങനെ വിലയിരുത്തും?

- A. സാങ്കേതിക കട റിപ്പോർട്ടുകൾക്ക് മാത്രം batch പ്രോസസ്സിങ് ഉപയോഗിക്കുക; merge-നു മുൻപുള്ള പരിശോധനകൾക്ക് തത്സമയ വിളികൾ നിലനിർത്തുക.
- B. രണ്ടും status polling-ഓടെ batch-ലേക്ക് മാറ്റുക.
- C. Batch ക്രമ പ്രശ്നങ്ങൾ ഒഴിവാക്കാൻ രണ്ടിനും തത്സമയ വിളികൾ നിലനിർത്തുക.
- D. രണ്ടും batch-ലേക്ക് മാറ്റി, timeout ആയാൽ തത്സമയത്തിലേക്ക് മടങ്ങുക.

✅ **A എന്തുകൊണ്ട്:** Batch-കൾക്ക് 24 മണിക്കൂർ വരെ എടുക്കാം — ഡെവലപ്പർമാർ കാത്തിരിക്കുന്ന, തടസ്സപ്പെടുത്തുന്ന merge-നു മുൻപുള്ള പരിശോധനകൾക്ക് ഇത് സ്വീകാര്യമല്ല. രാത്രി റിപ്പോർട്ടുകൾക്ക് 24 മണിക്കൂർ കുഴപ്പമില്ല. ഓരോ workflow-ഉം ശരിയായ API-യുമായി ചേർക്കുക. "പലപ്പോഴും വേഗം" എന്നതിനെ B ആശ്രയിക്കുന്നു, തടസ്സപ്പെടുത്തുന്ന ഒഴുക്കുകൾക്ക് അത് സ്വീകാര്യമല്ല. C തെറ്റാണ് — batch ഫലങ്ങൾ custom_id വഴി ബന്ധിപ്പിക്കപ്പെടുന്നു. D അനാവശ്യ സങ്കീർണത ചേർക്കുന്നു.

*ന്യായവാദ മാതൃക: രണ്ടിനും ഒരേ പൊതു നയം പ്രയോഗിക്കുന്നതിനു പകരം, ഓരോ workflow-ന്റെയും യഥാർഥ latency സഹിഷ്ണുതയോട് API തിരഞ്ഞെടുപ്പ് (batch vs. തത്സമയം) ചേർക്കൽ.*

**Q12 · ഡൊമെയ്ൻ 4 — Prompt Engineering**

ഒരു PR 14 ഫയലുകൾ മാറ്റുന്നു. ഒറ്റ pass review അസ്ഥിരമായ ഫലങ്ങൾ നൽകുന്നു: ചില ഫയലുകൾക്ക് വിശദം, മറ്റുള്ളവയ്ക്ക് ഉപരിപ്ലവം, വ്യക്തമായ ബഗുകൾ വിട്ടുപോയി, പരസ്പര വിരുദ്ധമായ feedback — ഒരു ഫയലിൽ ഒരു മാതൃക flag ചെയ്യുകയും മറ്റൊരിടത്ത് അതേ കോഡ് അംഗീകരിക്കുകയും ചെയ്യുന്നു. എങ്ങനെ പുനഃക്രമീകരിക്കണം?

- A. കേന്ദ്രീകൃതമായ pass-കളായി വിഭജിക്കുക: പ്രാദേശിക പ്രശ്നങ്ങൾക്കായി ഓരോ ഫയലും വെവ്വേറെ വിശകലനം ചെയ്യുക, പിന്നെ ഫയലുകൾക്കിടയിലെ ഡാറ്റാ ഒഴുക്ക് പരിശോധിക്കുന്ന വേറിട്ട ഒരു integration pass പ്രവർത്തിപ്പിക്കുക.
- B. വലിയ PR-കൾ 3-4 ഫയലുകളുള്ള ചെറിയ സമർപ്പണങ്ങളായി വിഭജിക്കാൻ ഡെവലപ്പർമാരോട് ആവശ്യപ്പെടുക.
- C. വലിയ context window-ഉള്ള ഉയർന്ന തട്ടിലുള്ള ഒരു മോഡലിലേക്ക് മാറുക.
- D. മുഴുവൻ PR-ലും മൂന്ന് സ്വതന്ത്ര pass-കൾ പ്രവർത്തിപ്പിച്ച്, മൂന്നിൽ രണ്ടിലെങ്കിലും വരുന്ന പ്രശ്നങ്ങൾ മാത്രം flag ചെയ്യുക.

✅ **A എന്തുകൊണ്ട്:** ഓരോ ഫയലായുള്ള വിശകലനം സ്ഥിരമായ ആഴം ഉറപ്പാക്കുന്നു. വേറിട്ട ഒരു integration pass ഫയലുകൾക്കിടയിലെ പ്രശ്നങ്ങൾ പിടിക്കുന്നു. ഇത് ശ്രദ്ധ ചിതറുന്നത് നേരിട്ട് പരിഹരിക്കുന്നു. B സിസ്റ്റം മെച്ചപ്പെടുത്താതെ ഭാരം ഡെവലപ്പർമാരിലേക്ക് മാറ്റുന്നു. വലിയ context window ശ്രദ്ധയുടെ ഗുണനിലവാര പ്രശ്നം പരിഹരിക്കില്ലെന്ന് C തെറ്റിദ്ധരിക്കുന്നു. സമവായം ആവശ്യപ്പെടുന്നതിലൂടെ യഥാർഥ ബഗുകൾ കണ്ടെത്തുന്നത് D അടിച്ചമർത്തും.

*ന്യായവാദ മാതൃക: വലിയ ഒരു ബഹു-ഫയൽ ഇൻപുട്ടിൽ ശ്രദ്ധ ചിതറുന്നത് തിരിച്ചറിഞ്ഞ്, കൂടുതൽ കംപ്യൂട്ടിങ്ങോ മോഡൽ വലുപ്പമോ പ്രക്രിയാ ഭാരമോ ചേർക്കുന്നതിനു പകരം review പ്രക്രിയ തന്നെ പുനഃക്രമീകരിക്കൽ.*
