## ഘടനാപരമായ ഔട്ട്പുട്ട് ഉറപ്പാക്കൽ — tool_use + JSON Schema

യഥാർഥ ലോകത്തെ പല ആപ്ലിക്കേഷനുകൾക്കും Claude-ന്റെ ഔട്ട്പുട്ട് യന്ത്രത്തിന് വായിക്കാവുന്നതാകണം — ഒരു ഖണ്ഡിക ഗദ്യമല്ല, നിങ്ങളുടെ ബാക്കെൻഡ് കോഡിന് വായിച്ച് പ്രവർത്തിക്കാവുന്ന ഒരു JSON ഒബ്ജക്ട്. ലളിതമായ സമീപനം prompt-ൽ ചോദിക്കുക എന്നതാണ്: "ദയവായി JSON-ൽ മാത്രം മറുപടി നൽകുക." ഇത് ചിലപ്പോൾ പ്രവർത്തിക്കും, പക്ഷേ ദുർബലമാണ്: JSON-ന് മുൻപ് Claude വിശദീകരണ ടെക്സ്റ്റ് ചേർത്തേക്കാം, markdown കോഡ് fence-ൽ പൊതിഞ്ഞേക്കാം, സ്ഥിരതയില്ലാത്ത ഫീൽഡ് പേരുകൾ ഉപയോഗിച്ചേക്കാം, അല്ലെങ്കിൽ വ്യാകരണപരമായി അസാധുവായ JSON ഉണ്ടാക്കിയേക്കാം.

### വിശ്വസനീയമായ സമീപനം: tool_use

നിങ്ങൾക്ക് വേണ്ട ഫീൽഡുകൾ, തരങ്ങൾ, ഘടന എന്നിവ കൃത്യമായി വിവരിക്കുന്ന ഒരു JSON schema-യോടെ ഒരു **tool** നിർവചിച്ച്, സ്വതന്ത്ര രൂപത്തിൽ മറുപടി എഴുതുന്നതിന് പകരം ആ ടൂൾ വിളിക്കാൻ Claude-നെ അനുവദിക്കുന്നതാണ് കൂടുതൽ വിശ്വസനീയമായ രീതി. ടൂളിന്റെ ഇൻപുട്ട് schema API നിർബന്ധമാക്കുന്നതിനാൽ, തിരികെ ലഭിക്കുന്ന ഡാറ്റ നിങ്ങൾ നിർവചിച്ച രൂപവുമായി വിശ്വസനീയമായി യോജിക്കുന്നു — വിട്ടുപോയ ബ്രാക്കറ്റുകളില്ല, സ്ഥിരതയില്ലാത്ത ഫീൽഡ് പേരുകളില്ല, payload-ൽ കലർന്ന അധിക വിവരണങ്ങളില്ല.

### ഘടനയും അർഥവും — ഏറ്റവും പ്രധാനപ്പെട്ട വ്യത്യാസം

ഉൾക്കൊള്ളേണ്ട ഏറ്റവും പ്രധാന സൂക്ഷ്മത ഇതാണ്: ഒരു JSON schema **ഘടന** ഉറപ്പാക്കുന്നു, **അർഥം** അല്ല. ഘടന എന്നാൽ ഫീൽഡ് പേരുകൾ ഉണ്ട്, തരങ്ങൾ ശരിയാണ് (`total_amount` യഥാർഥത്തിൽ ഒരു സംഖ്യയാണ്, ഒരു string അല്ല), നിർബന്ധിത ഫീൽഡുകൾ ഉണ്ട് എന്നാണ്. അർഥം എന്നാൽ *ഉള്ളടക്കം* യഥാർഥത്തിൽ ശരിയാണ് എന്നാണ് — ആകെത്തുക യഥാർഥത്തിൽ line item-കളുടെ തുകയ്ക്ക് തുല്യമാണ്, തീയതി കാലക്രമത്തിൽ യുക്തിസഹമാണ്, എടുത്ത ഇൻവോയ്സ് നമ്പർ യഥാർഥത്തിൽ ഉറവിട രേഖയിൽ ഉണ്ട്. Schema പരിശോധനയ്ക്ക് ഇവയൊന്നും പരിശോധിക്കാനാകില്ല. ഒരു മറുപടി തികച്ചും സാധുവായ JSON ആയിരിക്കുകയും എന്നിട്ടും വസ്തുതാപരമായി തെറ്റാവുകയും ചെയ്യാം. ഇതുകൊണ്ടാണ് ഘടനാപരമായ ഔട്ട്പുട്ട് നിർബന്ധം സാധാരണയായി വ്യാപാര ലോജിക് പരിശോധിക്കുന്ന ഒരു വെവ്വേറെ validation ഘട്ടത്തോടൊപ്പം വരുന്നത് — schema കൃത്യതയും അർഥപരമായ കൃത്യതയും രണ്ട് വ്യത്യസ്ത സംവിധാനങ്ങൾ പരിഹരിക്കുന്ന രണ്ട് വ്യത്യസ്ത പ്രശ്നങ്ങളാണ്.

### Schema രൂപകൽപ്പന: required, optional, enum

നല്ല schema രൂപകൽപ്പന "JSON തിരികെ കിട്ടുക" എന്നതിനപ്പുറം യഥാർഥ ജോലി ചെയ്യുന്നു:

- **നിർബന്ധിത ഫീൽഡുകൾ** (ഒരു `required` നിരയിൽ പട്ടികപ്പെടുത്തിയവ) ഏതൊക്കെ ഫീൽഡുകൾ എപ്പോഴും നിറയ്ക്കണമെന്ന് Claude-നോട് പറയുന്നു — ഒരു സാധുവായ എടുക്കലിൽ എപ്പോഴും ഉണ്ടാകേണ്ട ഫീൽഡുകൾക്ക് ഇത് ഉപയോഗിക്കുക.
- **ഐച്ഛിക / nullable ഫീൽഡുകൾ** (ഉദാ: `["string", "null"]` എന്ന് തരം നൽകിയവ) ഉറവിടത്തിൽ ന്യായമായും ഇല്ലാതിരിക്കാവുന്ന വിവരങ്ങൾക്കുള്ളതാണ്. Hallucination തടയാൻ ഇത് നിർണായകമാണ്: ഒരു ഫീൽഡ് *നിർബന്ധിതമാണെങ്കിലും* ആ വിവരം രേഖയിൽ യഥാർഥത്തിൽ ഇല്ലെങ്കിൽ, schema തൃപ്തിപ്പെടുത്താൻ വേണ്ടി മാത്രം വിശ്വസനീയമെന്ന് തോന്നിക്കുന്ന ഒരു മൂല്യം Claude ഉണ്ടാക്കിയേക്കാം. ഫീൽഡ് nullable ആക്കുന്നത് പകരം "കണ്ടെത്തിയില്ല" എന്ന് പറയാൻ വ്യക്തവും സാധുവുമായ ഒരു വഴി Claude-ന് നൽകുന്നു.
- **Enum-കൾ** ഒരു ഫീൽഡിനെ അനുവദനീയമായ ഒരു നിശ്ചിത കൂട്ടം മൂല്യങ്ങളിലേക്ക് പരിമിതപ്പെടുത്തുന്നു (ഉദാ: `"status": "pending" | "paid" | "overdue" | "other"`), ഇത് നിങ്ങളുടെ തുടർന്നുള്ള കോഡ് പരിശോധിക്കുന്ന ഒരു ഫീൽഡിലേക്ക് `"Pending"`, `"PAID"` പോലുള്ളവയോ പര്യായങ്ങളോ കടന്നുവരുന്ന സ്വതന്ത്ര-ടെക്സ്റ്റ് വ്യതിയാനം തടയുന്നു. ഒരു enum-നൊപ്പം ഒരു `"other"` പൊതു മൂല്യവും, `"other"` തിരഞ്ഞെടുക്കുമ്പോൾ ഉപയോഗിക്കാൻ ഒരു സ്വതന്ത്ര-ടെക്സ്റ്റ് `status_detail` ഫീൽഡും ചേർക്കുന്നത് സ്ഥിരതയും അപ്രതീക്ഷിത സാഹചര്യങ്ങൾക്ക് ഒരു രക്ഷാവഴിയും ഒരുമിച്ച് നൽകുന്നു.

### ഗദ്യ-JSON vs. tool_use + schema

| വശം | "ദയവായി JSON-ൽ മറുപടി നൽകുക" (ഗദ്യ നിർദേശം) | `tool_use` + JSON Schema |
|---|---|---|
| രൂപ ഉറപ്പ് | പരമാവധി ശ്രമം — ടെക്സ്റ്റോ, കോഡ് fence-ഓ, തകർന്ന JSON-ഓ ചേർത്തേക്കാം | നിങ്ങളുടെ schema-യുമായി API നിർബന്ധമാക്കുന്നു |
| ഫീൽഡ് സ്ഥിരത | വ്യതിചലിക്കാം (അക്ഷരത്തെറ്റുകൾ, പേര് മാറിയ ഫീൽഡുകൾ, സ്ഥിരതയില്ലാത്ത അക്ഷരരൂപം) | Schema നിർവചിച്ച property പേരുകളിലും തരങ്ങളിലും ഉറപ്പിച്ചിരിക്കുന്നു |
| വിട്ടുപോയ ഡാറ്റ കൈകാര്യം | ഫീൽഡ് "നിറയ്ക്കാൻ" മാതൃക ഒരു മൂല്യം ഉണ്ടാക്കിയേക്കാം | Nullable ഫീൽഡുകൾ മാതൃകയെ വ്യക്തമായി `null` നൽകാൻ അനുവദിക്കുന്നു |
| അർഥപരമായ കൃത്യത ഉറപ്പാക്കുന്നുണ്ടോ? | ഇല്ല | ഇല്ല — schema ഘടന മാത്രം പരിശോധിക്കുന്നു, ഒരിക്കലും അർഥമല്ല |

> **🌍 യഥാർഥ ഉദാഹരണം:** സ്കാൻ ചെയ്ത വെണ്ടർ PDF-കളിൽ നിന്ന് ഇൻവോയ്സ് ഡാറ്റ ഒരു ഡാറ്റാബേസിലേക്ക് എടുക്കുന്ന ഒരു pipeline ഒരു ഫിനാൻസ് ടീം നിർമിക്കുന്നു. തുടക്കത്തിൽ അവർ "ഇൻവോയ്സ് ഡാറ്റ JSON ആയി നൽകുക" എന്ന് മാത്രം Claude-നോട് ആവശ്യപ്പെട്ടു — ചില മറുപടികളിൽ "ഇതാ എടുത്ത ഡാറ്റ:" പോലുള്ള ഒരു ആദ്യ വാക്യം ഉണ്ടായിരുന്നു, അത് അവരുടെ JSON parser പൂർണമായി തകർത്തു. നിർവചിച്ച ഒരു schema-യോടെ (നിർബന്ധിത `invoice_number`, `total_amount`, nullable `discount_code`, `status`-ന് ഒരു enum) ഒരു `tool_use` വിളിയിലേക്ക് മാറിയത് parsing പരാജയങ്ങൾ പൂർണമായി ഇല്ലാതാക്കി. പക്ഷേ schema നിർബന്ധം മാത്രം പോരെന്നും ടീം കയ്പേറിയ അനുഭവത്തിലൂടെ പഠിച്ചു: ഒരു എടുക്കൽ തികച്ചും സാധുവായ JSON ആയിരുന്നു, പക്ഷേ അതിലെ `total_amount` line item-കളുടെ തുകയുമായി യോജിച്ചില്ല — schema-ക്ക് ഒരിക്കലും കണ്ടെത്താനാകാത്ത ഒരു അർഥപരമായ പിഴവ്. ഏതൊരു എടുക്കലും സ്വീകരിക്കും മുൻപ് ആകെത്തുക line-item തുകയുമായി താരതമ്യം ചെയ്യുന്ന ഒരു വെവ്വേറെ validation ഘട്ടം അവർ ചേർത്തു.

> **⚠️ ശ്രദ്ധിക്കുക:** "JSON വിജയകരമായി വായിച്ചു" എന്നാൽ "ഡാറ്റ ശരിയാണ്" എന്ന് കരുതരുത്. ഘടനാപരമായ സാധുതയും വസ്തുതാപരമായ കൃത്യതയും സ്വതന്ത്രമാണ് — വ്യാപാര ലോജിക് (ആകെത്തുകകൾ, തീയതികൾ, പരസ്പര പരാമർശങ്ങൾ) schema പരിശോധനയിൽ നിന്ന് വെവ്വേറെ എപ്പോഴും പരിശോധിക്കുക.
