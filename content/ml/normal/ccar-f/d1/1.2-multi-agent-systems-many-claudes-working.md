## Multi-Agent സിസ്റ്റങ്ങൾ — പല Claude-കൾ ഒരുമിച്ച് പ്രവർത്തിക്കുമ്പോൾ

ഒരൊറ്റ agentic loop (മുൻ വിഷയം കാണുക) ശക്തമാണ്, പക്ഷേ ചില പ്രശ്നങ്ങൾ ഒരു Claude instance-ന് ഒരൊറ്റ context window-നുള്ളിൽ കാര്യക്ഷമമായി കൈകാര്യം ചെയ്യാൻ കഴിയാത്തത്ര വലുതോ, വിശാലമോ, വ്യത്യസ്ത വൈദഗ്ധ്യം ആവശ്യപ്പെടുന്നതോ ആണ്. ഓരോന്നും വ്യത്യസ്ത പങ്ക് വഹിക്കുന്ന പല Claude instance-കൾക്കിടയിൽ ജോലി വിഭജിച്ചാണ് multi-agent സിസ്റ്റങ്ങൾ ഇത് പരിഹരിക്കുന്നത്.

### coordinator/subagent ബന്ധം

ഏറ്റവും സാധാരണമായ ഘടനയിൽ ഒരു **coordinator** (ചിലപ്പോൾ orchestrator എന്ന് വിളിക്കുന്നു) പല **subagent**-കളെ (workers) നയിക്കുന്നു. ഒരു പ്രോജക്ടിന്റെ ഭാഗങ്ങൾ വിദഗ്ധർക്ക് ഏൽപ്പിച്ച്, എല്ലാവരുടെയും ഫലം ഒരൊറ്റ ഉൽപ്പന്നമാക്കി ചേർക്കുന്ന ഒരു മാനേജരെപ്പോലെ കരുതുക. ചിത്രത്തിൽ:

```
           ┌─────────────────────┐
           │   COORDINATOR       │  ← the manager Claude
           │   (Orchestrator)    │
           └──────────┬──────────┘
        ┌─────────────┼──────────────┐
        ↓             ↓              ↓
  ┌──────────┐  ┌──────────┐  ┌──────────┐
  │ Subagent │  │ Subagent │  │ Subagent │
  │ (Search) │  │(Analysis)│  │(Writing) │
  └──────────┘  └──────────┘  └──────────┘
```

### coordinator-ന്റെ ഉത്തരവാദിത്തങ്ങൾ

coordinator വെറും സന്ദേശങ്ങൾ കൈമാറുകയല്ല, യഥാർഥ orchestration ജോലി ചെയ്യുകയാണ്:

- വലിയ ഒരു ജോലിയെ ചെറുതും വ്യക്തമായി പരിധി നിർണയിച്ചതുമായ ഭാഗങ്ങളായി വിഭജിക്കുന്നു.
- ഓരോ ഭാഗവും അതിന് ഏറ്റവും അനുയോജ്യമായ subagent-ന് നൽകുന്നു.
- പരാജയങ്ങൾ കൈകാര്യം ചെയ്യുന്നു — ഒരു subagent പിഴവ് കാണിക്കുകയോ ഉപയോഗശൂന്യമായത് നൽകുകയോ ചെയ്താൽ, വീണ്ടും ശ്രമിക്കണോ, മറ്റൊരാൾക്ക് നൽകണോ, അതോ ഭംഗിയായി കുറഞ്ഞ ഫലത്തിൽ ഒതുങ്ങണോ എന്ന് coordinator തീരുമാനിക്കുന്നു.
- വ്യക്തിഗത ഫലങ്ങളെ ഒരൊറ്റ യോജിച്ച അന്തിമ ഉത്തരമാക്കി ചേർക്കുന്നു (ഇത് നിസ്സാരമല്ല: ഫലങ്ങൾ പരസ്പരം വിരുദ്ധമാകാം, ആവർത്തിക്കാം, അല്ലെങ്കിൽ വ്യത്യസ്ത രൂപങ്ങളിൽ വരാം).
- ഓരോ subagent-ലേക്കും എന്ത് വിവരം പോകുന്നു, തിരികെ എന്ത് വരുന്നു എന്നത് കൃത്യമായി നിയന്ത്രിക്കുന്നു.
- യഥാർഥ ചോദ്യം അനുസരിച്ച്, ഏതൊക്കെ subagent-കൾ വേണം എന്ന് തീരുമാനിക്കുന്നു — എല്ലാ അഭ്യർഥനയ്ക്കും എല്ലാ വിദഗ്ധരും വേണമെന്നില്ല.

### ആളുകൾ തെറ്റുന്ന നിയമം: subagent-കൾക്ക് ഓർമയില്ല

multi-agent സിസ്റ്റങ്ങളെക്കുറിച്ച് ഉൾക്കൊള്ളേണ്ട ഏറ്റവും പ്രധാന വസ്തുത ഇതാണ്, അത് ഊന്നിപ്പറയുന്നതിന് കാരണവുമുണ്ട്: **ഒരു subagent തുടങ്ങുന്നത് പൂർണമായും ശൂന്യമായ context-ഓടെയാണ്.** coordinator കണ്ടതോ വായിച്ചതോ തീരുമാനിച്ചതോ ആയ ഒന്നും അത് സ്വയമേവ അവകാശമാക്കുന്നില്ല — ഉപയോക്താവിന്റെ യഥാർഥ ചോദ്യമോ, മുൻ subagent-കളുടെ കണ്ടെത്തലുകളോ, ഇതിനകം തുറന്ന ഫയലുകളോ ഒന്നും. ആ subagent-ന്റെ task prompt-ൽ coordinator വ്യക്തമായി എഴുതിയത് *മാത്രമാണ്* അതിന് അറിയാവുന്ന വിവരം.

അതായത്, സ്ഥാപനത്തെക്കുറിച്ച് ഒന്നും അറിയാത്ത ഒരു പുതിയ കരാറുകാരനെ മാനേജർ ബ്രീഫ് ചെയ്യുന്നതുപോലെ, subagent-നെ "ബ്രീഫ് ചെയ്യുന്ന" മുഴുവൻ ജോലിയും coordinator-ന്റെ prompt എഴുത്താണ് ചെയ്യുന്നത്. ഒരു നിബന്ധനയോ, മുൻ കണ്ടെത്തലോ, context-ന്റെ ഒരു ഭാഗമോ പറയാൻ coordinator മറന്നാൽ, subagent അത് ഒരിക്കലും അറിയില്ല — മറ്റൊരു വഴിയുമില്ല.

> **⚠️ ശ്രദ്ധിക്കുക:** coordinator വ്യക്തമായി പറയാത്ത ഒന്ന് ഒരു subagent-ന് "വെറുതെ അറിയാമായിരുന്നു" എന്ന മട്ടിൽ പെരുമാറുന്നതായി ഒരു പരീക്ഷാ ചോദ്യം വിവരിച്ചാൽ, സാധാരണ മാതൃകയിൽ ആ സാഹചര്യം അസാധ്യമാണ്. subagent-ന് context ഇല്ലെന്ന് തോന്നുന്ന ഒരു പിഴവിന്റെ ശരിയായ നിർണയം മിക്കവാറും എപ്പോഴും "coordinator ആ വിവരം task prompt-ൽ ഉൾപ്പെടുത്തിയില്ല" എന്നതാണ് — "subagent മറന്നു" എന്നോ "subagent-ന് പ്രവേശനമില്ല" എന്നോ അല്ല.

### മൂന്ന് അടിസ്ഥാന multi-agent മാതൃകകൾ

| മാതൃക | എങ്ങനെ പ്രവർത്തിക്കുന്നു | എപ്പോൾ ഉപയോഗിക്കണം |
|---|---|---|
| **Hub-and-Spoke** | ഒരു coordinator, പരസ്പരം സ്വതന്ത്രമായ പല വിദഗ്ധ subagent-കളെ നിയന്ത്രിക്കുന്നു | വ്യത്യസ്ത തരം വൈദഗ്ധ്യം യഥാർഥത്തിൽ വേണ്ട സങ്കീർണ ജോലികൾ (ഉദാ: ഒരാൾ ഗവേഷണം, ഒരാൾ വിശകലനം, ഒരാൾ എഴുത്ത്) |
| **Pipeline** | ഒരു agent-ന്റെ ഫലം അടുത്തതിന്റെ ഇൻപുട്ടാകുന്നു, നിശ്ചിത ക്രമത്തിൽ | ഓരോ ഘട്ടവും മുൻ ഘട്ടത്തിന്റെ ഫലത്തിന് മേൽ കർശനമായി കെട്ടിപ്പടുക്കുന്ന ക്രമാനുഗത ജോലികൾ |
| **Peer-to-Peer** | കേന്ദ്ര coordinator വഴിയല്ലാതെ agent-കൾ നേരിട്ട് സഹകരിക്കുന്നു | ഏകദേശം തുല്യരായ agent-കൾ തമ്മിലുള്ള സഹകരണപരമായ പരിഷ്കരണം (ഉദാ: ഒരു എഴുത്തുകാരൻ agent-ഉം ഒരു വിമർശകൻ agent-ഉം ചേർന്ന് ആവർത്തിക്കുന്നത്) |

പ്രൊഡക്ഷൻ സിസ്റ്റങ്ങളിൽ ഏറ്റവും സാധാരണം hub-and-spoke ആണ്, കാരണം അത് നിയന്ത്രണം കേന്ദ്രീകൃതവും പ്രവചനീയവുമായി നിലനിർത്തുന്നു — ഫലത്തിന്റെ മൊത്തത്തിലുള്ള ഗുണനിലവാരത്തിനും പൂർണതയ്ക്കും coordinator-നെ ഉത്തരവാദിയാക്കാം. task decomposition-ലേക്ക് എത്തുമ്പോഴും ഒന്നും വിട്ടുപോകുന്നില്ല എന്ന് ഉറപ്പാക്കുമ്പോഴും ഇത് വളരെ പ്രധാനമാണ്.

> **🌍 യഥാർഥ ഉദാഹരണം:** ഒരു കമ്പനി ഒരു "മത്സര ഗവേഷണ" agent നിർമിക്കുന്നു. മൂന്ന് എതിരാളികളുടെ വിലനിർണയ പേജുകൾ താരതമ്യം ചെയ്യാൻ ഒരു ഉപയോക്താവ് ആവശ്യപ്പെടുന്നു. coordinator ഒരു hub-and-spoke മാതൃകയിൽ മൂന്ന് subagent-കളെ ഉണ്ടാക്കുന്നു, ഓരോ എതിരാളിക്കും ഒന്ന് വീതം, ഓരോന്നിനോടും "ഈ URL-ലെ വിലനിർണയ പേജ് എടുത്ത് സംഗ്രഹിക്കുക, tier-കളും വിലകളും കുറിക്കുക" എന്ന് മാത്രം പറയുന്നു. മൂന്ന് subagent-കളിൽ ഒന്നിനും മറ്റ് രണ്ടെണ്ണം ഉണ്ടെന്ന് അറിയില്ല — അറിയാൻ കഴിയില്ല, കാരണം ഓരോന്നിനും അതിന്റേതായ ഇടുങ്ങിയ task prompt മാത്രമാണ് ലഭിച്ചത്. പിന്നീട് coordinator മൂന്ന് സംഗ്രഹങ്ങളും വായിച്ച് അന്തിമ താരതമ്യം എഴുതുന്നു. കറൻസി കുറിക്കാൻ ഓരോ subagent-നോടും പറയാൻ coordinator മറന്നിരുന്നെങ്കിൽ, ഒരു സംഗ്രഹത്തിലും അത് ഉണ്ടാകുമായിരുന്നില്ല — "സ്വയം മനസ്സിലാക്കിയില്ല" എന്ന് പറഞ്ഞ് coordinator-ന് subagent-കളെ കുറ്റപ്പെടുത്താനാകില്ല.
