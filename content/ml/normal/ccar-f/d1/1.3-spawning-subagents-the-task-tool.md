## Subagent-കൾ സൃഷ്ടിക്കൽ — Task ടൂൾ

Multi-agent സിസ്റ്റങ്ങൾ (മുൻ വിഷയം) coordinator-ന്റെയും subagent-ന്റെയും *ആശയപരമായ* പങ്കുകൾ വിവരിക്കുന്നു. ഒരു coordinator യഥാർഥത്തിൽ ഒരു subagent-നെ എങ്ങനെ സൃഷ്ടിക്കുന്നു എന്ന മൂർത്തമായ സംവിധാനമാണ് ഈ വിഷയം കൈകാര്യം ചെയ്യുന്നത്: **Task ടൂൾ**.

### സംവിധാനം

coordinator-ന്റെ വീക്ഷണത്തിൽ, ഒരു subagent സൃഷ്ടിക്കുന്നത് മറ്റൊരു ടൂൾ വിളി മാത്രമാണ് — agentic loop-ൽ മറ്റേതൊരു ടൂൾ വിളിക്കുന്നതിനും ഘടനാപരമായി സമാനം. subagent എന്ത് ചെയ്യണം എന്ന് വ്യക്തമാക്കുന്ന ഒരു ഇൻപുട്ടോടെ coordinator Task ടൂളിനായി ഒരു tool-use അഭ്യർഥന നൽകുന്നു. നിങ്ങളുടെ orchestration കോഡ് ഈ അഭ്യർഥന കണ്ട്, ഒരു പുതിയ Claude instance ആരംഭിക്കുന്നു (മുൻ വിഷയം അനുസരിച്ച്, സ്വന്തം ശൂന്യമായ context-ഓടെ), *ആ* instance-ന്റെ agentic loop പൂർത്തിയാകുംവരെ പ്രവർത്തിപ്പിക്കുന്നു, എന്നിട്ട് അതിന്റെ അന്തിമ ഫലം Task വിളിയുടെ "tool result" ആയി coordinator-ന് തിരികെ നൽകുന്നു.

മറ്റേതൊരു ടൂളിനെയും പോലെ ഇതിനും അനുമതി വേണ്ടതിനാൽ, ഒരു കർശന മുൻവ്യവസ്ഥയുണ്ട്: **coordinator-ന്റെ `allowedTools` പട്ടികയിൽ "Task" ഉണ്ടായിരിക്കണം.** ഇല്ലെങ്കിൽ, coordinator-ന് subagent-കൾ സൃഷ്ടിക്കാൻ ഒരു വഴിയുമില്ല — സിസ്റ്റത്തിന്റെ ബാക്കി ഭാഗം എങ്ങനെ രൂപകൽപ്പന ചെയ്താലും അത് ഒരൊറ്റ, ഏൽപ്പിക്കാത്ത agent പോലെ പെരുമാറും. ഇതൊരു സാധാരണ ക്രമീകരണ പിഴവും സ്വാഭാവികമായ ഒരു പരീക്ഷാ കെണിയുമാണ്: subagent-കൾ ഉപയോഗിക്കേണ്ടിയിരുന്ന ഒരു സിസ്റ്റം ഒരിക്കലും അത് ചെയ്യുന്നില്ലെങ്കിൽ, പലപ്പോഴും coordinator-ന്റെ ടൂൾ പട്ടികയിൽ "Task" ഇല്ലാത്തതാണ് കാരണം.

### subagent-കൾ സമാന്തരമായി പ്രവർത്തിപ്പിക്കൽ

രണ്ടോ അതിലധികമോ ഉപജോലികൾ യഥാർഥത്തിൽ സ്വതന്ത്രമാണെങ്കിൽ — ഒന്നിന് മുന്നോട്ടുപോകാൻ മറ്റൊന്നിന്റെ ഫലം വേണ്ടെങ്കിൽ — അവ ഒന്നിനുപുറകെ ഒന്നായി പ്രവർത്തിപ്പിക്കേണ്ടതില്ല. coordinator-ന് **ഒരൊറ്റ മറുപടിക്കുള്ളിൽ പല Task ടൂൾ വിളികൾ** നൽകാം, നിങ്ങളുടെ orchestration കോഡിന് ആ subagent-കളെയെല്ലാം ഒരേസമയം പ്രവർത്തിപ്പിക്കാം. ഇത് ഗണ്യമായ കാര്യക്ഷമത നേട്ടമാണ്: മൂന്ന് ക്രമാനുഗത യാത്രകൾക്ക് പകരം, മൂന്ന് ജോലികൾക്ക് ഒരു യാത്രയുടെ സമയം മാത്രം (ഏറ്റവും വൈകുന്ന subagent അനുസരിച്ച്).

ഓർക്കേണ്ട പ്രധാന വ്യത്യാസം: സമാന്തരത വരുന്നത് *ഒരു* turn-ലെ പല Task വിളികളിൽ നിന്നാണ്, വെവ്വേറെ turn-കളിൽ Task വിളികൾ പരത്തുന്നതിൽ നിന്നല്ല. coordinator ഒരു subagent-നെ ആവശ്യപ്പെട്ട്, അതിന്റെ ഫലത്തിനായി കാത്തിരുന്ന്, പിന്നെ മാത്രം അടുത്തത് ആവശ്യപ്പെടുന്നെങ്കിൽ അത് ക്രമാനുഗതമാണ് — ആ രണ്ട് ഉപജോലികളും പരസ്പരം ആശ്രയിച്ചിരുന്നില്ലെങ്കിൽ പോലും.

| സമീപനം | ഘടന | ഫലം |
|---|---|---|
| **സമാന്തരം** | ഒരൊറ്റ coordinator മറുപടിയിൽ പല Task ടൂൾ വിളികൾ | subagent-കൾ ഒരേസമയം പ്രവർത്തിക്കുന്നു; ആകെ സമയം ≈ ഏറ്റവും വൈകുന്നത് |
| **ക്രമാനുഗതം** | ഓരോ coordinator turn-ലും ഒരു Task വിളി, അടുത്തത് ആവശ്യപ്പെടും മുൻപ് ഓരോ ഫലത്തിനും കാത്തിരിക്കുന്നു | subagent-കൾ ഒന്നിനുപുറകെ ഒന്നായി പ്രവർത്തിക്കുന്നു; ആകെ സമയം = എല്ലാത്തിന്റെയും തുക |

### നല്ല ഒരു subagent prompt എഴുതുന്നത്

ഒരു subagent-ന് സ്വന്തമായി ഓർമയില്ലാത്തതിനാൽ (മുൻ വിഷയം കാണുക), അതിന്റെ ഫലത്തിന്റെ ഗുണനിലവാരം മിക്കവാറും പൂർണമായും coordinator എഴുതുന്ന prompt-ന്റെ ഗുണനിലവാരമാണ് നിർണയിക്കുന്നത്. മൂന്ന് കാര്യങ്ങൾ എപ്പോഴും ഉൾപ്പെടുത്തണം:

- **subagent-ന് വേണ്ടിവരുന്ന മുൻ agent-കളുടെ പൂർണ കണ്ടെത്തലുകൾ.** subagent A കണ്ടെത്തിയതിന് മേൽ subagent B കെട്ടിപ്പടുക്കണമെങ്കിൽ, A-യുടെ യഥാർഥ കണ്ടെത്തലുകൾ coordinator B-യുടെ prompt-ൽ ഒട്ടിക്കണം — B-ക്ക് A-യോട് നേരിട്ട് ചോദിക്കാനോ A-യുടെ സംഭാഷണം കാണാനോ കഴിയില്ല.
- **ഉറവിട വിവരം** — URL-കൾ, രേഖകളുടെ പേരുകൾ, പേജ് നമ്പറുകൾ, ഫയൽ പാതകൾ — അങ്ങനെ ഒരു വസ്തുത എവിടെനിന്ന് വന്നു എന്നത് ശൃംഖലയിലുടനീളം നിലനിൽക്കും, അന്തിമ ഉത്തരത്തിൽ എത്തുമ്പോഴേക്കും ഉറവിടമില്ലാത്ത ഒരു അവകാശവാദമായി ചുരുങ്ങിപ്പോകില്ല.
- **ഗവേഷണ ലക്ഷ്യങ്ങളും ഗുണനിലവാര മാനദണ്ഡങ്ങളും, കർശനമായ ഘട്ടം ഘട്ടമായുള്ള തിരക്കഥയല്ല.** നല്ല ഫലം *എന്താണെന്നും* അത് *എന്തുകൊണ്ട്* പ്രധാനമാണെന്നും subagent-നോട് പറയണം, എന്നിട്ട് അവിടെ *എങ്ങനെ* എത്തണമെന്ന് കണ്ടെത്താൻ വിശ്വസിക്കണം. കൃത്യമായ ഘട്ടങ്ങൾ അമിതമായി നിർദേശിക്കുന്നത്, ജോലിക്കിടയിൽ അപ്രതീക്ഷിതമായ എന്തെങ്കിലും കണ്ടെത്തുമ്പോൾ പൊരുത്തപ്പെടാനുള്ള subagent-ന്റെ കഴിവ് ഇല്ലാതാക്കുന്നു.

> **💡 നുറുങ്ങ്:** ഒരു subagent prompt എഴുതുമ്പോൾ ഉപയോഗപ്രദമായ ഒരു പരിശോധന: "ഈ സംഭാഷണത്തിന്റെ ഒരു ഭാഗവും ഈ subagent മുൻപ് കണ്ടിട്ടില്ലായിരുന്നെങ്കിൽ, നന്നായി ജോലി ചെയ്യാൻ ഈ prompt മാത്രം മതിയാകുമോ?" ഉത്തരം ഇല്ല എന്നാണെങ്കിൽ, prompt-ൽ എന്തോ വിട്ടുപോയിരിക്കുന്നു — subagent-ന്റെ ധാരണയിലല്ല.

> **🌍 യഥാർഥ ഉദാഹരണം:** "മൂന്ന് ചരക്കുനീക്ക രീതികളുടെ പാരിസ്ഥിതിക ആഘാതം" എന്ന വിഷയത്തിൽ ഒരു റിപ്പോർട്ട് എഴുതാൻ ഒരു ഗവേഷണ സഹായി agent-നോട് ആവശ്യപ്പെടുന്നു. coordinator-ന്റെ `allowedTools`-ൽ `Task` ഉള്ളതിനാൽ, ഓരോന്നായി ഗവേഷണം ചെയ്യുന്നതിന് പകരം ഒരൊറ്റ മറുപടിയിൽ മൂന്ന് Task വിളികൾ നൽകുന്നു — ഓരോ ചരക്കുനീക്ക രീതിക്കും ഒരു subagent. ഓരോ subagent-ന്റെയും prompt-ൽ ഗവേഷണം ചെയ്യേണ്ട നിർദിഷ്ട രീതി, ലക്ഷ്യം ("ടൺ-മൈലിന് CO2 കണക്കാക്കുക, ഉറവിടങ്ങൾ ഉദ്ധരിക്കുക"), ഗുണനിലവാര പരിധി ("കുറഞ്ഞത് രണ്ട് സ്വതന്ത്ര ഉറവിടങ്ങൾ ഉദ്ധരിക്കുക") എന്നിവ ഉൾപ്പെടുന്നു, പക്ഷേ കൃത്യമായ തിരയൽ ചോദ്യങ്ങൾ മനഃപൂർവം നിർദേശിക്കുന്നില്ല — കണ്ടെത്തുന്നതിനനുസരിച്ച് സമീപനം മാറ്റാൻ ഓരോ subagent-നെയും അനുവദിക്കുന്നു. മൂന്നും ഒരേസമയം പ്രവർത്തിക്കുന്നു, ആകെ ഗവേഷണ സമയം മൂന്നിന്റെയും തുകയ്ക്ക് പകരം ഏറ്റവും വൈകുന്ന ഒരൊറ്റ തിരയലിന്റെ ദൈർഘ്യത്തിലേക്ക് ചുരുങ്ങുന്നു.
