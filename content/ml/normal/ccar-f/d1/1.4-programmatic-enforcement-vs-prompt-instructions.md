## പ്രോഗ്രാം വഴിയുള്ള നിർബന്ധം vs. Prompt നിർദേശങ്ങൾ

യഥാർഥ പ്രവൃത്തികൾ ചെയ്യുന്ന agent-കൾ നിർമിക്കാൻ തുടങ്ങുമ്പോൾ — പണം തിരികെ നൽകുക, ഇമെയിൽ അയക്കുക, രേഖകൾ മാറ്റുക — പരീക്ഷയിൽ നിരന്തരം വരുന്ന ഒരു രൂപകൽപ്പനാ ചോദ്യം നേരിടേണ്ടിവരും: *ഈ നിയമം prompt-ൽ വേണോ, അതോ കോഡിൽ വേണോ?* ഉത്തരം പൂർണമായും നിങ്ങൾക്ക് എത്രത്തോളം പരാജയം സഹിക്കാനാകും എന്നതിനെ ആശ്രയിച്ചിരിക്കുന്നു.

### Agent പെരുമാറ്റം നിയന്ത്രിക്കാനുള്ള രണ്ട് വഴികൾ

നിങ്ങൾക്ക് ലഭ്യമായ ഉപാധികൾ രണ്ടെണ്ണം മാത്രം:

1. **Prompt നിർദേശങ്ങൾ** — Claude-ന്റെ system prompt-ന്റെയോ ജോലി നിർദേശങ്ങളുടെയോ ഭാഗമായി സ്വാഭാവിക ഭാഷയിൽ നിയമം എഴുതുന്നു ("മാനേജരുടെ അനുമതിയില്ലാതെ $500-ന് മുകളിൽ ഒരിക്കലും റീഫണ്ട് നൽകരുത്").
2. **പ്രോഗ്രാം വഴിയുള്ള നിർബന്ധം** — prompt എന്ത് പറഞ്ഞാലും, agent ചെയ്യാൻ ശ്രമിക്കുന്നത് പരിശോധിക്കുകയും ആവശ്യമെങ്കിൽ തടയുകയോ മാറ്റുകയോ ചെയ്യുന്ന യഥാർഥ കോഡ് നിങ്ങൾ എഴുതുന്നു.

ഇവ തുല്യമല്ല, വ്യത്യാസം അളവിന്റേതുമല്ല — ഉറപ്പിന്റെ *തരത്തിലുള്ള* വ്യത്യാസമാണ്.

### രണ്ട് സമീപനങ്ങളുടെ താരതമ്യം

| | Prompt നിർദേശം (അപകടകരം) | പ്രോഗ്രാം Hook (സുരക്ഷിതം) |
|---|---|---|
| **സംവിധാനം** | എന്ത് ചെയ്യണമെന്ന് Claude-നോട് പറയുന്ന prompt-ലെ വാക്കുകൾ | ടൂൾ വിളിയെത്തന്നെ തടസ്സപ്പെടുത്തുന്ന കോഡ് |
| **വിശ്വാസ്യത** | മിക്കപ്പോഴും പ്രവർത്തിക്കുന്നു | 100% സമയവും പ്രവർത്തിക്കുന്നു |
| **മറികടക്കാനാകുമോ?** | ഉവ്വ് — അവഗണിക്കാം, തെറ്റായി വായിക്കാം, ന്യായവാദത്തിലൂടെ ഒഴിവാക്കാം | ഇല്ല — മാതൃകയുടെ ഔട്ട്പുട്ടിന് ഇത് മറികടക്കാനാകില്ല |
| **പരാജയ നിരക്ക്** | പൂജ്യമല്ല, ചെറുതാണെങ്കിലും | പൂജ്യം (അത് നിർബന്ധിക്കുന്ന നിർദിഷ്ട പരിശോധനയ്ക്ക്) |
| **ഏറ്റവും അനുയോജ്യം** | ശൈലി, സ്വരം, വാക്യരൂപ മുൻഗണനകൾ, നിർണായകമല്ലാത്ത മൃദു നിയമങ്ങൾ | പണം, അനുസരണം, സുരക്ഷാ-നിർണായകം, നിയമപരമോ സാമ്പത്തികമോ ആയ പ്രത്യാഘാതമുള്ള എന്തും |

### ചില നിയമങ്ങൾക്ക് "പൂജ്യമല്ലാത്ത പരാജയ സാധ്യത" എന്തുകൊണ്ട് അയോഗ്യതയാകുന്നു

ഒരു prompt നിർദേശം അടിസ്ഥാനപരമായി ഒരു probabilistic സിസ്റ്റത്തോടുള്ള അഭ്യർഥനയാണ്. അതിവിദഗ്ധമായി പരിശീലിപ്പിച്ച ഒരു മാതൃക അതിവ്യക്തമായ ഒരു നിർദേശം പിന്തുടർന്നാൽ പോലും, ഒരു ഉപയോക്താവോ ശത്രുതാപരമായ ഒരു prompt injection-ഓ കൊണ്ടുവന്നേക്കാവുന്ന എല്ലാ അതിർസാഹചര്യങ്ങളുടെയും എല്ലാ വാക്യരൂപങ്ങളിലും അക്ഷരാർഥത്തിൽ 100% അനുസരണം നൽകില്ല. മിക്ക ജോലികൾക്കും ചെറിയ പരാജയ നിരക്ക് സ്വീകാര്യമായ ഒരു ചെലവാണ് — ഒരു സംഗ്രഹത്തിലെ അൽപ്പം പിഴച്ച സ്വരം വലിയ കാര്യമല്ല.

പക്ഷേ ചില വിഭാഗം നിയമങ്ങൾക്ക്, *ഏതൊരു* പൂജ്യമല്ലാത്ത പരാജയ നിരക്കും നിർവചനപ്രകാരം തന്നെ അസ്വീകാര്യമാണ്: "ഇടയ്ക്കിടെ അനുമതിയില്ലാത്ത റീഫണ്ടുകൾ നൽകുന്നു" എന്നത് ഒരു വ്യാപാരത്തിന് സഹിക്കാനാകില്ല, "ഇടയ്ക്കിടെ നിർബന്ധിത ഐഡന്റിറ്റി പരിശോധന ഒഴിവാക്കുന്നു" എന്നത് ഒരു ആരോഗ്യ സംവിധാനത്തിന് സഹിക്കാനാകില്ല, "ഇടയ്ക്കിടെ അംഗീകൃത പരിധിക്ക് പുറത്ത് ഒരു ഇടപാട് നടത്തുന്നു" എന്നത് ഒരു സാമ്പത്തിക സംവിധാനത്തിന് സഹിക്കാനാകില്ല. ഈ സാഹചര്യങ്ങളിൽ, prompt എത്ര നന്നായി എഴുതിയാലും prompt നിർദേശങ്ങൾ തെറ്റായ ഉപകരണമാണ്, കാരണം ആവശ്യകത തന്നെ "എപ്പോഴും" എന്നതാണ്, "എപ്പോഴും" നൽകാൻ കോഡിന് മാത്രമേ കഴിയൂ.

> **📝 പരീക്ഷാ ശ്രദ്ധ:** "ഒരിക്കലും പാടില്ല," "എപ്പോഴും നിർബന്ധം," "ഒഴിവുകളില്ല," "അനുസരണം" എന്നീ വാക്കുകൾ ഉപയോഗിച്ച് ഒരു നിയമം വിവരിക്കുന്ന ചോദ്യം കണ്ടാൽ, ഉദ്ദേശിക്കുന്ന ഉത്തരം ഒരു പ്രോഗ്രാം സംവിധാനമാണ് (ഒരു hook) എന്നതിന്റെ നേരിട്ടുള്ള സൂചനയായി അതിനെ കണക്കാക്കുക — പരിഷ്കരിച്ചതോ "മിടുക്കുള്ളതോ" ആയ ഒരു prompt അല്ല. ഒരു നിർദേശത്തിന്റെ വാക്യരൂപം മെച്ചപ്പെടുത്തുന്നത് ഒരു probabilistic ഉറപ്പിനെ ഒരിക്കലും സമ്പൂർണ ഉറപ്പാക്കി മാറ്റുന്നില്ല.

> **🌍 യഥാർഥ ഉദാഹരണം:** ഒരു ഉപഭോക്തൃ സപ്പോർട്ട് agent-ന്റെ prompt-ൽ ഇങ്ങനെ നിർദേശിക്കുന്നു: "ഒരു മനുഷ്യനിലേക്ക് ഉയർത്താതെ $500-ൽ കൂടുതൽ റീഫണ്ട് ഒരിക്കലും നൽകരുത്." ഇത് മഹാഭൂരിപക്ഷം സമയത്തും ശരിയായി പ്രവർത്തിക്കുന്നു. പക്ഷേ ദശലക്ഷക്കണക്കിന് സംഭാഷണങ്ങളിൽ, സമർഥമായി എഴുതിയ ഒരു ഉപഭോക്തൃ സന്ദേശമോ, അസാധാരണമായ ഒരു അതിർസാഹചര്യമോ, നയത്തിന്റെ സൂക്ഷ്മമായ ഒരു തെറ്റിദ്ധാരണയോ കാരണം agent സ്വന്തം അധികാരത്തിൽ $750 റീഫണ്ട് അംഗീകരിക്കുന്നത് ചുരുക്കം ചില തവണ സംഭവിക്കുന്നു. നിസ്സാര പ്രശ്നങ്ങൾ കൈകാര്യം ചെയ്യുന്ന ഒരു സപ്പോർട്ട് ടീമിന് ഇത് സഹിക്കാവുന്നതാകാം. ഒരു ബാങ്കിന്, അനുമതിയില്ലാത്ത ഒരൊറ്റ ആറക്ക വയർ ട്രാൻസ്ഫർ പോലും ഗുരുതരമായ സംഭവമാണ് — സാമ്പത്തികവും അനുസരണ-നിർണായകവുമായ പ്രവൃത്തികൾ prompt വാക്യരൂപത്തിന് വിടാതെ പ്രോഗ്രാം പരിശോധനകളിൽ (hooks) പൊതിയുന്നത് കൃത്യമായി ഇതുകൊണ്ടാണ്.

### ഇത് ആർക്കിടെക്ചറിൽ എന്തുകൊണ്ട് പ്രധാനമാകുന്നു

Claude അധിഷ്ഠിത agent സിസ്റ്റങ്ങളിൽ പ്രോഗ്രാം വഴിയുള്ള നിർബന്ധത്തിന്റെ മൂർത്തമായ സംവിധാനമായ അടുത്ത വിഷയത്തിന്റെ (Hooks) ആശയപരമായ അടിത്തറയാണ് ഈ വ്യത്യാസം. ഒരു നിയമം *എപ്പോൾ* prompt-ൽ നിന്ന് കോഡിലേക്ക് മാറ്റണം എന്ന് തിരിച്ചറിയുന്നത് പരീക്ഷ നേരിട്ട് പരിശോധിക്കുന്ന ഒരു രൂപകൽപ്പനാ വൈദഗ്ധ്യമാണ്: ഒഴിവുകളില്ലാത്ത, അനുസരണം ആവശ്യപ്പെടുന്ന, സമ്പൂർണമായ ഒരു ആവശ്യകത വിവരിക്കുന്ന ഏതൊരു സാഹചര്യവും സൂചിപ്പിക്കുന്നത്, ശരിയായ ആർക്കിടെക്ചർ ഉത്തരം കോഡ് തലത്തിലുള്ള നിർബന്ധമാണ് എന്നാണ് — കൂടുതൽ നന്നായി എഴുതിയ ഒരു നിർദേശമല്ല.
