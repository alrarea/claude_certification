## Agentic Loop — എല്ലാത്തിന്റെയും കാതൽ

Claude-ന് മുകളിൽ നിർമിച്ച ഏത് "agent"-ഉം, പുറമേ എത്ര സങ്കീർണമായി തോന്നിയാലും, ഉള്ളിൽ ഒരേ ലളിതമായ ചക്രം തന്നെയാണ് പ്രവർത്തിപ്പിക്കുന്നത്. Domain 1-ലെ ബാക്കിയെല്ലാം മനസ്സിലാക്കാനുള്ള ഏറ്റവും പ്രധാന മുൻവ്യവസ്ഥ ഈ ചക്രം മനസ്സിലാക്കുക എന്നതാണ് — കാരണം പിന്നീട് പഠിക്കുന്ന ഓരോ മാതൃകയും (subagent-കൾ, hooks, task decomposition, session forking) ഈ ഒരൊറ്റ loop-ന് മുകളിൽ ചേർത്ത വ്യതിയാനങ്ങൾ മാത്രമാണ്.

### എന്തിനാണ് ഒരു "loop"?

സാധാരണ ഒരു chatbot ഒരു സന്ദേശം സ്വീകരിച്ച് ഒരു മറുപടി നൽകുന്നു. സംഭാഷണത്തിന് അത് മതി, പക്ഷേ അതിന് ലോകത്ത് *പ്രവർത്തിക്കാൻ* കഴിയില്ല — ഒന്നും തിരയാനോ, കണക്കുകൂട്ടാനോ, ഡാറ്റാബേസ് പരിശോധിക്കാനോ, ഒരു ഫയൽ തിരുത്തി ആ തിരുത്ത് ഫലിച്ചോ എന്ന് നോക്കാനോ കഴിയില്ല. ജോലിക്കിടയിൽ നിർത്തി, സ്വന്തം ടെക്സ്റ്റ് നിർമാണത്തിന് പുറത്ത് എന്തെങ്കിലും ചെയ്ത്, എന്ത് സംഭവിച്ചു എന്ന് കണ്ട്, ആ പുതിയ വിവരവുമായി ചിന്ത തുടരാൻ ഒരു agent-ന് കഴിയണം. അത് സാധ്യമാക്കുന്ന സംവിധാനമാണ് agentic loop.

### ചക്രം ഘട്ടം ഘട്ടമായി

1. **നിങ്ങൾ ഒരു ജോലി അയക്കുന്നു.** ഇത് നിങ്ങളുടെ ആദ്യ പ്രോംപ്റ്റും, Claude-ന് ഉപയോഗിക്കാൻ അനുവാദമുള്ള ടൂളുകളുടെ പട്ടികയും (അവയുടെ പേരുകൾ, വിവരണങ്ങൾ, ഇൻപുട്ട് schema-കൾ) ചേർന്നതാണ്.
2. **Claude ചിന്തിച്ച് അടുത്തത് എന്തെന്ന് തീരുമാനിക്കുന്നു.** ലക്ഷ്യം പരിഗണിച്ച്, നേരിട്ട് ഉത്തരം നൽകാമോ അതോ വിവരം ശേഖരിക്കാനോ ഒരു പ്രവൃത്തി ചെയ്യാനോ ആദ്യം ഒരു ടൂൾ വേണോ എന്ന് Claude തീരുമാനിക്കുന്നു.
3. **Claude ഒരു `stop_reason` ഉൾപ്പെടുന്ന മറുപടി നൽകുന്നു.** അടുത്തത് എന്ത് സംഭവിക്കണം എന്ന് തീരുമാനിക്കാൻ നിങ്ങളുടെ ആപ്ലിക്കേഷൻ കോഡ് വായിക്കുന്ന സൂചനയാണ് ഈ ഫീൽഡ്. ഇത് ഐച്ഛികമോ അലങ്കാരമോ ആയ മെറ്റാഡാറ്റയല്ല — നിങ്ങളുടെ orchestration കോഡ് ശാഖ തിരിയുന്ന നിയന്ത്രണ ചരമാണ്.
4. **നിങ്ങളുടെ കോഡ് `stop_reason` പരിശോധിച്ച് ശാഖ തിരിയുന്നു:**
   - അത് `tool_use` ആണെങ്കിൽ, ഒന്നോ അതിലധികമോ ടൂളുകൾ പ്രവർത്തിപ്പിക്കാൻ Claude ആവശ്യപ്പെട്ടിരിക്കുന്നു. നിങ്ങളുടെ ആപ്ലിക്കേഷൻ കോഡാണ് (Claude അല്ല) യഥാർഥത്തിൽ ടൂൾ പ്രവർത്തിപ്പിക്കുന്നത് — API വിളിക്കുന്നു, ഡാറ്റാബേസ് ചോദ്യം ചെയ്യുന്നു, ഷെൽ കമാൻഡ് നടത്തുന്നു — എന്നിട്ട് *ഫലം* തുടരുന്ന സംഭാഷണത്തിന്റെ ഭാഗമായി Claude-ന് തിരികെ അയക്കുന്നു.
   - അത് `end_turn` ആണെങ്കിൽ, ജോലി പൂർത്തിയായി എന്ന് Claude കരുതുന്നു, ഇനി ഒന്നും ചെയ്യാനില്ല. നിങ്ങളുടെ കോഡ് loop നിർത്തി അന്തിമ ഉത്തരം ഉപയോക്താവിന് നൽകുന്നു.

ഇതുകൊണ്ടാണ് ഇതിനെ ഒരു *loop* എന്ന് വിളിക്കുന്നത്: ഒരു `tool_use` മറുപടിക്ക് ശേഷം നിങ്ങൾ പുതിയ സംഭാഷണം തുടങ്ങുന്നില്ല — നിലവിലുള്ള സന്ദേശ ചരിത്രത്തോട് ടൂൾ ഫലം ചേർത്ത് മാതൃകയെ വീണ്ടും വിളിക്കുന്നു. Claude ഒടുവിൽ `end_turn` നൽകുന്നതുവരെ ഈ ചക്രം പലതവണ ആവർത്തിക്കാം (ഒരു വിവരം ശേഖരിക്കുക, പിന്നെ മറ്റൊന്ന്, പിന്നെ രണ്ടിനെക്കുറിച്ചും ചിന്തിക്കുക, പിന്നെ പ്രവർത്തിക്കുക).

### നാല് stop_reason മൂല്യങ്ങളും

| മൂല്യം | ലളിതമായ അർഥം | നിങ്ങൾ ചെയ്യേണ്ടത് |
|---|---|---|
| `tool_use` | Claude-ന് ഒരു ടൂൾ ഉപയോഗിക്കണം | ടൂൾ പ്രവർത്തിപ്പിക്കുക, ഫലം തിരികെ അയക്കുക, വീണ്ടും loop ചെയ്യുക |
| `end_turn` | Claude ജോലി പൂർത്തിയാക്കി | loop നിർത്തുക, ഉത്തരം നൽകുക |
| `stop_sequence` | നിങ്ങൾ ക്രമീകരിച്ച ഒരു "stop word" വന്നു | നിങ്ങളുടെ സ്വന്തം ക്രമീകരണ പ്രകാരം നിർത്തുക |
| `max_tokens` | മറുപടി മുറിഞ്ഞു — സ്ഥലം തീർന്നു | ഇതൊരു പിഴവായി കണക്കാക്കുക: token പരിധി കൂട്ടുകയോ സംഗ്രഹം ചോദിക്കുകയോ ചെയ്യുക, മുറിഞ്ഞ ഉത്തരം നിശ്ശബ്ദമായി സ്വീകരിക്കരുത് |

### കെണി: സ്വന്തമായി നിർത്തൽ വ്യവസ്ഥകൾ ഉണ്ടാക്കുന്നത്

loop തത്ത്വത്തിൽ ദീർഘനേരം പ്രവർത്തിക്കാമെന്നതിനാൽ, "10 ആവർത്തനങ്ങൾക്ക് ശേഷം നിർത്തുക" അല്ലെങ്കിൽ "ടെക്സ്റ്റിൽ 'done' എന്ന വാക്ക് വന്നാൽ നിർത്തുക" പോലുള്ള "സുരക്ഷാ" വ്യവസ്ഥകൾ ചേർക്കാൻ തോന്നും. ഇവ ന്യായമെന്ന് തോന്നുമെങ്കിലും യഥാർഥത്തിൽ പ്രൊഡക്ഷനിൽ പരാജയപ്പെടുന്ന anti-pattern-കളാണ്, മാത്രമല്ല ഒരു ക്ലാസിക് പരീക്ഷാ കെണിയുമാണ്:

- **നിശ്ചിത എണ്ണം ആവർത്തനങ്ങൾക്ക് ശേഷം നിർത്തുന്നത്** നിങ്ങൾ ഊഹിച്ചതിലും കൂടുതൽ (അല്ലെങ്കിൽ കുറവ്) ഘട്ടങ്ങൾ ഒരു ജോലിക്ക് ന്യായമായും വേണ്ടിവരുന്ന നിമിഷം തകരുന്നു. ലളിതമായ ഒരു തിരയൽ ഒറ്റ turn-ൽ തീർന്നേക്കാം; പല ഫയലുകളിലെ ഒരു refactor-ന് ഇരുപത് വേണ്ടിവന്നേക്കാം.
- **"done" അല്ലെങ്കിൽ "finished" പോലുള്ള വാക്കുകൾക്കായി assistant-ന്റെ ടെക്സ്റ്റ് പാഴ്‌സ് ചെയ്യുന്നത്** ദുർബലമാണ്, കാരണം Claude-ന്റെ വാക്യരൂപം സ്ഥിരമായിരിക്കും എന്ന് ഉറപ്പില്ല, തെറ്റായ പോസിറ്റീവുകളും നെഗറ്റീവുകളും ഒഴിവാക്കാനാകില്ല.
- **assistant ടെക്സ്റ്റ് ഉണ്ടെന്നത് turn പൂർത്തിയായതിന്റെ സൂചനയായി കണക്കാക്കുന്നത്** വിശ്വസനീയമല്ല — വിശദീകരണ ടെക്സ്റ്റ് നൽകുന്നതോടൊപ്പം *തന്നെ* അതേ turn-ൽ Claude-ന് ഒരു ടൂൾ വിളിയും ആവശ്യപ്പെടാം.

> **⚠️ ശ്രദ്ധിക്കുക:** ആവർത്തനങ്ങൾ എണ്ണുക, കീവേഡുകൾക്കായി ടെക്സ്റ്റ് പരിശോധിക്കുക, അല്ലെങ്കിൽ loop അവസാനിപ്പിക്കാൻ `stop_reason` ഫീൽഡ് അല്ലാതെ മറ്റെന്തെങ്കിലും ഉപയോഗിക്കുക — ഇവ നിർദേശിക്കുന്ന ഏത് ഉത്തരവും തെറ്റാണ്. നിങ്ങൾ ഊഹിക്കേണ്ടിവരാതിരിക്കാൻ വേണ്ടിത്തന്നെയാണ് API വ്യക്തവും ഘടനാപരവുമായ ഒരു സൂചന നൽകുന്നത്.

> **🌍 യഥാർഥ ഉദാഹരണം:** "`payment_test.py`-ലെ പരാജയപ്പെടുന്ന ടെസ്റ്റ് ശരിയാക്കുക" എന്ന ജോലി ഏൽപ്പിച്ച ഒരു coding agent സങ്കൽപ്പിക്കുക. loop ഇങ്ങനെ പോയേക്കാം: Claude ഫയൽ വായിക്കാൻ ആവശ്യപ്പെടുന്നു (`tool_use`) → നിങ്ങളുടെ കോഡ് ഫയലിന്റെ ഉള്ളടക്കം നൽകുന്നു → Claude ടെസ്റ്റ് സ്യൂട്ട് പ്രവർത്തിപ്പിക്കാൻ ആവശ്യപ്പെടുന്നു (`tool_use`) → നിങ്ങളുടെ കോഡ് പരാജയ വിവരം നൽകുന്നു → Claude ഫയൽ തിരുത്താൻ ആവശ്യപ്പെടുന്നു (`tool_use`) → നിങ്ങളുടെ കോഡ് തിരുത്ത് നടപ്പാക്കി വിജയം അറിയിക്കുന്നു → Claude ടെസ്റ്റുകൾ വീണ്ടും പ്രവർത്തിപ്പിക്കാൻ ആവശ്യപ്പെടുന്നു (`tool_use`) → ടെസ്റ്റുകൾ വിജയിക്കുന്നു → Claude `end_turn` നൽകി പരിഹാരം സംഗ്രഹിക്കുന്നു. അഞ്ച് തവണ അങ്ങോട്ടുമിങ്ങോട്ടും, ആ എണ്ണം മുൻകൂട്ടി അറിയാൻ കഴിയുമായിരുന്നില്ല. "3 ടൂൾ വിളികൾക്ക് ശേഷം നിർത്തുക" എന്ന ഉറപ്പിച്ച പരിധി പരിഹാരം പരിശോധിക്കപ്പെടും മുൻപേ agent-നെ മുറിച്ചുകളയുമായിരുന്നു.

### ഏക ശരിയായ നിയമം

`stop_reason == "end_turn"` ആകുമ്പോൾ മാത്രം — അപ്പോൾ എപ്പോഴും — loop നിർത്തുക. മറ്റെല്ലാ വ്യവസ്ഥകളും ഒന്നുകിൽ നിങ്ങൾ സ്വയം ക്രമീകരിച്ച ഒരു പ്രത്യേക സാഹചര്യമാണ് (`stop_sequence`), അല്ലെങ്കിൽ നിങ്ങൾ കൈകാര്യം ചെയ്യേണ്ട ഒരു പിഴവാണ് (`max_tokens`) — API യഥാർഥത്തിൽ നൽകുന്ന ഫീൽഡ് വായിക്കുന്നതിന് ഒരിക്കലും പകരമല്ല.
