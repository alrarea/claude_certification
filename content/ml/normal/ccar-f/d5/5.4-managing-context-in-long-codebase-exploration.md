## ദീർഘമായ കോഡ്ബേസ് പര്യവേക്ഷണത്തിൽ Context കൈകാര്യം ചെയ്യൽ

ദീർഘകാലം നീളുന്ന coding session-കൾ — ഡസൻ കണക്കിന് ടൂൾ വിളികളിലൂടെ പരിചയമില്ലാത്ത ഒരു വലിയ കോഡ്ബേസ് പര്യവേക്ഷണം ചെയ്യുന്ന ഒരു agent ആലോചിക്കുക — ഒരു പ്രത്യേക പരാജയ രീതി വെളിപ്പെടുത്തുന്നു: **context ശോഷണം**. ഒരു session-ന്റെ തുടക്കത്തിൽ Claude യഥാർഥ ഫയലുകൾ വായിക്കുകയും ഇപ്പോൾ കണ്ട യഥാർഥ കോഡിനെക്കുറിച്ച് ചിന്തിക്കുകയും ചെയ്യുന്നു. Session വളരെ നീളുമ്പോൾ, പഴയ നിരീക്ഷണങ്ങൾ ഫലപ്രദമായ ശ്രദ്ധാ പരിധിക്ക് പുറത്താകുന്നു (അല്ലെങ്കിൽ പിന്നീട് വായിച്ചതെല്ലാം കൊണ്ട് പുറന്തള്ളപ്പെടുന്നു), Claude യഥാർഥത്തിൽ നിരീക്ഷിച്ചതിന് പകരം **"സാധാരണ മാതൃകകളെക്കുറിച്ചുള്ള" പൊതുവിജ്ഞാനം** ഉപയോഗിക്കാൻ തുടങ്ങുന്നു. ഔട്ട്പുട്ട് വിശ്വസനീയമെന്ന് തോന്നിക്കുന്നു പക്ഷേ ആ നിർദിഷ്ട കോഡ്ബേസിൽ അടിസ്ഥാനമുള്ളതല്ലാതാകുന്നു — സൂക്ഷ്മവും അപകടകരവുമായ ഒരു വ്യതിയാനം, കാരണം അത് ഒരു പിഴവാണെന്ന് സ്വയം പ്രഖ്യാപിക്കുന്നില്ല; നിശ്ശബ്ദമായി കൃത്യത കുറയുന്നു എന്ന് മാത്രം.

### ഇത് എന്തുകൊണ്ട് സംഭവിക്കുന്നു

ഓരോ ടൂൾ വിളിയും — ഒരു ഫയൽ വായിക്കുക, ഒരു തിരയൽ നടത്തുക, ഒരു കമാൻഡ് പ്രവർത്തിപ്പിക്കുക — അതിന്റെ മുഴുവൻ ഔട്ട്പുട്ടും സംഭാഷണ context-ലേക്ക് ചേർക്കുന്നു. ഒരു ദീർഘ പര്യവേക്ഷണത്തിൽ ഇത് വേഗത്തിൽ കുമിഞ്ഞുകൂടുന്നു: ഡസൻ കണക്കിന് ഫയൽ വായനകൾ, വാചാലമായ തിരയൽ ഫലങ്ങൾ, കമാൻഡ് ഔട്ട്പുട്ട്. Context window അനന്തമായി വളരുന്നില്ല, ഒരു വലിയ window-നുള്ളിൽ പോലും lost-in-the-middle പ്രഭാവം (ആ വിഷയം കാണുക) അർഥമാക്കുന്നത്, എന്തെങ്കിലും അക്ഷരാർഥത്തിൽ ഉപേക്ഷിക്കപ്പെടും മുൻപേ തന്നെ, പഴയ ഉള്ളടക്കത്തിന് മാതൃകയുടെ നിലവിലെ ന്യായവാദത്തിൽ ക്രമേണ സ്വാധീനം കുറയുന്നു എന്നാണ്. പ്രായോഗിക ലക്ഷണം: ഒരു authentication മൊഡ്യൂൾ പര്യവേക്ഷണം ചെയ്ത് ഇരുപത് ടൂൾ വിളികൾ കഴിഞ്ഞ്, പത്ത് വിളികൾക്ക് മുൻപ് വായിച്ച യഥാർഥ token-refresh ഫംഗ്ഷൻ ഉദ്ധരിക്കുന്നതിന് പകരം "OAuth ഒഴുക്കുകൾ സാധാരണയായി എങ്ങനെ പ്രവർത്തിക്കുന്നു" എന്ന് വിവരിക്കാൻ തുടങ്ങുന്ന ഒരു agent.

### ലഘൂകരണ തന്ത്രങ്ങൾ

| തന്ത്രം | ഇത് എങ്ങനെ സഹായിക്കുന്നു |
|---|---|
| **Scratchpad ഫയലുകൾ** | പ്രധാന കണ്ടെത്തലുകൾ സംഭാഷണ context-ന് പുറത്തുള്ള ഒരു സ്ഥിര ഫയലിൽ എഴുതുന്നു; ഭാവി ചോദ്യങ്ങൾക്ക് Claude-ന്റെ മങ്ങുന്ന ഓർമയെ ആശ്രയിക്കുന്നതിന് പകരം ആ ഫയൽ പരാമർശിക്കാം |
| **Subagent ഏൽപ്പിക്കൽ** | വാചാലമായ പര്യവേക്ഷണം (പല ഫയലുകൾ വായിക്കൽ, പല തിരയലുകൾ) ഒരു subagent-നുള്ളിൽ നടക്കുന്നു, അതിന്റെ മുഴുവൻ വിവരണവും പ്രധാന agent-ന്റെ context-ൽ ഒരിക്കലും കടക്കുന്നില്ല — പ്രധാന agent-ന് ഒരു ചുരുക്കിയ സംഗ്രഹം മാത്രം ലഭിക്കുന്നു, അതിന്റെ context ഉയർന്ന തല ഏകോപനത്തിൽ കേന്ദ്രീകരിച്ച് നിലനിർത്തുന്നു |
| **`/compact`** | നിലവിലെ session context സജീവമായി സംഗ്രഹിക്കുകയും ഞെരുക്കുകയും ചെയ്യുന്നു, പ്രധാന ധാരകൾ നിലനിർത്താൻ ശ്രമിക്കുന്നതിനൊപ്പം സ്ഥലം സ്വതന്ത്രമാക്കുന്നു — ഇതിനകം നീണ്ട ഒരു session കൈകാര്യം ചെയ്യാനുള്ള നേരിട്ടുള്ള ഉപകരണം |
| **ഘടനാപരമായ അവസ്ഥാ കയറ്റുമതി** | ഓരോ agent/subagent-ഉം അതിന്റെ നിലവിലെ അവസ്ഥ (എന്ത് കണ്ടെത്തി, എന്ത് ചെയ്യുന്നു) ഇടയ്ക്കിടെ ഒരു ഫയലിൽ എഴുതുന്നു; resume ചെയ്യുമ്പോൾ ഒരു coordinator-ന് ആ അവസ്ഥ വീണ്ടും ലോഡ് ചെയ്യാം, ഇത് crash വീണ്ടെടുക്കലായും പ്രവർത്തിക്കുന്നു — പ്രക്രിയ നിലച്ചാലും ജോലി നഷ്ടപ്പെടുന്നില്ല |

ഈ തന്ത്രങ്ങൾക്ക് ഒരു പൊതു ആശയമുണ്ട്: **സത്യം നിലനിൽക്കുന്ന ഏക സ്ഥലമായി തത്സമയ സംഭാഷണത്തെ ആശ്രയിക്കരുത്.** വളരുന്ന ഒരു context window-ൽ അവ നിഷ്ക്രിയമായി അതിജീവിക്കുമെന്ന് പ്രതീക്ഷിക്കുന്നതിന് പകരം, പ്രധാന കണ്ടെത്തലുകൾ ഈടുനിൽക്കുന്ന എവിടെയെങ്കിലും സൂക്ഷിച്ച് മനഃപൂർവം വീണ്ടും ചേർക്കുക.

### ഇവയ്ക്കിടയിൽ തിരഞ്ഞെടുക്കൽ

Scratchpad ഫയലുകൾ ഭാരം കുറഞ്ഞവയാണ്, നിർദിഷ്ട വസ്തുതകൾ ഓർക്കേണ്ട ഒരൊറ്റ ദീർഘകാല agent-ന് നല്ലതാണ് (ഉദാ: "auth token പുതുക്കുന്നത് `auth/client.ts`-ലെ `refreshToken()`-ലാണ്, interceptor-ലല്ല"). പര്യവേക്ഷണം തന്നെ ബൃഹത്താകാൻ പോകുമ്പോഴാണ് subagent ഏൽപ്പിക്കൽ ശരിയായ ഉപകരണം — ആ ശബ്ദം ഉണ്ടാക്കി പിന്നെ ഞെരുക്കുന്നതിനെക്കാൾ നല്ലത് അത് പ്രധാന ധാരയിൽ നിന്ന് പൂർണമായി മാറ്റിനിർത്തുന്നതാണ്. `/compact` പ്രതികരണാത്മക ഉപകരണമാണ്: ഒരു session ഇതിനകം നീണ്ടുപോയി, പുതുതായി തുടങ്ങാതെ വെട്ടിച്ചുരുക്കേണ്ടിവരുമ്പോൾ ഉപകാരപ്രദം. വിശ്വാസ്യതയ്ക്കായി രൂപകൽപ്പന ചെയ്ത സിസ്റ്റങ്ങളിലാണ് ഘടനാപരമായ അവസ്ഥാ കയറ്റുമതി ഏറ്റവും പ്രധാനം, അവിടെ ഒരു crash-ഓ പുനരാരംഭമോ പര്യവേക്ഷണം ആദ്യം മുതൽ ചെയ്യേണ്ടിവരുന്നതിന് കാരണമാകരുത്.

> **🌍 യഥാർഥ ഉദാഹരണം:** ഒരു പഴയ monolith-ന്റെ authentication പാളി ഒരു പുതിയ framework-ലേക്ക് മാറ്റാൻ ഒരു എൻജിനീയർ ഒരു coding agent ഉപയോഗിച്ചു, ഇതിന് പല മൊഡ്യൂളുകളിലായി ഡസൻ കണക്കിന് ഫയലുകൾ വായിക്കേണ്ടിയിരുന്നു. ഒരു നീണ്ട session-ന്റെ പാതിവഴിയിൽ, ഒരു മണിക്കൂർ മുൻപ് വായിച്ച യഥാർഥ (അസാധാരണമായ) session-കൈകാര്യ കോഡുമായി യോജിക്കാത്ത "സാധാരണ" middleware മാതൃകകൾ agent നിർദേശിക്കാൻ തുടങ്ങി. വിശകലനം ചെയ്ത ഓരോ മൊഡ്യൂളിനും ശേഷം agent ഒരു `migration_notes.md` scratchpad എഴുതുന്ന വിധത്തിലും, ഫയൽ-തോറുമുള്ള പര്യവേക്ഷണം ഓരോന്നിനും രണ്ട് ഖണ്ഡിക സംഗ്രഹം മാത്രം നൽകുന്ന subagent-കൾക്ക് ഏൽപ്പിച്ചും ടീം ഇത് പരിഹരിച്ചു — പ്രധാന agent-ന്റെ context അസംസ്കൃത ഫയൽ ഉള്ളടക്കത്തിലല്ല, തീരുമാനങ്ങളിൽ കേന്ദ്രീകരിച്ച് നിലനിർത്തി.
