## Multi-Agent സിസ്റ്റങ്ങളിലെ പിഴവ് കൈമാറ്റം

ഒരു multi-agent സിസ്റ്റത്തിൽ, ഒരു coordinator (orchestrator) agent subagent-കൾക്ക് ജോലി ഏൽപ്പിക്കുകയും പിന്നെ ആ subagent-കൾ റിപ്പോർട്ട് ചെയ്യുന്നതിന്റെ അടിസ്ഥാനത്തിൽ തീരുമാനങ്ങൾ എടുക്കുകയും വേണം. Coordinator-ന്റെ തീരുമാനങ്ങളുടെ ഗുണനിലവാരം അതിന് ലഭിക്കുന്ന വിവരത്തിന്റെ ഗുണനിലവാരത്താൽ പരിമിതപ്പെടുന്നു — അതിൽ *പരാജയത്തെക്കുറിച്ചുള്ള* വിവരവും ഉൾപ്പെടുന്നു. ഒരു subagent നിശ്ശബ്ദമായോ, അവ്യക്തമായോ, തെറ്റിദ്ധരിപ്പിക്കുംവിധമോ പരാജയപ്പെട്ടാൽ, coordinator ആ പ്രശ്നം അവകാശമാക്കുകയും മോശം വിവരത്തിന് മേൽ തുടർ തീരുമാനങ്ങൾ കെട്ടിപ്പടുത്ത് പലപ്പോഴും അത് കൂടുതൽ വഷളാക്കുകയും ചെയ്യുന്നു.

### "വിജയം/പരാജയം റിപ്പോർട്ട് ചെയ്താൽ മതി" എന്നത് എന്തുകൊണ്ട് പോരാ

Subagent ഫലങ്ങളെ ദ്വിമാനമായി കരുതാൻ തോന്നും: പ്രവർത്തിച്ചു, അല്ലെങ്കിൽ ഇല്ല. പക്ഷേ ഒരു ദ്വിമാന സൂചന മാത്രം ലഭിക്കുന്ന coordinator-ന് നല്ലൊരു വീണ്ടെടുക്കൽ തീരുമാനം എടുക്കാനാകില്ല. ഒരു വിജ്ഞാന ശേഖരം തിരയാൻ ഏൽപ്പിച്ച, പ്രസക്തമായ ഒന്നും കണ്ടെത്താത്ത ഒരു subagent പരിഗണിക്കുക. അത് ഒരു യഥാർഥ "ഫലങ്ങളില്ല" ആണോ (തിരയൽ പ്രവർത്തിച്ചു, ഒന്നുമില്ല) അതോ ഒരു പരാജയമാണോ (തിരയൽ API സമയപരിധി കവിഞ്ഞു, ക്രെഡൻഷ്യലുകൾ കാലഹരണപ്പെട്ടു, ചോദ്യം തെറ്റായി രൂപപ്പെട്ടു)? വ്യത്യാസം തിരിച്ചറിയാനാകാത്ത ഒരു coordinator, തിരയൽ യഥാർഥത്തിൽ ഒരിക്കലും നടന്നിട്ടില്ലാത്തപ്പോൾ "വിവരമൊന്നും ലഭ്യമല്ല" എന്ന് അന്തിമ ഉപയോക്താവിനോട് റിപ്പോർട്ട് ചെയ്തേക്കാം.

### സാധാരണ പരാജയ മാതൃകകൾ, ഏറ്റവും മോശത്തിൽ നിന്ന് ഏറ്റവും നല്ലതിലേക്ക്

| സമീപനം | പ്രശ്നം |
|---|---|
| ഒഴിഞ്ഞ ഫലം നൽകി അത് വിജയമായി അടയാളപ്പെടുത്തുക | ജോലി വിജയിച്ചെന്ന് coordinator വിശ്വസിക്കുകയും, വിട്ടുപോയ ഡാറ്റയെ ഡാറ്റയുടെ സ്ഥിരീകരിച്ച അഭാവമായി കണക്കാക്കി തുടർ തീരുമാനങ്ങൾ എടുക്കുകയും ചെയ്യുന്നു |
| ഒരു agent പരാജയപ്പെടുന്ന നിമിഷം മുഴുവൻ ജോലിക്രമവും നിർത്തുക | പരാജയം വീണ്ടെടുക്കാവുന്നതോ ഒറ്റപ്പെട്ടതോ ആയിരുന്നാൽ പോലും, വിജയിച്ച മറ്റ് agent-കൾ ഇതിനകം ചെയ്ത മുഴുവൻ ജോലിയും പാഴാക്കുന്നു |
| "search unavailable" പോലുള്ള ഒരു പൊതു സന്ദേശം നൽകുക | വീണ്ടും ശ്രമിക്കണോ, ഒരു ബദൽ ഉറവിടത്തിലേക്ക് മാറണോ, അതോ ഈ ഭാഗം ഒഴിവാക്കി തുടരണോ എന്ന് തീരുമാനിക്കാൻ coordinator-ന് ഒരു വഴിയുമില്ല |
| ഒരു ഘടനാപരമായ പിഴവ് നൽകുക: പരാജയ തരം, എന്ത് ശ്രമിച്ചു, ഭാഗിക ഫലങ്ങൾ, ലഭ്യമായ ബദലുകൾ | ബുദ്ധിപരമായ ഒരു വീണ്ടെടുക്കൽ തീരുമാനം എടുക്കാൻ coordinator-ന് മതിയായ വിവരമുണ്ട് — വീണ്ടും ശ്രമിക്കുക, മറ്റൊരു ഡാറ്റ ഉറവിടം ഉപയോഗിക്കുക, അല്ലെങ്കിൽ ഒരു മുന്നറിയിപ്പോടെ ഭാഗിക ഫലങ്ങളുമായി തുടരുക |

### ഒരു നല്ല ഘടനാപരമായ പിഴവ് എങ്ങനെയിരിക്കും

വിജയകരമായ മാതൃക, subagent പരാജയ റിപ്പോർട്ടിങ്ങിനെ agent-ന്റെ ഔട്ട്പുട്ട് വ്യവസ്ഥയുടെ ഒരു പ്രഥമ ഭാഗമായി കണക്കാക്കുക എന്നതാണ്, പിന്നീടുള്ള ഒരു ചിന്തയായല്ല. നന്നായി രൂപകൽപ്പന ചെയ്ത ഒരു പരാജയ റിപ്പോർട്ടിൽ സാധാരണയായി ഇവ ഉൾപ്പെടുന്നു:

- **പരാജയ തരം/വിഭാഗം** — timeout, authentication പിഴവ്, പൊരുത്തപ്പെടുന്ന ഡാറ്റയില്ല, തെറ്റായ ഇൻപുട്ട്, rate limit, മുതലായവ. വ്യത്യസ്ത പരാജയ വിഭാഗങ്ങൾക്ക് വ്യത്യസ്ത വീണ്ടെടുക്കൽ തന്ത്രങ്ങൾ പ്രയോഗിക്കാൻ ഇത് coordinator-നെ അനുവദിക്കുന്നു.
- **എന്ത് ശ്രമിച്ചു** — ഏത് ചോദ്യം, ഏത് endpoint, എത്ര retry — അങ്ങനെ coordinator-ന് (അല്ലെങ്കിൽ പിന്നീട് ലോഗുകൾ പരിശോധിക്കുന്ന ഒരു മനുഷ്യന്) എന്ത് സംഭവിച്ചെന്ന് പുനർനിർമിക്കാനാകും.
- **ഭാഗിക ഫലങ്ങൾ, ഉണ്ടെങ്കിൽ** — ഭാഗികമെന്ന് വ്യക്തമായി ലേബൽ ചെയ്തിരിക്കുന്നിടത്തോളം, ഒരു അപൂർണ ഉത്തരം പോലും ഒന്നുമില്ലാത്തതിനെക്കാൾ ഉപകാരപ്രദമാകാം.
- **അറിയാവുന്ന ബദലുകൾ** — ഉദാ: "പ്രാഥമിക ഡാറ്റാബേസിൽ എത്താനാകുന്നില്ല, പക്ഷേ 2 മണിക്കൂർ മുൻപുള്ള ഒരു cache snapshot ലഭ്യമാണ്" എന്നത് ഒരു അന്തമില്ലാത്ത വഴിക്ക് പകരം coordinator-ന് യഥാർഥത്തിൽ ഒരു തീരുമാനം നൽകുന്നു.

സിസ്റ്റങ്ങൾ വളരുമ്പോൾ ഇത് കൂടുതൽ പ്രധാനമാകുന്നു: ഒരൊറ്റ agent-ഉള്ളപ്പോൾ സാധാരണയായി ഒരു മനുഷ്യൻ നോക്കിനിൽക്കുന്നുണ്ട്, അവ്യക്തമായ ഒരു പരാജയം വ്യാഖ്യാനിക്കാൻ കഴിയും. പല subagent-കൾ സമാന്തരമായോ ക്രമത്തിലോ പ്രവർത്തിക്കുമ്പോൾ, നോക്കിനിൽക്കുന്നത് coordinator *മാത്രമാണ്*, അതിനാൽ പരാജയങ്ങളെക്കുറിച്ച് ചിന്തിക്കാനുള്ള അതിന്റെ കഴിവ് പൂർണമായും അതിന് നൽകുന്ന ഘടനാപരമായ വിവരത്തിന്റെ ഗുണനിലവാരത്തെ ആശ്രയിച്ചിരിക്കുന്നു.

> **🌍 യഥാർഥ ഉദാഹരണം:** ഒരു സാമ്പത്തിക ഗവേഷണ സഹായി മൂന്ന് subagent-കളെ ഏകോപിപ്പിക്കുന്നു: ഒന്ന് SEC ഫയലിങ്ങുകൾ എടുക്കുന്നു, ഒന്ന് അനലിസ്റ്റ് കണക്കുകൾ എടുക്കുന്നു, ഒന്ന് സമീപകാല വാർത്തകൾ എടുക്കുന്നു. അനലിസ്റ്റ്-കണക്ക് subagent ഒരു rate limit-ൽ എത്തിയപ്പോൾ, ഒരു ആദ്യ പതിപ്പ് വെറും ഒഴിഞ്ഞ ഒരു പട്ടിക നൽകി, coordinator "കണക്കുകളില്ല" എന്നത് ഒരു സാധുവായ കണ്ടെത്തലായി കണക്കാക്കി, ഉപയോക്താവിനോട് "ഈ ഓഹരിക്ക് അനലിസ്റ്റ് കണക്കുകളൊന്നും നിലവിലില്ല" എന്ന് പറഞ്ഞു — അത് തെറ്റും തെറ്റിദ്ധരിപ്പിക്കുന്നതുമായിരുന്നു. ഒരു ഘടനാപരമായ പിഴവ് നൽകാൻ ടീം subagent പുനർരൂപകൽപ്പന ചെയ്തശേഷം (`{type: "rate_limited", attempted: "estimates API v2", partial: null, alternative: "retry in 60s or use cached estimates from yesterday"}`), coordinator ശരിയായി ഒരിക്കൽ വീണ്ടും ശ്രമിക്കാൻ തീരുമാനിച്ചു, അതും പരാജയപ്പെട്ടപ്പോൾ ഒരു തെറ്റായ നിഷേധത്തിന് പകരം ഉപയോക്താവിന് വ്യക്തമായ ഒരു മുന്നറിയിപ്പ് നൽകി.
