## CLAUDE.md — പ്രധാന ക്രമീകരണ ഫയൽ

Claude Code-ൽ ഒരു session തുടങ്ങുമ്പോഴെല്ലാം, നിങ്ങളുടെ പ്രോജക്ടിന്റെ കീഴ്‌വഴക്കങ്ങളോ, ടീമിന്റെ ഇഷ്ട ലൈബ്രറികളോ, ഒരിക്കലും തൊടാൻ പാടില്ലാത്ത കാര്യങ്ങളോ (ഒരു പ്രൊഡക്ഷൻ ഡാറ്റാബേസ് migration സ്ക്രിപ്റ്റ് പോലെ) Claude-ന് സ്വയമേവ അറിയില്ല. ആ വിടവ് നികത്തുന്നതാണ് CLAUDE.md. session-ന്റെ തുടക്കത്തിൽ Claude സ്വയമേവ വായിക്കുന്ന ഒരു സാധാരണ markdown ഫയലാണിത്, ഒരു സ്ഥിരം ബ്രീഫിങ് രേഖ പോലെയാണ് അത് പ്രവർത്തിക്കുന്നത് — ആദ്യ ദിവസം ഒരു പുതിയ കരാറുകാരന് നൽകുന്ന പരിചയപ്പെടുത്തൽ കുറിപ്പുകൾ പോലെ.

ഓരോ session-ലും Claude ഈ ഫയൽ വീണ്ടും വായിക്കുന്നതിനാൽ, അതിൽ വയ്ക്കുന്നതെന്തും ആവർത്തിച്ച് പറയാതെതന്നെ സംഭാഷണങ്ങൾക്കിടയിൽ നിലനിൽക്കുന്നു. അതാണ് അടിസ്ഥാന മൂല്യം: ഓരോ ചാറ്റിലും "ഞങ്ങൾ npm അല്ല, pnpm ഉപയോഗിക്കുന്നു" അല്ലെങ്കിൽ "main-ലേക്ക് നേരിട്ട് commit ചെയ്യരുത്" എന്ന് വീണ്ടും ടൈപ്പ് ചെയ്യുന്നതിന് പകരം, ഒരിക്കൽ എഴുതിയാൽ അത് എപ്പോഴും context-ൽ ഉണ്ടാകും.

### 3 തലങ്ങളിലുള്ള ക്രമീകരണ ശ്രേണി

CLAUDE.md ഫയലുകൾ മൂന്ന് വ്യത്യസ്ത തലങ്ങളിൽ ഉണ്ടാകാം, ഒരു നിയമം ഏത് തലത്തിൽ വേണമെന്ന് മനസ്സിലാക്കുന്നത് Claude Code ക്രമീകരിക്കുന്നതിലെ ഏറ്റവും പ്രായോഗിക പ്രാധാന്യമുള്ള വൈദഗ്ധ്യങ്ങളിൽ ഒന്നാണ്:

1. **User തലം (വ്യക്തിഗതം)** — `~/.claude/CLAUDE.md`. ഇത് നിങ്ങളുടെ home directory-യിൽ, ഏതെങ്കിലും git റെപ്പോസിറ്ററിക്ക് പുറത്താണ്. നിങ്ങൾ തുറക്കുന്ന എല്ലാ പ്രോജക്ടിലും, നിങ്ങൾക്ക് മാത്രം ഇത് ബാധകമാണ്. സഹപ്രവർത്തകരുമായി ഒരിക്കലും പങ്കിടുന്നില്ല, version control-ൽ ഒരിക്കലും ചേർക്കുന്നില്ല. "എനിക്ക് വിശദമായ വിശദീകരണങ്ങൾ ഇഷ്ടമാണ്" അല്ലെങ്കിൽ "commit trailer-ൽ എപ്പോഴും എന്റെ വ്യക്തിഗത GitHub handle ഉപയോഗിക്കുക" പോലുള്ളവയുടെ ശരിയായ ഇടമാണിത് — പ്രോജക്ടിനെക്കുറിച്ചല്ല, *നിങ്ങളെക്കുറിച്ചുള്ള* മുൻഗണനകൾ.

2. **Project തലം (ടീം)** — റെപ്പോ റൂട്ടിലെ `./CLAUDE.md` അല്ലെങ്കിൽ `.claude/CLAUDE.md`. ഇത് git-ൽ ചേർക്കുന്നു, അതിനാൽ കോഡ്ബേസിനൊപ്പം സഞ്ചരിക്കുകയും clone ചെയ്യുന്ന എല്ലാവർക്കും ബാധകമാകുകയും ചെയ്യുന്നു. ടീം-വ്യാപക മാനദണ്ഡങ്ങൾ ഇവിടെയാണ് വേണ്ടത്: കോഡിങ് ശൈലി, ടെസ്റ്റിങ് ആവശ്യകതകൾ, deployment guardrail-കൾ, ആർക്കിടെക്ചർ കീഴ്‌വഴക്കങ്ങൾ.

3. **Directory തലം (നിർദിഷ്ടം)** — ഒരു ഉപഫോൾഡറിനുള്ളിൽ വയ്ക്കുന്ന ഒരു `CLAUDE.md`. Claude ആ നിർദിഷ്ട ഫോൾഡറിനുള്ളിൽ സജീവമായി പ്രവർത്തിക്കുമ്പോൾ മാത്രം ഇത് ബാധകമാകുന്നു, അങ്ങനെ റൂട്ട് ഫയൽ കുഴപ്പത്തിലാക്കാതെ, ഉദാഹരണത്തിന് ഒരു `backend/` ഫോൾഡറിനും ഒരു `frontend/` ഫോൾഡറിനും കൂടുതൽ നിർദിഷ്ട നിർദേശങ്ങൾ നൽകാം.

> **🔑 പ്രധാന നിഗമനം:** സുവർണ നിയമം ഇതാണ് — **ടീം നിയമങ്ങൾ project തലത്തിലുള്ള ഫയലിലാണ് വേണ്ടത്, user തലത്തിലുള്ളതിലല്ല.** ഒരു നിർണായക നിയമം നിങ്ങളുടെ വ്യക്തിഗത `~/.claude/CLAUDE.md`-ൽ വച്ചാൽ, അത് നിങ്ങളെ എല്ലായിടത്തും പിന്തുടരും, പക്ഷേ ഒരു പുതിയ സഹപ്രവർത്തകൻ ചേർന്ന് റെപ്പോ clone ചെയ്യുന്ന നിമിഷം അവർക്കത് ലഭിക്കില്ല — കാരണം അത് ഒരിക്കലും റെപ്പോയിൽ ഉണ്ടായിരുന്നില്ല. ഏറ്റവും സാധാരണമായ ക്രമീകരണ പിഴവ് കൃത്യമായി ഇതാണ്: ഒരു നിയമം "എന്റെ യന്ത്രത്തിൽ" പ്രവർത്തിക്കുന്നു, കാരണം അത് ആരുടെയോ വ്യക്തിഗത ക്രമീകരണത്തിലാണ്, ഒരു പുതിയ ജീവനക്കാരന്റെ Claude session മറ്റെല്ലാവരുടേതിൽ നിന്നും വ്യത്യസ്തമായി പെരുമാറുന്നതുവരെ അത് നഷ്ടപ്പെട്ടിരിക്കുന്നുവെന്ന് ആരും ശ്രദ്ധിക്കുന്നില്ല.

> **🌍 യഥാർഥ ഉദാഹരണം:** ഒരു ഫിൻടെക് സ്റ്റാർട്ടപ്പിൽ ലീഡ് എൻജിനീയറുടെ `~/.claude/CLAUDE.md`-ൽ "വ്യക്തമായ സ്ഥിരീകരണമില്ലാതെ `/migrations`-ലെ ഫയലുകൾ ഒരിക്കലും മാറ്റരുത്" എന്ന ഒരു വ്യക്തിഗത നിയമം ഉണ്ടെന്ന് സങ്കൽപ്പിക്കുക. അവർക്ക് അത് നന്നായി പ്രവർത്തിക്കുന്നു. മൂന്ന് മാസത്തിന് ശേഷം ഒരു പുതിയ ബാക്കെൻഡ് എൻജിനീയർ ചേരുന്നു, റെപ്പോ clone ചെയ്യുന്നു, "കുറച്ച് പഴയ migration ഫയലുകൾ വൃത്തിയാക്കുക" എന്ന് Claude Code-നോട് ആവശ്യപ്പെടുന്നു — ആ guardrail-ന്റെ ഒരു രേഖയുമില്ലാത്ത Claude, ഉപയോഗശൂന്യമായ കോഡ് പോലെ തോന്നുന്നത് സന്തോഷത്തോടെ ഇല്ലാതാക്കുന്നു, ഒരു ഓഡിറ്റ് രേഖയ്ക്ക് ആവശ്യമായ ഒരു ചരിത്രപരമായ migration നഷ്ടപ്പെടുന്നു. അതേ നിയമം project തലത്തിലുള്ള `.claude/CLAUDE.md`-ൽ ആയിരുന്നെങ്കിൽ, റെപ്പോയുടെ ഓരോ പുതിയ clone-ഉം ആ സുരക്ഷ സ്വയമേവ അവകാശമാക്കുമായിരുന്നു.

### CLAUDE.md ക്രമത്തിൽ സൂക്ഷിക്കൽ

ഒരു പ്രോജക്ട് വളരുമ്പോൾ, ഒരൊറ്റ CLAUDE.md ഫയൽ കൈകാര്യം ചെയ്യാൻ പ്രയാസമാകാം — ടെസ്റ്റിങ് കീഴ്‌വഴക്കങ്ങളും API രൂപകൽപ്പനാ നിയമങ്ങളും deployment കുറിപ്പുകളും കൂടിക്കലർന്ന നൂറുകണക്കിന് വരികൾ. ഇത് പരിപാലിക്കാവുന്നതാക്കി നിലനിർത്താൻ Claude Code രണ്ട് വഴികൾ നൽകുന്നു:

| രീതി | എന്ത് ചെയ്യുന്നു | എപ്പോൾ ഉപയോഗിക്കണം |
|---|---|---|
| `@import filename.md` | മറ്റൊരു ഫയലിന്റെ ഉള്ളടക്കം നേരിട്ട് CLAUDE.md-ലേക്ക് കൊണ്ടുവരുന്നു | ഓരോ വിഷയത്തിനും മാനദണ്ഡങ്ങൾ വെവ്വേറെ ഫയലുകളായി വിഭജിക്കുമ്പോൾ (ഉദാ: `@import docs/testing-standards.md`) |
| `.claude/rules/` ഫോൾഡർ | ഓരോ വിഷയത്തിനും വെവ്വേറെ നിയമ ഫയലുകൾ സൂക്ഷിക്കുന്നു, ഐച്ഛികമായി നിർദിഷ്ട ഫയൽ പാതകളിലേക്ക് പരിമിതപ്പെടുത്താം | CLAUDE.md വളരെ നീണ്ടതാകുമ്പോൾ (ഏകദേശം 500+ വരികൾ) വിഭജിക്കേണ്ടിവരുമ്പോൾ |
| glob മാതൃകകളോടെ പാത പരിമിതപ്പെടുത്തൽ | പൊരുത്തപ്പെടുന്ന ഫയലുകളിൽ Claude പ്രവർത്തിക്കുമ്പോൾ മാത്രം നിയമങ്ങൾ context-ലേക്ക് വരുന്നു | ഉദാ: `*.test.tsx` ഫയലുകൾ തിരുത്തുമ്പോൾ മാത്രം ബാധകമാകുന്ന ടെസ്റ്റ് എഴുത്ത് നിയമങ്ങൾ |

അടിസ്ഥാന തത്ത്വം context ശുചിത്വമാണ്: കൈയിലുള്ള ജോലിക്ക് ബാധകമല്ലാത്ത നിയമങ്ങൾ കൊണ്ട് context window കുഴഞ്ഞുമറിയാത്തപ്പോൾ Claude മികച്ച പ്രകടനം കാഴ്ചവയ്ക്കുന്നു. ഒരു Python ബാക്കെൻഡ് സ്ക്രിപ്റ്റ് Claude debug ചെയ്യുമ്പോൾ ഒരു React കംപോണന്റ് ശൈലിയെക്കുറിച്ചുള്ള നിയമം വെറും ശബ്ദമാണ് — നിയമങ്ങൾ വിഭജിച്ച് പരിധി നിർണയിക്കുന്നത് ഓരോ session-ഉം പ്രസക്തമായതിൽ കേന്ദ്രീകരിക്കാൻ സഹായിക്കുന്നു.
