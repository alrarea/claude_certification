## കസ്റ്റം Slash Commands & Skills

ടീമുകൾ Claude Code സ്വീകരിക്കുമ്പോൾ, ഒരേ ബഹുഘട്ട ജോലിക്രമങ്ങൾ വീണ്ടും വീണ്ടും ടൈപ്പ് ചെയ്യപ്പെടാറുണ്ട്: "ഞങ്ങളുടെ ചെക്ക്‌ലിസ്റ്റുമായി ഈ PR പരിശോധിക്കുക," "deployment-ന് മുൻപുള്ള ഘട്ടങ്ങൾ നടത്തുക," "ഇന്നത്തെ git പ്രവർത്തനം സംഗ്രഹിക്കുക." ഈ ആവർത്തിക്കുന്ന ജോലിക്രമങ്ങൾ ഒരിക്കൽ രേഖപ്പെടുത്തി ഒരു ചെറിയ ട്രിഗർ കൊണ്ട് വിളിക്കാൻ വേണ്ടിയാണ് കസ്റ്റം slash commands-ഉം Skills-ഉം ഉള്ളത് — വീണ്ടും ടൈപ്പ് ചെയ്യുന്നതിന് പകരം, അല്ലെങ്കിൽ അതിലും മോശമായി, പാതി ഓർമയിൽ ഓരോ തവണയും അൽപ്പം വ്യത്യസ്തമായി ചെയ്യുന്നതിന് പകരം.

### Slash Commands

ഒരു slash command അടിസ്ഥാനപരമായി `/project:review-pr` എന്ന് ടൈപ്പ് ചെയ്യുന്നതുപോലുള്ള ഒരു കുറുക്കുവഴി കൊണ്ട് വിളിക്കാവുന്ന, സൂക്ഷിച്ചുവച്ച ഒരു prompt ടെംപ്ലേറ്റാണ്. "ടെസ്റ്റുകൾ പരിശോധിക്കുക, lint പിഴവുകൾ പരിശോധിക്കുക, സുരക്ഷാ പ്രശ്നങ്ങൾ പരിശോധിക്കുക, changelog എൻട്രി പരിശോധിക്കുക" എന്നതിന്റെ ഓരോ ഘട്ടവും ഒരു ഡെവലപ്പർ ഓർത്തിരിക്കേണ്ടതിന് പകരം, മുഴുവൻ ചെക്ക്‌ലിസ്റ്റും ഒരിക്കൽ നിർവചിച്ച് ഒരൊറ്റ കമാൻഡ് കൊണ്ട് പ്രവർത്തിപ്പിക്കുന്നു.

### Skills

Skills സമാനമായ ഉദ്ദേശ്യം നിറവേറ്റുന്നു — ആവർത്തിക്കാവുന്ന ഒരു ജോലിക്രമം പൊതിയുക — പക്ഷേ കൂടുതൽ മുന്നോട്ടുപോകുന്നു. ഒരു Skill സ്വന്തം ഒറ്റപ്പെട്ട context-ൽ പ്രവർത്തിക്കുന്നു (അതിനാൽ വാചാലവും പര്യവേക്ഷണാത്മകവുമായ ഒരു ജോലിക്രമം നിങ്ങളുടെ പ്രധാന സംഭാഷണം നിറച്ച് കുഴപ്പത്തിലാക്കുന്നില്ല), കൂടാതെ `SKILL.md` എന്ന ഫയലിലെ ഒരു frontmatter ബ്ലോക്ക് വഴി അതിന്റേതായ ക്രമീകരണം പിന്തുണയ്ക്കുന്നു. ഒരു ജോലിക്രമം എത്രത്തോളം സങ്കീർണമാണെന്നാൽ അത് ഏതൊക്കെ ടൂളുകൾ തൊടാമെന്ന് കൃത്യമായി നിയന്ത്രിക്കണം, അല്ലെങ്കിൽ അതിന്റെ ഇടക്കാല ഔട്ട്പുട്ട് പ്രധാന ചാറ്റിലേക്ക് എല്ലാം തള്ളിയാൽ ശബ്ദമാകും — അപ്പോൾ Skills ആണ് മെച്ചപ്പെട്ട തിരഞ്ഞെടുപ്പ്.

### Commands-ഉം Skills-ഉം എവിടെ നിലനിൽക്കുന്നു

Commands-ഉം Skills-ഉം ഒരു "project" രൂപത്തിലും ഒരു "personal" രൂപത്തിലും വരുന്നു, ഈ വ്യത്യാസം നിങ്ങൾക്ക് ഇതിനകം പരിചിതമായ CLAUDE.md ശ്രേണിയെ പ്രതിഫലിപ്പിക്കുന്നു: project-പരിധിയിലുള്ളവ git-ൽ ചേർത്ത് മുഴുവൻ ടീമുമായി പങ്കിടുന്നു, personal-പരിധിയിലുള്ളവ നിങ്ങളുടെ home directory-യിൽ നിങ്ങൾക്ക് മാത്രമായി നിലനിൽക്കുന്നു.

| തരം | സ്ഥാനം | ആർക്ക് ഉപയോഗിക്കാം | ഏതിന് നല്ലത് |
|---|---|---|---|
| Project Command | `.claude/commands/` | ടീമിലെ എല്ലാവർക്കും (git-ൽ ചേർത്തത്) | PR review, deployment പോലുള്ള പങ്കിട്ട ജോലിക്രമങ്ങൾ |
| Personal Command | `~/.claude/commands/` | നിങ്ങൾക്ക് മാത്രം | വ്യക്തിഗത കുറുക്കുവഴികൾ |
| Project Skill | `.claude/skills/` | ടീമിലെ എല്ലാവർക്കും | context ഒറ്റപ്പെടുത്തൽ ഗുണം ചെയ്യുന്ന സങ്കീർണ ജോലിക്രമങ്ങൾ |
| Personal Skill | `~/.claude/skills/` | നിങ്ങൾക്ക് മാത്രം | സഹപ്രവർത്തകരെ ബാധിക്കാത്ത വ്യക്തിഗത വകഭേദങ്ങൾ |

### Skill Frontmatter ഉപാധികൾ

ഒരു Skill ഒരു `SKILL.md` ഫയലിൽ നിർവചിക്കുന്നതിനാൽ, ഒരു സാധാരണ slash command-ന് കഴിയാത്ത അധിക ക്രമീകരണം അതിന്റെ frontmatter-ന് വഹിക്കാനാകും:

- **`context: fork`** — Skill-നെ അതിന്റേതായ ഒറ്റപ്പെട്ട ഉപ-session-ൽ പ്രവർത്തിപ്പിക്കുന്നു, അതിനാൽ അതിന്റെ ഔട്ട്പുട്ട് നിങ്ങളുടെ പ്രധാന സംഭാഷണം മലിനമാക്കുന്നില്ല. വാചാലമായ വിശകലന ജോലിക്രമങ്ങൾക്ക് (ഉദാ: "മുഴുവൻ റെപ്പോയും സ്കാൻ ചെയ്ത് എല്ലാ TODO-യും സംഗ്രഹിക്കുക") ഇത് പ്രത്യേകിച്ച് വിലപ്പെട്ടതാണ് — അന്തിമ സംഗ്രഹം വേണം, മുഴുവൻ സ്കാൻ വിവരണവും പ്രധാന context-ൽ ഇരിക്കേണ്ട.
- **`allowed-tools: [Read, Write]`** — Skill-ന് ഏതൊക്കെ ടൂളുകൾ ഉപയോഗിക്കാമെന്ന് പരിമിതപ്പെടുത്തുന്നു. ഇതൊരു സുരക്ഷാ സംവിധാനമാണ്: കോഡ് *വിശകലനം* ചെയ്യാൻ മാത്രമുള്ള ഒരു Skill-ന് `Write`-ഉം `Bash`-ഉം പൂർണമായി പൂട്ടിവയ്ക്കാം, അങ്ങനെ ഒരു prompt injection-ഓ ഒരു ബഗ്ഗോ ആ ദിശയിലേക്ക് തള്ളാൻ ശ്രമിച്ചാലും നാശകരമായ പ്രവൃത്തികൾ ചെയ്യുന്നത് തടയുന്നു.
- **`argument-hint: "PR number"`** — ആവശ്യമായ ഒരു പാരാമീറ്റർ നൽകാതെ Skill വിളിച്ചാൽ ഡെവലപ്പറോട് അത് ചോദിക്കുന്നു, ഒരു argument മറന്നാൽ ഉപയോഗ വിവരം അച്ചടിക്കുന്ന ഒരു CLI ഉപകരണം പോലെ.

> **💡 നുറുങ്ങ്:** ഒറ്റപ്പെടുത്തൽ (ജോലിക്രമം നീണ്ടതോ വാചാലമോ ആണ്) അല്ലെങ്കിൽ സുരക്ഷാ നിയന്ത്രണങ്ങൾ (ജോലിക്രമം ചില ടൂളുകൾ തൊടാൻ പാടില്ല) വേണ്ടിവരുമ്പോൾ ഒരു സാധാരണ slash command-ന് പകരം ഒരു Skill ഉപയോഗിക്കുക. ഇവ രണ്ടും ബാധകമല്ലെങ്കിൽ, ഭാരം കുറഞ്ഞ ഒരു slash command പരിപാലിക്കാൻ എളുപ്പമാണ്.

> **🌍 യഥാർഥ ഉദാഹരണം:** ഒരു ടീം `context: fork`-ഉം `allowed-tools: [Read, Grep, Glob]`-ഉം ഉള്ള ഒരു `/project:review-pr` Skill പരിപാലിക്കുന്നു. ഒരു ഡെവലപ്പർ ഒരു pull request തുറക്കുമ്പോൾ അവർ Skill വിളിക്കുന്നു, അത് മാറിയ ഓരോ ഫയലും വായിക്കുന്നു, ടീമിന്റെ ശൈലീ മാർഗരേഖയുമായി ഒത്തുനോക്കുന്നു, നഷ്ടപ്പെട്ട ടെസ്റ്റുകൾ പരിശോധിക്കുന്നു — എല്ലാം അതിന്റേതായ fork ചെയ്ത ഉപ-session-നുള്ളിൽ. `allowed-tools` `Write`-ഉം `Bash`-ഉം ഒഴിവാക്കുന്നതിനാൽ, മാറ്റം മനസ്സിലാക്കാൻ പൂർണ വായനാ പ്രവേശനമുണ്ടെങ്കിലും, പരിശോധിക്കുന്നതിനിടെ അബദ്ധത്തിൽ ഫയലുകൾ മാറ്റാനോ കമാൻഡുകൾ പ്രവർത്തിപ്പിക്കാനോ review Skill-ന് ഘടനാപരമായി തന്നെ കഴിയില്ല. ഡെവലപ്പറുടെ പ്രധാന സംഭാഷണം അന്തിമ review സംഗ്രഹം മാത്രമേ കാണുന്നുള്ളൂ, അവിടെയെത്താൻ Skill നടത്തിയ ഡസൻ കണക്കിന് ഫയൽ വായനകൾ കാണുന്നില്ല.
