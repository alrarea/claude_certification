## Plan Mode vs. നേരിട്ടുള്ള നിർവഹണം

എല്ലാ ജോലിക്കും ഒരേ അളവിലുള്ള ജാഗ്രത വേണ്ടതില്ല. ഒരു കമന്റിലെ അക്ഷരത്തെറ്റ് തിരുത്തുന്നതും ഒരു microservice ആർക്കിടെക്ചർ പുനഃക്രമീകരിക്കുന്നതും "കോഡിൽ മാറ്റം വരുത്താൻ Claude-നോട് ആവശ്യപ്പെടുന്നു" എന്ന നിലയിൽ ഒരുപോലെയാണ്, പക്ഷേ അവയെ ഒരേപോലെ കണക്കാക്കുന്നത് — എപ്പോഴും മുൻകൂട്ടി ഒരു പദ്ധതി ആവശ്യപ്പെടുകയോ, എപ്പോഴും ഉടനടി നിർവഹിക്കുകയോ — ഒന്നുകിൽ നിസ്സാര ജോലി മന്ദഗതിയിലാക്കും, അല്ലെങ്കിൽ പരിശോധിക്കാത്ത വ്യാപകമായ മാറ്റങ്ങൾ കോഡ്ബേസിലുടനീളം വരുത്താനുള്ള അപകടമുണ്ടാക്കും. ചോദ്യത്തിന്റെ വലുപ്പത്തിനൊത്ത മറുപടി നൽകാൻ Claude Code രണ്ട് രീതികൾ നൽകുന്നു.

### Plan Mode

Plan mode-ൽ, എന്താണ് ചെയ്യാൻ ഉദ്ദേശിക്കുന്നത് എന്ന് വിവരിക്കുന്ന ഒരു പദ്ധതി Claude ആദ്യം തയ്യാറാക്കുന്നു — ഏതൊക്കെ ഫയലുകൾ തൊടും, എന്ത് സമീപനം സ്വീകരിക്കും, എന്തൊക്കെ വിട്ടുവീഴ്ചകൾ തൂക്കിനോക്കുന്നു — എന്നിട്ട് എന്തെങ്കിലും മാറ്റം വരുത്തും മുൻപ് നിങ്ങളുടെ വ്യക്തമായ അനുമതിക്കായി കാത്തിരിക്കുന്നു. നിങ്ങൾ അംഗീകരിച്ചശേഷം മാത്രമേ അത് നിർവഹണത്തിലേക്ക് നീങ്ങൂ. ഉറവിട പാഠത്തിലെ ഉപമ നല്ലതാണ്: നിർമാണം തുടങ്ങും മുൻപ് ഒരു കരാറുകാരൻ നിങ്ങൾക്ക് ബ്ലൂപ്രിന്റ് കാണിക്കുന്നതുപോലെ. ഒരൊറ്റ ചുമര് പൊളിക്കും മുൻപ് ഒരു തെറ്റായ അനുമാനം കണ്ടെത്താനോ, സമീപനം മാറ്റാനോ, മുഴുവൻ പദ്ധതിയും തള്ളാനോ നിങ്ങൾക്ക് അവസരം ലഭിക്കുന്നു.

### നേരിട്ടുള്ള നിർവഹണം

നേരിട്ടുള്ള നിർവഹണത്തിൽ, ആദ്യം പരിശോധിച്ച് അംഗീകരിക്കുന്ന ഘട്ടമില്ലാതെ Claude ഉടനടി ജോലി ചെയ്യുന്നു. ഉപമ തുടർന്നാൽ, ഇത് ഒരു കരാറുകാരൻ ഇറ്റുവീഴുന്ന ഒരു ടാപ്പ് ശരിയാക്കുന്നതുപോലെയാണ് — ശരിയായ പരിഹാരത്തെക്കുറിച്ച് അവ്യക്തതയില്ല, പരിധി ചെറുതാണ്, അഞ്ച് മിനിറ്റ് ജോലിക്ക് ഒപ്പിട്ട ബ്ലൂപ്രിന്റ് ആദ്യം വാങ്ങുന്നത് അനാവശ്യ ഭാരമാകും.

### ഇവയ്ക്കിടയിൽ തിരഞ്ഞെടുക്കൽ

തീരുമാനം അടിസ്ഥാനപരമായി അപകടസാധ്യതയിലേക്കും അവ്യക്തതയിലേക്കും ചുരുങ്ങുന്നു: ഒരു ജോലി ചെലവേറിയതോ പഴയപടിയാക്കാൻ പ്രയാസമുള്ളതോ ആയ വിധം തെറ്റാനുള്ള സാധ്യത കൂടുന്തോറും, അല്ലെങ്കിൽ തിരഞ്ഞെടുക്കാൻ ന്യായമായ സമീപനങ്ങൾ കൂടുന്തോറും, ആദ്യം ഒരു പദ്ധതി തയ്യാറാക്കുന്നത് കൂടുതൽ മൂല്യവത്താകുന്നു.

| Plan Mode ഉപയോഗിക്കുക… | നേരിട്ടുള്ള നിർവഹണം ഉപയോഗിക്കുക… |
|---|---|
| വലിയ തോതിലുള്ള മാറ്റങ്ങൾ (45+ ഫയലുകൾ) | ലളിതമായ, ഒറ്റ ഫയലിലെ ബഗ് പരിഹാരം |
| ആർക്കിടെക്ചർ തീരുമാനങ്ങൾ | ഒരു തീയതി validation പരിശോധന ചേർക്കൽ |
| ഒന്നിലധികം സാധുവായ സമീപനങ്ങൾ ഉണ്ട് | പരിഹാരം വ്യക്തവും നന്നായി മനസ്സിലാക്കിയതുമാണ് |
| ലൈബ്രറി migration | ഒരു വേരിയബിളിന്റെ പേര് മാറ്റൽ |
| Microservice പുനഃക്രമീകരണം | രേഖകളിലെ ഒരു അക്ഷരത്തെറ്റ് തിരുത്തൽ |

ഇടത് നിരയിലെ മാതൃക ശ്രദ്ധിക്കുക: വ്യാപ്തി (പല ഫയലുകൾ), അവ്യക്തത (ഒന്നിലധികം സാധുവായ സമീപനങ്ങൾ), പഴയപടിയാക്കാനുള്ള ബുദ്ധിമുട്ട് (ആർക്കിടെക്ചർ, migration-കൾ, പുനഃക്രമീകരണം) എന്നിവയാണ് ആവർത്തിക്കുന്ന സൂചനകൾ. വലത് നിര അതിന്റെ കണ്ണാടി പ്രതിബിംബമാണ്: ചെറിയ ആഘാത പരിധി, ഒരു വ്യക്തമായ ശരിയുത്തരം, തെറ്റിയാൽ നിസ്സാരമായി പഴയപടിയാക്കാം.

> **📝 പരീക്ഷാ ശ്രദ്ധ:** വേർതിരിക്കുന്ന സൂചന "ഇതൊരു കോഡ് മാറ്റമാണോ" എന്നതല്ല — രണ്ട് രീതികളും കോഡ് മാറ്റങ്ങൾ വരുത്തുന്നു. വേർതിരിക്കുന്ന സൂചന പരിധിയും അവ്യക്തതയുമാണ്. വ്യക്തമായ ശരിയുത്തരമുള്ള ഒരു വരി തിരുത്തലിന് ഒരു ബ്ലൂപ്രിന്റ് വേണ്ട; ഡസൻ കണക്കിന് ഫയലുകൾ തൊടുന്നതോ മത്സരിക്കുന്ന രൂപകൽപ്പനകൾക്കിടയിൽ ഒരു വിലയിരുത്തൽ ആവശ്യപ്പെടുന്നതോ ആയ മാറ്റത്തിന് വേണം.

> **🌍 യഥാർഥ ഉദാഹരണം:** 60+ ഫയലുകൾ തൊടുന്ന ഒരു monorepo-യിൽ അവരുടെ REST API പാളി ഒരു പഴയ HTTP client ലൈബ്രറിയിൽ നിന്ന് പുതിയ ഒന്നിലേക്ക് മാറ്റാൻ ഒരു എൻജിനീയറിങ് ടീം തീരുമാനിക്കുന്നു. ഫയലുകൾ ഓരോന്നായി Claude മുന്നോട്ടുകുതിക്കാൻ അനുവദിക്കുന്നതിന് പകരം അവർ plan mode വിളിക്കുന്നു. Claude ആദ്യം കോഡ്ബേസ് സർവേ ചെയ്യുന്നു, എല്ലാ വിളി സ്ഥലങ്ങളും കണ്ടെത്തുന്നു, ഒരു migration ക്രമം നിർദേശിക്കുന്നു (ആദ്യം utilities, പിന്നെ feature മൊഡ്യൂളുകൾ, പിന്നെ ടെസ്റ്റുകൾ), പഴയതും പുതിയതുമായ ലൈബ്രറികൾ retry-കൾ വ്യത്യസ്തമായി കൈകാര്യം ചെയ്യുന്ന രണ്ട് സ്ഥലങ്ങൾ എടുത്തുകാണിക്കുന്നു — ഒരു മനുഷ്യ തീരുമാനം വേണ്ട ഒരു ബിന്ദു. ടീം ഈ പദ്ധതി പരിശോധിച്ച് retry കൈകാര്യ സമീപനം സ്ഥിരീകരിച്ചശേഷം മാത്രമേ Claude ഫയലുകൾ ഓരോന്നായി നിർവഹിക്കാൻ തുടങ്ങൂ. ഇതിനെ, അതേ പ്രോജക്ടിലെ ഒരു സഹപ്രവർത്തകൻ അന്നേദിവസം പിന്നീട് ഒരു validation ഫംഗ്ഷനിലെ തകർന്ന ഒരു തീയതി-രൂപ string ശരിയാക്കാൻ മാത്രം Claude-നെ ആവശ്യപ്പെടുന്നതുമായി താരതമ്യം ചെയ്യുക — അവർ നേരിട്ടുള്ള നിർവഹണത്തിലേക്ക് പോകുന്നു, കാരണം കൃത്യമായി ഒരു വ്യക്തമായ പരിഹാരമേയുള്ളൂ, തെറ്റിയാലും കാര്യമായ അപകടമില്ല.
