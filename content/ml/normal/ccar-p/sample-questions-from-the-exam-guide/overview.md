# പരീക്ഷാ ഗൈഡിലെ മാതൃകാ ചോദ്യങ്ങൾ (In-Depth)

CCAR-P പരീക്ഷാ ഗൈഡിലെ (PDF) മൂന്ന് ഔദ്യോഗിക മാതൃകാ ചോദ്യങ്ങളാണ് ഇവ. ന്യായവാദം ശ്രദ്ധയോടെ പഠിക്കുക — പരീക്ഷ ഓർമശക്തിയല്ല, തീരുമാനമെടുക്കലാണ് പരിശോധിക്കുന്നത്. താഴെ, ഓരോ ചോദ്യവും യഥാർഥത്തോട് വിശ്വസ്തമായി നിലനിർത്തിയിരിക്കുന്നു (ചോദ്യം, ഉത്തര സാധ്യതകൾ, മുഴുവൻ വിശദീകരണം), ഒപ്പം അത് പരിശോധിക്കുന്ന ന്യായവാദ മാതൃകയെക്കുറിച്ച് ഒരു ചെറിയ കുറിപ്പും ചേർത്തിരിക്കുന്നു.

## മാതൃക 1 · ഡൊമെയ്ൻ 3 — സംയോജനം

> **📝️ പരീക്ഷാ ശ്രദ്ധ:** *തടയൽ* നിയന്ത്രണങ്ങളും (കഴിവ് നീക്കം ചെയ്യൽ) *കണ്ടെത്തൽ* നിയന്ത്രണങ്ങളും (ലോഗിങ്, സ്ഥിരീകരണം) വേർതിരിക്കാൻ നിങ്ങൾക്ക് കഴിയുമോ എന്ന് ഈ ചോദ്യം പരിശോധിക്കുന്നു — Integration, Governance ഡൊമെയ്നുകളിൽ ആവർത്തിച്ച് വരുന്ന ഒരു വേർതിരിവ്.

ടിക്കറ്റുകൾ വായിക്കാനും മറുപടികൾ തയ്യാറാക്കാനും റീഫണ്ട് നൽകാനും user അക്കൗണ്ടുകൾ മായ്ക്കാനും കഴിയുന്ന ഒരു ഉപഭോക്തൃ സപ്പോർട്ട് agent ഒരു ടീം നൽകുന്നു. സപ്പോർട്ട് ജീവനക്കാർക്ക് ടിക്കറ്റുകൾ വായിക്കാനും മറുപടികൾ തയ്യാറാക്കാനും മാത്രമേ വേണ്ടൂ. Least-privilege തത്വങ്ങൾ പ്രയോഗിച്ചാൽ, ഏത് മാറ്റമാണ് അപകടസാധ്യത ഏറ്റവും നന്നായി കുറയ്ക്കുന്നത്?

- A. ദുരുപയോഗം പിന്നീട് പരിശോധിക്കാൻ റീഫണ്ട്, delete ടൂളുകളിൽ ലോഗിങ് ചേർക്കുക.
- B. Agent-ന്റെ ക്രമീകരണത്തിൽ നിന്ന് റീഫണ്ട്, delete ടൂളുകൾ പൂർണമായി നീക്കുക.
- C. എല്ലാ ടൂളുകളും നിലനിർത്തി റീഫണ്ടുകൾക്കും മായ്ക്കലുകൾക്കും മുൻപ് ഒരു സ്ഥിരീകരണ ചോദ്യം ചേർക്കുക.
- D. നിർദേശങ്ങൾ കൂടുതൽ വിശ്വസനീയമായി പാലിക്കുന്ന ഒരു വലിയ മോഡൽ കൊണ്ട് agent-നെ മാറ്റുക.
- ✅ **ശരിയുത്തരം: B** — ടൂളുകൾ പൂർണമായി നീക്കുക.

**B എന്തുകൊണ്ട്?** Least privilege എന്നാൽ ആ role-ന് ആവശ്യമില്ലാത്ത കഴിവുകൾ നീക്കം ചെയ്യുക എന്നാണ് — അതിനെ നിരീക്ഷിക്കുകയോ കാവൽ നിൽക്കുകയോ അല്ല, ആക്രമണ പ്രതലം ഇല്ലാതാക്കുക. ലോഗിങ് (A), സ്ഥിരീകരണ ചോദ്യങ്ങൾ (C) എന്നിവ "കണ്ടെത്തൽ" നിയന്ത്രണങ്ങളാണ് — സംഭവത്തിനു ശേഷം അവ സഹായിക്കുന്നു, പക്ഷേ ടൂളുകൾ ഇപ്പോഴും നിലനിൽക്കുന്നു, ഇപ്പോഴും ദുരുപയോഗം ചെയ്യാം. മോഡലിന്റെ വലുപ്പത്തിന് (D) അനുമതി പരിധിയുമായി ഒരു ബന്ധവുമില്ല.

## മാതൃക 2 · ഡൊമെയ്ൻ 2 — Models, Prompting & Context

> **📝️ പരീക്ഷാ ശ്രദ്ധ:** ചുരുക്കലോ മോഡൽ ചെറുതാക്കലോ പോലുള്ള ബന്ധമില്ലാത്ത ഒരു പരിഹാരത്തിലേക്ക് പോകുന്നതിനു പകരം, ചെലവും latency-യും ചേർന്ന ഒരു പ്രശ്നത്തിന്റെ നേരിട്ടുള്ള ഉപാധിയായി prompt caching തിരിച്ചറിയുന്നുണ്ടോ എന്ന് ഇത് പരിശോധിക്കുന്നു.

ഒരു ആപ്ലിക്കേഷൻ ഓരോ അഭ്യർഥനയിലും അതേ 8,000-token system prompt-ഉം നയ രേഖയും അയക്കുന്നു, പിന്നാലെ ചെറുതും മാറുന്നതുമായ ഒരു user സന്ദേശവും. Latency-യും ചെലവും രണ്ടും ആശങ്കയാണ്. ഏത് മെച്ചപ്പെടുത്തലാണ് രണ്ടിനെയും ഏറ്റവും നേരിട്ട് അഭിസംബോധന ചെയ്യുന്നത്?

- A. നയ രേഖ ആദ്യ 1,000 token-ലേക്ക് ചുരുക്കുക.
- B. ജോലിക്ക് ഇണങ്ങുന്നുണ്ടോ എന്ന് നോക്കാതെ ലഭ്യമായ ഏറ്റവും ചെറിയ മോഡലിലേക്ക് മാറുക.
- ✅ **ശരിയുത്തരം: C** — സ്ഥിരമായ ഉള്ളടക്കം ആദ്യം വെച്ച് prompt caching ഓണാക്കുക.
- D. നയ രേഖ ഒരു few-shot ഉദാഹരണ ഭാഗത്തേക്ക് മാറ്റുക.

**C എന്തുകൊണ്ട്?** സ്ഥിരമായ ഉള്ളടക്കം ആദ്യം ക്രമീകരിച്ച് prompt caching ഓണാക്കുന്നത്, ആവർത്തിക്കുന്ന prefix വീണ്ടും ഉപയോഗിക്കാൻ അനുവദിക്കുന്നു — തുടർന്നുള്ള ഓരോ വിളിയിലും ആദ്യ token വരാനുള്ള സമയവും ഓരോ അഭ്യർഥനയുടെയും ചെലവും കുറയ്ക്കുന്നു. ചുരുക്കൽ (A) ആവശ്യമായ നയ ഉള്ളടക്കം നഷ്ടപ്പെടുത്തുന്നു. കണ്ണടച്ച് ചെറുതാക്കൽ (B) ഗുണനിലവാരം മോശമാക്കാനുള്ള അപകടമുണ്ടാക്കുന്നു. Few-shot-ലേക്ക് മാറ്റുന്നത് (D) cache ചെയ്യാവുന്ന, വീണ്ടും ഉപയോഗിക്കാവുന്ന ഒരു prefix ഉണ്ടാക്കുന്നില്ല, പ്രധാന പ്രശ്നം പരിഹരിക്കുന്നുമില്ല.

## മാതൃക 3 · ഡൊമെയ്ൻ 4 — വിലയിരുത്തലും ഒപ്റ്റിമൈസേഷനും

> **📝️ പരീക്ഷാ ശ്രദ്ധ:** "ഉറപ്പോടെയുള്ള പക്ഷേ തെറ്റായ" നിർണയ മാതൃകയാണ് ഇത് പരിശോധിക്കുന്നത് — മോഡലിനെ സംശയിക്കുന്നതിനു പകരം, ഒരു ലക്ഷണത്തെയും അടുത്തിടെയുള്ള ഒരു മാറ്റത്തെയും (രേഖാ പുതുക്കൽ) ഏറ്റവും സാധ്യതയുള്ള മൂലകാരണവുമായി (retrieval) ചേർക്കൽ.

ഒരു രേഖാ പുതുക്കലിനു ശേഷം ഒരു RAG സിസ്റ്റം പെട്ടെന്ന് ഉറപ്പോടെയുള്ള പക്ഷേ തെറ്റായ ഉത്തരങ്ങൾ നൽകുന്നു, അതേസമയം latency-യും മോഡൽ version-ഉം മാറിയിട്ടില്ല. ആദ്യം അന്വേഷിക്കേണ്ട ഏറ്റവും സാധ്യതയുള്ള സ്ഥലം ഏതാണ്?

- A. മോഡൽ weight-കൾ നിശ്ശബ്ദമായി മാറി.
- ✅ **ശരിയുത്തരം: B** — retrieval/indexing ഘട്ടം പ്രസക്തമല്ലാത്തതോ പഴഞ്ചനോ ആയ ഭാഗങ്ങൾ നൽകുന്നു.
- C. Temperature ക്രമീകരണം വളരെ കുറവാണ്.
- D. Context window ചുരുങ്ങി.

**B എന്തുകൊണ്ട്?** ഒരു രേഖാ പുതുക്കലിനു പിന്നാലെ വരുന്ന ഉറപ്പോടെയുള്ള തെറ്റുത്തരങ്ങൾ — മോഡൽ version-ഉം latency-യും മാറാതെ — retrieval മോഡലിന് മോശം context നൽകുന്നതിലേക്ക് നേരിട്ട് ചൂണ്ടുന്നു. തകർന്ന ഒരു re-index-ഓ പൊരുത്തപ്പെടാത്ത embedding-കളോ കൃത്യം ഈ ലക്ഷണം ഉണ്ടാക്കും. A, C, D എന്നിവ ഒരു രേഖാ പുതുക്കൽ സംഭവം കൊണ്ട് പ്രത്യേകമായി ഉണ്ടാകുന്നവയല്ല.
