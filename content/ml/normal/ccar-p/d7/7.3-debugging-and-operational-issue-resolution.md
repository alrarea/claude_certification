## ഡീബഗ്ഗിങ്ങും പ്രവർത്തന പ്രശ്ന പരിഹാരവും

AI അടിസ്ഥാനമാക്കിയ ഒരു സിസ്റ്റം പ്രൊഡക്ഷനിൽ എത്തിക്കഴിഞ്ഞാൽ, "ഡീബഗ്ഗിങ്" പരമ്പരാഗത സോഫ്റ്റ്‌വെയർ ഡീബഗ്ഗിങ്ങിൽ നിന്ന് വ്യത്യസ്തമായി കാണപ്പെടുന്നു. ഒരു വരി നമ്പറിലേക്ക് ചൂണ്ടുന്ന ഒരു stack trace സാധാരണ ഉണ്ടാകില്ല. പകരം, നിങ്ങൾ *പെരുമാറ്റ* പ്രശ്നങ്ങളാണ് നിർണയിക്കുന്നത് — agent എന്തോ തെറ്റ് ചെയ്തു, അല്ലെങ്കിൽ എന്തോ വൈകി, അല്ലെങ്കിൽ എന്തോ ചെലവേറിയതായി — ആഴത്തിൽ പോകും മുൻപ് *സിസ്റ്റത്തിന്റെ ഏത് തട്ടാണ്* ഉത്തരവാദിയെന്ന് വേഗം ചുരുക്കുകയാണ് ഒരു ഓപ്പറേറ്ററുടെ ആദ്യ ജോലി.

### പരാജയത്തെക്കുറിച്ച് ചിന്തിക്കാൻ ഒരു തട്ടുകളായുള്ള വഴി

Claude-ൽ നിർമിച്ച agentic സിസ്റ്റങ്ങൾക്ക് ഒന്നിനുമേൽ ഒന്നായി അടുക്കിയ പല ചലിക്കുന്ന ഭാഗങ്ങളുണ്ട്: മോഡൽ തന്നെ, നിങ്ങൾ അയക്കുന്ന prompt/നിർദേശങ്ങൾ, അത് വിളിക്കുന്ന ടൂളുകൾ, നിങ്ങൾ നൽകുന്ന retrieval അഥവാ context, അടിയിലുള്ള caching/ചെലവ് തട്ട്. മിക്ക പ്രവർത്തന പ്രശ്നങ്ങളും ഇവയിൽ കൃത്യമായി ഒന്നിലെ മാറ്റത്തിലേക്കാണ് നയിക്കുന്നത് — ഏത് ലക്ഷണം ഏത് തട്ടിലേക്ക് ചൂണ്ടുന്നുവെന്ന് അറിയുകയാണ് വൈദഗ്ധ്യം.

### ഓരോ ലക്ഷണത്തിലൂടെയും

**Agent പ്രതീക്ഷിക്കാത്ത ഫലം നൽകുന്നു → prompt version-ഉം മോഡൽ version-ഉം പരിശോധിക്കുക.** ഏറ്റവും സാധാരണമായ ഒറ്റ മൂലകാരണം ഇതാണ്, ഒപ്പം ഏറ്റവും എളുപ്പം വിട്ടുപോകുന്നതും — കാരണം "ഒന്നും മാറിയിട്ടില്ല" എന്നത് അപൂർവമായേ ശരിയാകൂ. ഒന്നുകിൽ prompt template തിരുത്തപ്പെട്ടു (ഒരു ഇടവേളയോ ക്രമ മാറ്റമോ പോലും പെരുമാറ്റം മാറ്റാം), അല്ലെങ്കിൽ അടിസ്ഥാന മോഡൽ പുതുക്കപ്പെട്ടു — ഉറപ്പിച്ച ഒരു മോഡൽ version-നു പകരം ഒരു rolling alias-ലേക്കാണ് ചൂണ്ടുന്നതെങ്കിൽ ചിലപ്പോൾ നിശ്ശബ്ദമായി. കൂടുതൽ അസാധാരണമായ എന്തെങ്കിലും അന്വേഷിക്കും മുൻപ്, നിലവിലെ prompt-നെ അവസാനം ശരിയായിരുന്ന version-മായി താരതമ്യം ചെയ്യുക, ഏത് മോഡൽ version ആണ് ആ അഭ്യർഥന കൈകാര്യം ചെയ്തതെന്ന് ഉറപ്പാക്കുക.

**ടൂൾ വിളി പരാജയങ്ങൾ കൂടുന്നു → ടൂൾ log-കൾ പരിശോധിക്കുക; പുറത്തുള്ള സേവനം പിഴവുകൾ നൽകുന്നുണ്ടോ?** Claude-ന്റെ ടൂൾ വിളി യുക്തി തകരാറിലായതായി തോന്നുമ്പോൾ, കൂടുതൽ സാധാരണമായ കാരണം ടൂൾ തന്നെയാണ് — Claude വിളിക്കുന്ന API, ഡാറ്റാബേസ്, അല്ലെങ്കിൽ സേവനം — അത് മോശമായോ rate-limit ചെയ്യുകയോ അതിന്റെ പ്രതികരണ രൂപം മാറ്റുകയോ ചെയ്തിരിക്കാം. ടൂൾ നൽകുന്നത് Claude വിശ്വസ്തതയോടെ റിപ്പോർട്ട് ചെയ്യുകയോ retry ചെയ്യുകയോ ചെയ്യും, അതിനാൽ മോഡലിന്റെ ടൂൾ തിരഞ്ഞെടുക്കൽ യുക്തി പിന്നോട്ട് പോയെന്ന് കരുതും മുൻപ്, എപ്പോഴും Claude-ന് *താഴെ* — ടൂളിന്റെ സ്വന്തം log-കളിലും പിഴവ് നിരക്കുകളിലും — നോക്കുകയാണ് ആദ്യ നീക്കം.

**Latency വർധന → token എണ്ണം (prompt-കൾ നീളുന്നുണ്ടോ?) പരിശോധിക്കുക, retrieval സമയം അളക്കുക.** ഒരു LLM സിസ്റ്റത്തിലെ പ്രതികരണ സമയം പ്രധാനമായും രണ്ട് കാര്യങ്ങളാണ് നിശ്ചയിക്കുന്നത്: എത്ര token ഉണ്ടാക്കണം/പ്രോസസ്സ് ചെയ്യണം, മോഡലിന് പ്രതികരിക്കാനാകും മുൻപ് ഏതെങ്കിലും retrieval-ഓ ടൂൾ വിളിയോ എത്ര സമയമെടുക്കുന്നു. Latency പിന്നോട്ടുപോക്ക് പലപ്പോഴും വിശദീകരിക്കപ്പെടുന്നത്, മോഡലിലോ infrastructure-ലോ ഉള്ള മാറ്റം കൊണ്ടല്ല, prompt-കൾ നിശ്ശബ്ദമായി വളർന്നതുകൊണ്ടാണ് (കൂടുതൽ context കുത്തിനിറച്ചു, ഒരു RAG ഘട്ടം കൂടുതലോ വലുതോ ആയ ഭാഗങ്ങൾ നൽകുന്നു).

**ചെലവ് പെട്ടെന്ന് കൂടി → cache ചെയ്ത prompt-കൾ ഇപ്പോഴും cache-ൽ എത്തുന്നുണ്ടോ എന്ന് പരിശോധിക്കുക; token എണ്ണം പരിശോധിക്കുക.** പ്രൊഡക്ഷൻ LLM സിസ്റ്റങ്ങളിലെ ചെലവ് ബില്ല് ചെയ്ത token-കളുടെ ഫലമാണ്, വലുതും ആവർത്തിക്കുന്നതുമായ context താങ്ങാവുന്നതാക്കി നിർത്തുന്നത് prompt caching ആണ്. ചെലവ് വർധന പലപ്പോഴും ഉപയോഗ വളർച്ചയേ അല്ല — അതൊരു cache അസാധുവാക്കലാണ്: ഒരു prefix മാറി (ഒരു സമയമുദ്രയോ ക്രമം മാറിയ ഒരു system ഭാഗമോ പോലും), cache യോഗ്യമായ prefix പൊരുത്തപ്പെടാതായി, ഓരോ അഭ്യർഥനയും മുഴുവൻ വിലയുള്ള, cache ചെയ്യാത്ത token ബില്ലിങ്ങിലേക്ക് മടങ്ങി.

### LLM സിസ്റ്റങ്ങളുടെ ഡീബഗ്ഗിങ് vs. പരമ്പരാഗത സോഫ്റ്റ്‌വെയർ

| വശം | പരമ്പരാഗത സോഫ്റ്റ്‌വെയർ ഡീബഗ്ഗിങ് | LLM/agentic സിസ്റ്റം ഡീബഗ്ഗിങ് |
|---|---|---|
| പ്രധാന രേഖ | Stack trace, exception, വരി നമ്പർ | പെരുമാറ്റ രേഖ, prompt/പ്രതികരണ ജോഡി |
| "അതേ ഇൻപുട്ട്, അതേ ഔട്ട്പുട്ട്"? | സാധാരണ ഉവ്വ് (നിശ്ചിതം) | ഉറപ്പില്ല — കോഡിൽ മാറ്റമില്ലാതെ മോഡൽ/version drift പെരുമാറ്റം മാറ്റുന്നു |
| ആദ്യം ചോദിക്കേണ്ട ചോദ്യം | കോഡിൽ എന്ത് മാറി? | Prompt, മോഡൽ version, ടൂളുകൾ, അല്ലെങ്കിൽ എടുത്ത context — ഇവയിൽ എന്ത് മാറി? |
| സാധാരണ അന്ധബിന്ദു | Off-by-one, null pointer | നിശ്ശബ്ദമായ മോഡൽ പുതുക്കൽ, cache അസാധുവാക്കൽ, prompt drift |
| മൂലകാരണ തട്ട് | സാധാരണ ഒരു ഫയൽ/ഫങ്ഷൻ | Prompt, മോഡൽ, ടൂൾ, retrieval, അല്ലെങ്കിൽ cache തട്ട് ആകാം — ഏതെന്ന് വേർതിരിക്കണം |

### ഒരു പ്രവർത്തന ശീലം ഉണ്ടാക്കൽ

ഇവിടെ പരീക്ഷയ്ക്ക് പ്രസക്തമായ ശിക്ഷണം, prompt version-കളെയും മോഡൽ version-കളെയും ഒരു dependency version പോലെ കണക്കാക്കുകയാണ് — അവ ഉറപ്പിക്കുക, ഓരോ അഭ്യർഥനയും ഏതാണ് കൈകാര്യം ചെയ്തതെന്ന് ലോഗ് ചെയ്യുക, പെരുമാറ്റം മാറിയതായി തോന്നുന്ന നിമിഷം അവ താരതമ്യം ചെയ്യുക. Caching-നും അതേ ശിക്ഷണം ബാധകമാണ്: ഒരു cache hit-ന് എന്ത് byte-to-byte ഒരുപോലെ നിൽക്കണമെന്ന് കൃത്യമായി അറിയുക, cache-hit നിരക്കിനെ പിന്നീട് ചിന്തിക്കാനുള്ള കാര്യമായല്ല, ഒന്നാം കിട പ്രവർത്തന അളവായി നിരീക്ഷിക്കുക.

> **🌍️ യഥാർഥ ഉദാഹരണം:** ഒരു സപ്പോർട്ട്-ടിക്കറ്റ് triage agent രാത്രിക്ക് രാത്രി വിചിത്രമായ രൂപത്തിലുള്ള പ്രതികരണങ്ങൾ നൽകിത്തുടങ്ങുന്നു, agent-ന്റെ പാഴ്‌സിങ് കോഡിലെ ഒരു ബഗ് സംശയിക്കാനാണ് on-call എൻജിനീയറുടെ ആദ്യ തോന്നൽ. അഭ്യർഥനാ log-കൾ പെട്ടെന്ന് പരിശോധിച്ചപ്പോൾ, ഉപയോഗിച്ചിരുന്ന മോഡൽ alias ഒരു ഉറപ്പിച്ച version-നു പകരം "latest"-ലേക്കാണ് ചൂണ്ടിയിരുന്നതെന്നും കുറച്ച് മണിക്കൂർ മുൻപ് ഒരു പതിവ് മോഡൽ പുതുക്കൽ വന്നിരുന്നെന്നും കാണുന്നു — prompt ഒരിക്കലും സ്പർശിച്ചിരുന്നില്ല, മോഡൽ version ആയിരുന്നു യഥാർഥ മൂലകാരണം. ടീമിന്റെ പരിഹാരം ഉടനടിയുള്ളതും (ഒരു പ്രത്യേക മോഡൽ version-ലേക്ക് ഉറപ്പിക്കുക) ഘടനാപരവുമാണ് (ഇനി മുതൽ ലോഗ് ചെയ്യുന്ന ഓരോ അഭ്യർഥനയിലും മോഡൽ version ചേർക്കുക, പ്രതീക്ഷിക്കാത്ത version മാറ്റങ്ങളിൽ മുന്നറിയിപ്പ് നൽകുക).
