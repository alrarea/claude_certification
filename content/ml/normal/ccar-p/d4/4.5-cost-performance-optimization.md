## ചെലവ്-പ്രകടന ഒപ്റ്റിമൈസേഷൻ

Claude അടിസ്ഥാനമാക്കിയ ഓരോ സിസ്റ്റവും ഒടുവിൽ അതേ വലിവ് നേരിടുന്നു: അത് മെച്ചപ്പെടുത്തുന്നത് (കൂടുതൽ കൃത്യം, കൂടുതൽ ശേഷി) സാധാരണ ചെലവേറിയതും വൈകുന്നതുമാക്കുന്നു, അതേസമയം വിലകുറയ്ക്കുന്നത് ഗുണനിലവാരത്തെ അപകടത്തിലാക്കുന്നു. എല്ലാം കണ്ണടച്ച് താഴ്ത്തുന്നതിനു പകരം *ശരിയായ* ഉപാധികൾ — ഗുണനിലവാരത്തെ ഏറ്റവും കുറച്ച് ബാധിച്ച് ചെലവോ latency-യോ കുറയ്ക്കുന്നവ — ഉപയോഗിക്കുന്ന ശിക്ഷണമാണ് ചെലവ്-പ്രകടന ഒപ്റ്റിമൈസേഷൻ.

### ഉപാധികളിലൂടെ

- **Prompt caching** വിളികൾക്കിടയിൽ മാറാത്ത ഉള്ളടക്കം വീണ്ടും പ്രോസസ്സ് ചെയ്യുന്നത് ഒഴിവാക്കാൻ അനുവദിക്കുന്നു — ഒരു സ്ഥിര system prompt, ഒരു വലിയ റഫറൻസ് രേഖ, അല്ലെങ്കിൽ few-shot ഉദാഹരണങ്ങൾ. ആ ഉള്ളടക്കം ഓരോ അഭ്യർഥനയിലും വീണ്ടും പ്രോസസ്സ് ചെയ്യാതെ cache ചെയ്യുന്നതിനാൽ, വലിയ അളവിലുള്ള, ആവർത്തിക്കുന്ന context-ഉള്ള ജോലികളിൽ cache ചെയ്ത ഭാഗത്ത് 50%-ൽ അധികം ചെലവ് ലാഭം കാണാം. ഉള്ളടക്കം തന്നെ മാറാത്തതിനാൽ ഗുണനിലവാര അപകടത്തിന്റെ കാര്യത്തിൽ ഈ ഉപാധി ഏതാണ്ട് "സൗജന്യ"മാണ് — *എന്ത്* പ്രോസസ്സ് ചെയ്യുന്നു എന്നതല്ല, *എങ്ങനെ* പ്രോസസ്സ് ചെയ്യുന്നു എന്നതാണ് നിങ്ങൾ മെച്ചപ്പെടുത്തുന്നത്.
- **മോഡൽ ചെറുതാക്കൽ** എന്നാൽ ലളിതമായ ജോലികൾ (തരംതിരിക്കൽ, ചെറിയ extraction, രൂപീകരണം) ചെറുതും വിലകുറഞ്ഞതും വേഗമുള്ളതുമായ ഒരു മോഡലിലേക്ക് അയക്കുകയും, ആഴത്തിലുള്ള ന്യായവാദം ശരിക്കും വേണ്ട ജോലികൾക്കായി ഏറ്റവും ശേഷിയുള്ള മോഡൽ മാറ്റിവെക്കുകയും ചെയ്യുന്നു. ജാഗ്രത കൊണ്ട് എല്ലായിടത്തും ഏറ്റവും വലിയ മോഡൽ ഉപയോഗിക്കുന്നതിനു പകരം, നിങ്ങളുടെ pipeline-ലെ ഏതൊക്കെ ജോലികൾക്ക് ശരിക്കും ഏറ്റവും ശക്തമായ മോഡൽ വേണമെന്ന് അറിയണം — ഒരു ജോലി-സങ്കീർണതാ പരിശോധന.
- **Batch API** അടിയന്തരമല്ലാത്ത, ഇടപെടലില്ലാത്ത ജോലികൾക്കാണ് (വൻതോതിലുള്ള സംഗ്രഹം, offline വിശകലനം, ഡാറ്റാസെറ്റ് നിർമാണം), അവിടെ ഏകദേശം പകുതി ചെലവിന് പകരം ഒരു കാലതാമസം സഹിക്കാം. ഈ ഉപാധി ചെലവിനുവേണ്ടി latency വിട്ടുകൊടുക്കുന്നു, ഒരു ഉപയോക്താവ് ഒരേസമയം പ്രതികരണത്തിനായി കാത്തിരിക്കാത്തിടത്ത് മാത്രം ബാധകമാണ്.
- **കുറഞ്ഞ ഭാഗങ്ങൾ എടുക്കൽ** ഓരോ വിളിയിലും മോഡലിന് അയക്കുന്ന context window ചുരുക്കുന്നു. അയഞ്ഞ ബന്ധമുള്ള 10 ഭാഗങ്ങൾക്കു പകരം വളരെ പ്രസക്തമായ 3 ഭാഗങ്ങൾ എടുക്കുന്നത് ചെലവും (കുറഞ്ഞ ഇൻപുട്ട് token) latency-യും (പ്രോസസ്സ് ചെയ്യാൻ കുറവ്) കുറയ്ക്കുന്നു — ചിലപ്പോൾ കൃത്യത *മെച്ചപ്പെടുത്തുക*പോലും ചെയ്യാം, കാരണം പ്രസക്തമല്ലാത്ത ഭാഗങ്ങൾ ആശയക്കുഴപ്പമുള്ളതോ നേർപ്പിച്ചതോ ആയ ഉത്തരങ്ങളുടെ സാധാരണ ഉറവിടമാണ്. അപകടം വേണ്ടത്ര എടുക്കാതെ ആവശ്യമായ context നഷ്ടപ്പെടുത്തലാണ്, അതിനാൽ ഈ ഉപാധി കണ്ണടച്ച് വെക്കാതെ ഒരു വിലയിരുത്തൽ ഡാറ്റാസെറ്റുമായി ഒത്തുനോക്കി ക്രമീകരിക്കണം.
- **`max_tokens` ക്രമീകരണം** ജോലിക്ക് ശരിക്കും വേണ്ടതിലേക്ക് ഔട്ട്പുട്ടിന്റെ നീളം പരിമിതപ്പെടുത്തുന്നു, മൂല്യം ചേർക്കാതെ token ചെലവാക്കുന്ന വിധത്തിൽ മോഡൽ അമിതമായി ഉണ്ടാക്കുന്നത് (വളച്ചുകെട്ടൽ, ആവർത്തനം, നിറയ്ക്കൽ) തടയുന്നു.

### ഒപ്റ്റിമൈസേഷന്റെ രണ്ട് സമീപനങ്ങൾ

| സമീപനം | തന്ത്രം | അപകട സ്വഭാവം |
|---|---|---|
| എല്ലാം ഒരുപോലെ താഴ്ത്തൽ | ചെലവ് വിശാലമായി കുറയ്ക്കുക — എല്ലായിടത്തും ചെറിയ മോഡലോ കുറഞ്ഞ context-ഓ | വേഗം നടപ്പാക്കാം, പക്ഷേ ശക്തമായ ക്രമീകരണം ശരിക്കും വേണ്ടിയിരുന്ന ജോലികളിൽ ഗുണനിലവാരം പിന്നോട്ട് പോകാനുള്ള അപകടം |
| ലക്ഷ്യമിട്ട ഉപാധി തിരഞ്ഞെടുക്കൽ | ഓരോ ഉപാധിയും ഇണങ്ങുന്നിടത്ത് മാത്രം പ്രയോഗിക്കുക (സ്ഥിരമായത് cache ചെയ്യുക, ലളിത ഉപജോലികൾ മാത്രം ചെറുതാക്കുക, അടിയന്തരമല്ലാത്ത ജോലികൾ മാത്രം batch ചെയ്യുക) | മുൻകൂട്ടി കൂടുതൽ വിശകലനം വേണം, പക്ഷേ ലാഭത്തിന്റെ ഭൂരിഭാഗവും നേടിക്കൊണ്ട് പ്രധാനപ്പെട്ടിടത്ത് ഗുണനിലവാരം നിലനിർത്തുന്നു |

Architect-മാർ ഇഷ്ടപ്പെടുന്നത് ലക്ഷ്യമിട്ട സമീപനമാണ്: മുകളിലെ ഓരോ ഉപാധിയും ഒരു *പ്രത്യേക* തരം പാഴാക്കലിനെ (ആവർത്തിച്ചുള്ള പ്രോസസ്സിങ്, അമിത വലുപ്പമുള്ള മോഡൽ, ഒരേസമയ API ഉപയോഗം മാത്രം, അധിക context, അതിരില്ലാത്ത ഔട്ട്പുട്ട്) അഭിസംബോധന ചെയ്യുന്നു, എല്ലാവർക്കും ഒരേ അളവിലുള്ള മുരടൻ ചെലവ് വെട്ടിക്കുറയ്ക്കലല്ല. ഇങ്ങനെ ചെയ്യുന്ന ഓരോ മാറ്റവും A/B testing പ്രക്രിയ വഴി സാധൂകരിക്കണം — കടലാസിൽ മാത്രമല്ല, വിലയിരുത്തൽ ഡാറ്റാസെറ്റിൽ നിങ്ങളുടെ കൃത്യതാ അളവിനെതിരെ നിലനിന്നാൽ മാത്രമേ ഒരു "വിലകുറഞ്ഞ" മാറ്റം ഒരു നേട്ടമാകൂ.

> **🌍️ യഥാർഥ ഉദാഹരണം:** ഒരു രേഖാ-QA സിസ്റ്റം ഓരോ ചോദ്യത്തിനും ഏറ്റവും മുകളിലെ 10 ഭാഗങ്ങൾ എടുക്കുകയും, ലളിതമായ അന്വേഷണങ്ങൾ ഉൾപ്പെടെ ഓരോ അഭ്യർഥനയ്ക്കും ഏറ്റവും ശേഷിയുള്ള മോഡൽ ഉപയോഗിക്കുകയും, ഓരോ വിളിയിലും ഒരുപോലുള്ള പല പേജുള്ള system prompt വീണ്ടും അയക്കുകയും ചെയ്തിരുന്നു. സ്ഥിരമായ system prompt-ന് prompt caching ഓണാക്കി, ലളിതമായ അന്വേഷണ ചോദ്യങ്ങൾ ഒരു ചെറിയ മോഡലിലേക്ക് അയച്ച്, retrieval ഏറ്റവും മുകളിലെ 3 ഭാഗങ്ങളാക്കി ചുരുക്കിയതോടെ (കൃത്യത നിലനിൽക്കുന്നുവെന്ന് A/B ടെസ്റ്റ് വഴി ഉറപ്പാക്കി), ടീം ഓരോ അഭ്യർഥനയുടെയും ചെലവ് പകുതിയിലധികം കുറയ്ക്കുകയും latency ശ്രദ്ധേയമായി കുറയ്ക്കുകയും ചെയ്തു — മുഴുവൻ ശക്തിയുള്ള മോഡലും മുഴുവൻ context-ഉം ഇപ്പോഴും വേണ്ടിയിരുന്ന കൂടുതൽ ബുദ്ധിമുട്ടുള്ള ന്യായവാദ ചോദ്യങ്ങളെ സ്പർശിക്കാതെ.
