# പെട്ടെന്നുള്ള റഫറൻസും ആവർത്തന ചെക്ക്‌ലിസ്റ്റും (In-Depth)

പരീക്ഷ മുഴുവനും വേഗം നോക്കാനുള്ള റഫറൻസാണ് ഈ പേജ്. താഴെയുള്ള ഓരോ പ്രധാന വിഭാഗവും യഥാർഥ ചെക്ക്‌ലിസ്റ്റ് അതേപടി നിലനിർത്തുന്നു, ഒപ്പം ആ വിഭാഗം എന്തുകൊണ്ട് പ്രധാനമാണെന്ന് വിശദീകരിക്കുന്ന ഒരു ചെറിയ ഖണ്ഡികയും.

പരീക്ഷയ്ക്ക് കയറുമ്പോൾ നിങ്ങളുടെ വേഗതയും വിജയ പരിധിയും നിശ്ചയിക്കുന്ന സംഖ്യകൾ ഇവയാണ്: 120 മിനിറ്റിൽ 63 ചോദ്യങ്ങൾ എന്നത് ഓരോ ചോദ്യത്തിനും ശരാശരി രണ്ട് മിനിറ്റിൽ താഴെയാണ്, 720/1000 എന്ന വിജയ സ്കോർ അർഥമാക്കുന്നത് കുറച്ച് തെറ്റുകൾക്ക് ഇടമുണ്ടെന്നാണ് — കുറ്റമറ്റ ഒരു പ്രകടനം ആവശ്യമില്ല.

## ഈ പരീക്ഷയ്ക്കുള്ള 12 പ്രധാന നിയമങ്ങൾ

പരീക്ഷ മുഴുവനിലും ഏറ്റവും ഫലപ്രദവും ഏറ്റവുമധികം പരിശോധിക്കപ്പെടുന്നതുമായ മാതൃകകളാണ് ഈ പന്ത്രണ്ട് നിയമങ്ങൾ. മറ്റൊന്നും ഓർമയില്ലെങ്കിലും ഇവ ഓർക്കുക — ഓരോന്നും ആവർത്തിക്കുന്ന ഒരു ചോദ്യ മാതൃകയുമായി നേരിട്ട് ചേരുന്നു (ഔദ്യോഗിക മാതൃകാ ചോദ്യങ്ങളിൽ കാണുന്നതുപോലെ):

- Least privilege = role-ന് വേണ്ടാത്ത ടൂളുകൾ നീക്കുക. ലോഗിങ്ങും സ്ഥിരീകരണ ചോദ്യങ്ങളും മതിയാകില്ല.
- Prompt caching = സ്ഥിരമായ ഉള്ളടക്കം ആദ്യം, മാറുന്ന ഉള്ളടക്കം അവസാനം. ഇത് ചെലവും latency-യും ലാഭിക്കുന്നു.
- രേഖാ പുതുക്കലിനു ശേഷമുള്ള RAG പിഴവുകൾ = മോഡലല്ല, ആദ്യം re-indexing ഘട്ടം പരിശോധിക്കുക.
- A/B testing = ഒരു സമയത്ത് ഒരു ഘടകം മാത്രം മാറ്റുക. എപ്പോഴും ഒരേ വിലയിരുത്തൽ ഡാറ്റാസെറ്റിൽ താരതമ്യം ചെയ്യുക.
- GDPR-ന്റെ പ്രധാന തത്വങ്ങൾ: ഡാറ്റ കുറയ്ക്കൽ, ഉദ്ദേശ്യ പരിമിതി, മായ്ക്കാനുള്ള അവകാശം, സുതാര്യത.
- HIPAA = ആരോഗ്യ ഡാറ്റ; എൻക്രിപ്ഷൻ, audit log-കൾ, പ്രവേശന നിയന്ത്രണം, ചോർച്ച അറിയിക്കൽ എന്നിവ വേണം.
- Human-in-the-loop = വലിയ അപകടസാധ്യതയുള്ള, തിരിച്ചെടുക്കാനാകാത്ത നടപടികൾക്ക് approval gate; സൂക്ഷ്മമായ ഉള്ളടക്കത്തിന് review queue.
- SLA രൂപകൽപ്പന മോഡൽ തിരഞ്ഞെടുപ്പിനെ നയിക്കുന്നു: latency SLA → ചെറിയ മോഡൽ + caching; കൃത്യതാ SLA → വലിയ മോഡൽ + RAG.
- Observability: ഓരോ അഭ്യർഥന/പ്രതികരണവും + token എണ്ണവും + latency-യും + retrieval ഫലങ്ങളും ലോഗ് ചെയ്യുക.
- ഉറപ്പോടെയുള്ള പക്ഷേ തെറ്റായ ഉത്തരങ്ങൾ = retrieval പ്രശ്നം (തെറ്റായ ഭാഗങ്ങൾ), മോഡലിന്റെ പ്രശ്നമല്ല.
- Hybrid retrieval (അർഥാധിഷ്ഠിതം + keyword) മിക്ക പ്രൊഡക്ഷൻ സിസ്റ്റങ്ങളിലും ഏതൊന്നിനെക്കാളും മെച്ചം.
- പങ്കാളികളുമായുള്ള ആശയവിനിമയം: വിട്ടുവീഴ്ചാ തീരുമാനങ്ങൾ എപ്പോഴും സാങ്കേതിക ഇഷ്ടവുമായല്ല, ബിസിനസ് മൂല്യവുമായി ബന്ധിപ്പിക്കുക.

ഈ നിയമങ്ങൾ പ്രധാനമാണ്, കാരണം അവ പരീക്ഷയുടെ പ്രധാന "കെണി" സാഹചര്യങ്ങളെ പ്രതിനിധീകരിക്കുന്നു — അന്തർജ്ഞാനപരമായ പക്ഷേ തെറ്റായ ഒരു ഉത്തരം (ലോഗിങ് ചേർക്കുക, മോഡലിനെ കുറ്റപ്പെടുത്തുക, വലിയ മോഡൽ ഉപയോഗിക്കുക) ശരിയായ, കൂടുതൽ അച്ചടക്കമുള്ള ഉത്തരത്തിനൊപ്പം നൽകുന്ന സാഹചര്യങ്ങൾ.

## ഡൊമെയ്ൻ ആവർത്തന ചെക്ക്‌ലിസ്റ്റ്

പരീക്ഷാ ദിവസത്തിനു മുൻപ് ഒരു സ്വയം വിലയിരുത്തലായി ഇത് ഉപയോഗിക്കുക — ഓരോ ഇനവും സത്യസന്ധമായി അടയാളപ്പെടുത്താൻ നിങ്ങൾക്ക് കഴിയണം. ഡൊമെയ്ൻ അനുസരിച്ച് ക്രമീകരിച്ചിരിക്കുന്നതിനാൽ, നിങ്ങളുടെ ദുർബല മേഖലകൾ ഒറ്റനോട്ടത്തിൽ കാണാം — ഓരോ ഡൊമെയ്നും സ്കോറിൽ എത്ര തൂക്കമുണ്ടെന്നതിനൊപ്പം.

#### D1 — Solution Design (17%)

- ഒരു ബിസിനസ് പ്രശ്നത്തിന് ശരിയായ architectural pattern എനിക്ക് കണ്ടെത്താനാകും
- 5 ബിസിനസ് മൂല്യ സ്തംഭങ്ങൾ എനിക്ക് അറിയാം, ഒരു use case അവയുമായി ബന്ധിപ്പിക്കാനാകും
- ഒരു സങ്കീർണ ജോലിക്ക് ഒരു multi-agent സിസ്റ്റം topology എനിക്ക് രൂപകൽപ്പന ചെയ്യാനാകും
- വിഭജന തന്ത്രങ്ങൾ ഞാൻ മനസ്സിലാക്കുന്നു: functional, data, domain
- മുഴുവൻ input→processing→output→feedback loop-ഉം എനിക്ക് രൂപകൽപ്പന ചെയ്യാനാകും

#### D2 — Models, Prompting & Context (13%)

- മോഡലിന്റെ വലുപ്പങ്ങൾക്കിടയിലെ വിട്ടുവീഴ്ചകൾ എനിക്ക് അറിയാം: വേഗത vs. കൃത്യത vs. ചെലവ്
- Zero-shot, few-shot, chain-of-thought എന്നിവയും ഏതെപ്പോൾ ഉപയോഗിക്കണമെന്നും എനിക്ക് അറിയാം
- Prompt caching ഞാൻ മനസ്സിലാക്കുന്നു: സ്ഥിരം ആദ്യം, മാറുന്നത് അവസാനം
- Context window മാനേജ്മെന്റ് തന്ത്രങ്ങളും അവയുടെ വിട്ടുവീഴ്ചകളും എനിക്ക് അറിയാം
- Role, അതിരുകൾ, രൂപം, guardrail-കൾ എന്നിവയുള്ള ഒരു system prompt എനിക്ക് രൂപകൽപ്പന ചെയ്യാനാകും

#### D3 — Integration (19%)

ഇതാണ് ഏറ്റവും വലിയ ഡൊമെയ്ൻ, അതിനാൽ ഇവിടെ ദുർബലമായ ഒരു ചെക്ക്‌ലിസ്റ്റ് ഏറ്റവുമധികം നഷ്ടമുണ്ടാക്കുന്നു:

- MCP, നേരിട്ടുള്ള API, agent-to-agent സംയോജനം എന്നിവയിൽ ഏതെപ്പോൾ ഉപയോഗിക്കണമെന്ന് എനിക്ക് അറിയാം
- ഒരു പൂർണ RAG pipeline എനിക്ക് രൂപകൽപ്പന ചെയ്യാനാകും (ingest → chunk → embed → index → retrieve → generate)
- Chunking തന്ത്രങ്ങളും ഏതെപ്പോൾ ഉപയോഗിക്കണമെന്നും എനിക്ക് അറിയാം
- Retrieval തന്ത്രങ്ങൾ എനിക്ക് അറിയാം: അർഥാധിഷ്ഠിതം, keyword, hybrid, re-ranking
- Least privilege ഞാൻ മനസ്സിലാക്കുന്നു, ടൂൾ/agent ക്രമീകരണത്തിൽ അത് പ്രയോഗിക്കാനാകും
- ഒരു പ്രൊഡക്ഷൻ AI സിസ്റ്റത്തിൽ observability എങ്ങനെയിരിക്കുമെന്ന് എനിക്ക് അറിയാം
- കൃത്യത-latency-ചെലവ് വിട്ടുവീഴ്ചകൾ ഞാൻ മനസ്സിലാക്കുന്നു, തീരുമാനങ്ങൾ ന്യായീകരിക്കാനാകും

#### D4 — വിലയിരുത്തൽ (16%)

- പ്രധാന വിലയിരുത്തൽ അളവുകൾ എനിക്ക് അറിയാം: കൃത്യത, latency, ചെലവ്, സുരക്ഷ, hallucination നിരക്ക്
- അതിർത്തി സാഹചര്യങ്ങളും യഥാർഥ ഉത്തരങ്ങളുമുള്ള ഒരു വിലയിരുത്തൽ ഡാറ്റാസെറ്റ് എനിക്ക് രൂപകൽപ്പന ചെയ്യാനാകും
- A/B testing പ്രക്രിയയും ഫലങ്ങൾ എപ്പോൾ സ്ഥിതിവിവരപരമായി അർഥവത്താകുന്നുവെന്നും ഞാൻ മനസ്സിലാക്കുന്നു
- ലക്ഷണങ്ങളിൽ നിന്ന് സിസ്റ്റം പ്രശ്നങ്ങൾ എനിക്ക് നിർണയിക്കാനാകും (ഉറപ്പോടെയുള്ള തെറ്റുത്തരങ്ങൾ → retrieval)
- ചെലവ് കുറയ്ക്കാനുള്ള ഉപാധികൾ എനിക്ക് അറിയാം: caching, മോഡലിന്റെ വലുപ്പം, batch API, max_tokens

#### D5 — ഗവേണൻസ് (14%)

- GDPR, HIPAA, FedRAMP എന്നിവയുടെ പ്രധാന ആവശ്യങ്ങൾ എനിക്ക് അറിയാം
- Guardrail-കൾ എനിക്ക് രൂപകൽപ്പന ചെയ്യാനാകും: input validation, output filtering, PreToolUse hooks
- HITL രീതികൾ എനിക്ക് അറിയാം: approval gate, review queue, escalation trigger
- Bias, fairness, transparency എന്നിവയും അവയ്ക്കായി എങ്ങനെ പരിശോധിക്കാമെന്നും ഞാൻ മനസ്സിലാക്കുന്നു
- AI പരാജയ രീതികൾ എനിക്ക് തിരിച്ചറിയാനാകും: hallucination, injection, ഡാറ്റ ചോർച്ച, model drift

#### D6 — പങ്കാളികൾ (14%)

- Structured discovery നടത്താനും വിജയ മാനദണ്ഡങ്ങൾ നിർവചിക്കാനും എനിക്ക് കഴിയും
- സാങ്കേതികരല്ലാത്ത പങ്കാളികളോട് architecture വിട്ടുവീഴ്ചകൾ എനിക്ക് അവതരിപ്പിക്കാനാകും
- SLA-കൾ എങ്ങനെ രൂപകൽപ്പന ചെയ്യാമെന്നും അവ ഏതൊക്കെ architecture തിരഞ്ഞെടുപ്പുകളെ നയിക്കുന്നുവെന്നും എനിക്ക് അറിയാം
- മുഴുവൻ ജീവിതചക്രവും ഞാൻ മനസ്സിലാക്കുന്നു: discovery → design → handoff → monitoring → iteration

#### D7 — ഡെവലപ്പർ പ്രൊഡക്ടിവിറ്റി (7%)

ഏറ്റവും ചെറിയ ഡൊമെയ്ൻ — അതിന്റെ തൂക്കത്തിന് ആനുപാതികമായി ഒരു പെട്ടെന്നുള്ള ആവർത്തനം മതി:

- Claude Code config ശ്രേണി എനിക്ക് അറിയാം (Foundations-ൽ നിന്ന് ആവർത്തിക്കുക)
- ടീം തല workflow-കൾ എനിക്ക് വിവരിക്കാനാകും: slash commands, CI/CD സംയോജനം
- ലക്ഷണങ്ങളിൽ നിന്ന് സാധാരണ പ്രവർത്തന പ്രശ്നങ്ങൾ എനിക്ക് നിർണയിക്കാനാകും

## എങ്ങനെ തയ്യാറെടുക്കാം — ഔദ്യോഗിക മാർഗനിർദേശം

| പ്രവർത്തനം | എന്തുകൊണ്ട് പ്രധാനം |
|---|---|
| പരീക്ഷാ blueprint പഠിക്കുക (PDF-ന്റെ വിഭാഗം 6) | ഓരോ ചോദ്യവും ഈ ലക്ഷ്യങ്ങൾക്കെതിരെയാണ് എഴുതിയിരിക്കുന്നത് — ഇതാണ് നിങ്ങളുടെ സിലബസ് |
| RAG-ഉം വിലയിരുത്തലുമുള്ള തുടക്കം മുതൽ ഒടുക്കം വരെയുള്ള ഒരു Claude സൊല്യൂഷൻ ഉണ്ടാക്കുക | പരീക്ഷ പരിശോധിക്കുന്ന വിട്ടുവീഴ്ചകൾ മനസ്സിലാക്കാനുള്ള ഏറ്റവും നല്ല വഴി നേരിട്ടുള്ള പരിചയമാണ് |
| ഔദ്യോഗിക Anthropic രേഖകൾ വായിക്കുക | Claude API, മോഡലുകൾ, prompt engineering, MCP, Skills രേഖകൾ |
| Architecture തീരുമാനങ്ങൾ എടുക്കാൻ പരിശീലിക്കുക | മോഡൽ തിരഞ്ഞെടുക്കൽ, സംയോജന പ്രോട്ടോക്കോളുകൾ, സുരക്ഷാ വിട്ടുവീഴ്ചകൾ |
| പരീക്ഷാ ഗൈഡിലെ മാതൃകാ ചോദ്യങ്ങൾ പൂർത്തിയാക്കുക | ചോദ്യങ്ങളുടെ ശൈലിയും പ്രതീക്ഷിക്കുന്ന ചിന്താ നിലവാരവും മനസ്സിലാക്കുക |

ഈ മാർഗനിർദേശം നിലനിൽക്കുന്നത്, പരീക്ഷ ഓർമശക്തി അധിഷ്ഠിതമല്ല സാഹചര്യ അധിഷ്ഠിതമായതുകൊണ്ടാണ് — രേഖകൾ വായിക്കുക മാത്രം ചെയ്താൽ ആളുകൾക്ക് പദങ്ങൾ നിർവചിക്കാനാകും, പക്ഷേ പരീക്ഷാ സാഹചര്യത്തിൽ അവ പ്രയോഗിക്കാനാകില്ല; അതുകൊണ്ടാണ് വായനയ്ക്കൊപ്പം നേരിട്ടുള്ള നിർമാണവും തീരുമാനങ്ങൾ പരിശീലിക്കലും വ്യക്തമായി ശുപാർശ ചെയ്യുന്നത്.
