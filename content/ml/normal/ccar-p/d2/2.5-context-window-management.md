## Context Window മാനേജ്മെന്റ്

ഓരോ മോഡലിനും ഒരു പരിമിതമായ context window ഉണ്ട് — ഒരൊറ്റ വിളിയിൽ എത്ര token സംഭാഷണ ചരിത്രവും രേഖകളും നിർദേശങ്ങളും ഉണ്ടാകാം എന്നതിന്റെ കർശന പരിധി. സംഭാഷണങ്ങൾ നീളുകയോ ജോലികൾ കൂടുതൽ റഫറൻസ് സാമഗ്രികൾ ഉൾക്കൊള്ളുകയോ ചെയ്യുമ്പോൾ, മോഡലിന്റെ "കാഴ്ചയിൽ" എന്ത് നിൽക്കണമെന്ന് architect സജീവമായി കൈകാര്യം ചെയ്യണം, കാരണം രേഖ അനിയന്ത്രിതമായി വളരാൻ വിട്ടാൽ ഒടുവിൽ പരിധിയിൽ ഇടിക്കുകയോ, സംഭാഷണത്തിന്റെ തുടക്കത്തിലെ ബഹളത്തിൽ യഥാർഥത്തിൽ പ്രസക്തമായ ഉള്ളടക്കം മുങ്ങിപ്പോകുകയോ ചെയ്യും. എന്ത് സൂക്ഷിക്കണം, എന്ത് ചുരുക്കണം, എന്ത് prompt-ന് പുറത്തേക്ക് മാറ്റണം, എന്ത് ആവശ്യമുള്ളപ്പോൾ മാത്രം ലോഡ് ചെയ്യണം എന്ന് തീരുമാനിക്കുന്ന ശിക്ഷണമാണ് context window മാനേജ്മെന്റ്.

### നാല് പ്രധാന തന്ത്രങ്ങൾ

**Progressive summarisation** ഒരു സംഭാഷണത്തിലെ പഴയ turn-കൾക്ക് പകരം ഒരു ചുരുക്ക സംഗ്രഹം വെക്കുന്നു, മുൻപുള്ളതിന്റെ സാരം നിലനിർത്തിക്കൊണ്ട് പുതിയ ഉള്ളടക്കത്തിന് ഇടമുണ്ടാക്കുന്നു. നടപ്പാക്കാൻ ലളിതമാണ്, പക്ഷേ നഷ്ടമുണ്ടാക്കുന്നതാണ് — തുടക്ക turn-കളിലെ കൃത്യമായ വാക്കുകൾ, കൃത്യമായ സംഖ്യകൾ, സൂക്ഷ്മമായ ഭാഷ എന്നിവ ചുരുക്കലിൽ നഷ്ടപ്പെടാം; പിന്നീടൊരു turn-ന് അവ കൃത്യമായി വേണ്ടിവന്നാൽ ഇത് പ്രധാനമാണ്.

**External memory** വിശദാംശങ്ങൾ prompt-ൽ നിന്ന് പൂർണമായി എടുത്തുമാറ്റി ഒരു ഡാറ്റാബേസിലോ മറ്റ് സ്ഥിര സംഭരണിയിലോ വെക്കുന്നു, നിലവിലെ turn-ന് പ്രസക്തമായ ഭാഗങ്ങൾ മാത്രം എടുക്കുന്നു (retrieval-augmented generation-നു പിന്നിലെ അതേ ആശയം). എല്ലാം context-ൽ സൂക്ഷിക്കുന്നതിനെക്കാൾ ഇത് വളരെ നന്നായി വളരുന്നു, പക്ഷേ retrieval latency-യും ഒരു പുതിയ പരാജയ രീതിയും കൊണ്ടുവരുന്നു: തെറ്റായതോ അപൂർണമോ ആയ വിവരം എടുക്കൽ.

**Modular prompts / Skills** system prompt-നെ തന്നെ വെവ്വേറെ ലോഡ് ചെയ്യാവുന്ന ഭാഗങ്ങളായി ഘടനപ്പെടുത്തുന്നു, അങ്ങനെ സാധ്യമായ എല്ലാ സാഹചര്യവും ഉൾക്കൊള്ളുന്ന ഒരൊറ്റ വലിയ prompt-നു പകരം നിലവിലെ ജോലിക്ക് പ്രസക്തമായ നിർദേശങ്ങൾ മാത്രം ഉൾപ്പെടുന്നു. ഇത് ഓരോ വിളിയും ലളിതമായി നിർത്തുന്നു, പക്ഷേ ശരിയായ module ശരിയായ സമയത്ത് തിരഞ്ഞെടുക്കപ്പെടാൻ prompt ഉള്ളടക്കം ക്രമീകരിക്കുന്നതിലും അടയാളപ്പെടുത്തുന്നതിലും architect മുൻകൂട്ടി യഥാർഥ ജോലി ചെയ്യണം.

**Prompt caching** — ചെലവിനും latency-ക്കുമുള്ള ഒരു രീതിയായി പറഞ്ഞത് — ഒരു context തന്ത്രമായും പ്രവർത്തിക്കുന്നു: വിളികൾക്കിടയിൽ ഒരു സ്ഥിര prefix മാറാതെ നിർത്തുന്നതിലൂടെ, ഇത് context window-ന്റെ വലുപ്പം കുറയ്ക്കുന്നില്ല, പക്ഷേ ഒരു വലിയ സ്ഥിര ഭാഗം ആവർത്തിച്ച് അയക്കുന്നത് വളരെ വിലകുറഞ്ഞതും വേഗമുള്ളതുമാക്കുന്നു — ഓരോ വിളിയിലും എത്ര റഫറൻസ് സാമഗ്രി നിലനിർത്താൻ നിങ്ങൾ തയ്യാറാണ് എന്ന കണക്ക് ഇത് മാറ്റുന്നു.

### ഒരു തന്ത്രം തിരഞ്ഞെടുക്കൽ

ഈ നാല് സമീപനങ്ങൾ പരസ്പരം ഒഴിവാക്കുന്നവയല്ല — പക്വതയുള്ള സിസ്റ്റങ്ങൾ സാധാരണ പലതും ചേർക്കുന്നു: മുകളിൽ cache ചെയ്ത, modular ആയ ഒരു system prompt; നിലനിർത്താൻ കഴിയാത്തത്ര വലുതായ എന്തിനും external memory/retrieval; ഒരു നീണ്ട session-ൽ വളരുന്ന സംഭാഷണ ചരിത്രത്തിന് progressive summarisation.

| തന്ത്രം | എങ്ങനെ പ്രവർത്തിക്കുന്നു | വിട്ടുവീഴ്ച |
|---|---|---|
| Progressive summarisation | ഇടം ലാഭിക്കാൻ പഴയ turn-കൾ സംഗ്രഹിക്കുക | കൃത്യമായ വാക്കുകൾ നഷ്ടപ്പെടുന്നു |
| External memory | വിശദാംശങ്ങൾ ഒരു DB-യിൽ സൂക്ഷിക്കുക, ആവശ്യമുള്ളപ്പോൾ എടുക്കുക | Retrieval latency കൂട്ടുന്നു |
| Modular prompts / Skills | പ്രസക്തമായ prompt ഭാഗങ്ങൾ മാത്രം ലോഡ് ചെയ്യുക | മുൻകൂട്ടിയുള്ള ക്രമീകരണം വേണം |
| Prompt caching | വിളികൾക്കിടയിൽ സ്ഥിര prefix cache ചെയ്യുക | ഉള്ളടക്കം യഥാർഥത്തിൽ സ്ഥിരമായിരിക്കണം |

> **🌍️ യഥാർഥ ഉദാഹരണം:** ദീർഘനേരം പ്രവർത്തിക്കുന്ന ഒരു coding agent പല മണിക്കൂർ നീളുന്ന ഒരു session-ൽ ഒരു വലിയ repository-യിലൂടെ പ്രവർത്തിക്കുന്നു. മുഴുവൻ ഫയൽ ചരിത്രവും context-ൽ സൂക്ഷിക്കുന്നതിനു പകരം, അത് നേരത്തേയുള്ള പര്യവേക്ഷണ ഘട്ടങ്ങൾ ക്രമേണ സംഗ്രഹിക്കുന്നു, വായിച്ച ഫയലുകളുടെ മുഴുവൻ ഉള്ളടക്കവും ആവശ്യമുള്ളപ്പോൾ വീണ്ടും ചോദിക്കാവുന്ന ഒരു ബാഹ്യ index-ൽ സൂക്ഷിക്കുന്നു, നിലവിലെ ഉപജോലിക്ക് പ്രസക്തമായ "Skill" module (ഉദാ: ടെസ്റ്റിങ് രീതികൾ, വിന്യാസ ഘട്ടങ്ങൾ) മാത്രം ലോഡ് ചെയ്യുന്നു. ഒരൊറ്റ window-യിൽ ഉൾക്കൊള്ളാവുന്നതിലും എത്രയോ കൂടുതൽ വിവരങ്ങളിലൂടെ മൊത്തം ജോലി വ്യാപിക്കുമ്പോഴും ഇത് ഓരോ വിളിയും context window-ക്കുള്ളിൽ സുഖമായി നിർത്തുന്നു.

> **⚠️ ശ്രദ്ധിക്കുക:** നടപ്പാക്കാൻ ഏറ്റവും എളുപ്പമായതിനാൽ ടീമുകൾ ആദ്യം എടുക്കുന്ന തന്ത്രം പലപ്പോഴും progressive summarisation ആണ്, പക്ഷേ ഏറ്റവുമധികം നഷ്ടമുണ്ടാക്കുന്നതും അതാണ്. ഒരു session-ന്റെ തുടക്കത്തിലെ കൃത്യമായ ഒരു കണക്കോ ഉദ്ധരണിയോ നിർദേശമോ ഓർത്തെടുക്കുന്നതിനെ ഒരു ജോലി ആശ്രയിക്കുന്നെങ്കിൽ, അത് നിശ്ശബ്ദമായി ഉപേക്ഷിച്ചിരിക്കാൻ ഏറ്റവും സാധ്യതയുള്ള തന്ത്രം summarisation ആണ്.
