## Prompt Caching — ചെലവും Latency-യും കുറയ്ക്കൽ

Agentic സിസ്റ്റങ്ങൾ വളരുമ്പോൾ, ഓരോ അഭ്യർഥനയിലെയും token-കളുടെ വലിയൊരു ഭാഗം ഓരോ വിളിയിലും *ഒരുപോലെ* ആയിരിക്കും: system prompt, ടൂൾ നിർവചനങ്ങളുടെ ഒരു കൂട്ടം, ഒരു റഫറൻസ് രേഖ, ഒരു ശൈലീ ഗൈഡ്. Caching ഇല്ലാതെ, ഓരോ API വിളിയും ആ മുഴുവൻ സ്ഥിര ഭാഗവും വീണ്ടും തുടക്കം മുതൽ പ്രോസസ്സ് ചെയ്യുന്നു — കഴിഞ്ഞ വിളിക്കു ശേഷം മാറാത്ത ഉള്ളടക്കത്തിന് നിങ്ങൾ മുഴുവൻ പ്രോസസ്സിങ് ചെലവും മുഴുവൻ latency-യും നൽകുന്നു. മുൻപ് കണ്ട ഒരു prefix-ൽ ചെയ്ത ആന്തരിക പ്രോസസ്സിങ് ജോലി വീണ്ടും ഉപയോഗിക്കാൻ Claude-നെ അനുവദിച്ച് prompt caching ഇത് പരിഹരിക്കുന്നു, അങ്ങനെ ആ prefix പങ്കിടുന്ന ആവർത്തിക്കുന്ന വിളികൾ വിലകുറഞ്ഞതും വേഗമുള്ളതുമാകുന്നു.

### വലിയ തോതിൽ ഇത് പ്രധാനമാകുന്നത് എന്തുകൊണ്ട്

ഒരു നീണ്ട സംഭാഷണത്തിന്റെ ഓരോ turn-ലും, അല്ലെങ്കിൽ ഒരു batch ജോലിയിലെ ആയിരക്കണക്കിന് സ്വതന്ത്ര API വിളികളിലും, 8,000 token-ന്റെ ഒരു system prompt (role നിർവചനം, ടൂൾ schema-കൾ, നയ രേഖകൾ) വഹിക്കുന്ന ഒരു agent പരിഗണിക്കുക. Caching ഇല്ലാതെ, അതിൽ ഒന്നും മാറിയിട്ടില്ലെങ്കിലും ആ 8,000 token ഭാഗത്തിന് വീണ്ടും വീണ്ടും പണം നൽകുകയും അത് പ്രോസസ്സ് ചെയ്യുകയും ചെയ്യുന്നു. വിളികളുടെ എണ്ണം കൂടുമ്പോൾ, ഇത് ഒരു പ്രൊഡക്ഷൻ വിന്യാസത്തിലെ ഏറ്റവും വലുതും ഏറ്റവും എളുപ്പം ഒഴിവാക്കാവുന്നതുമായ ചെലവുകളിൽ ഒന്നാകുന്നു — ഒപ്പം ഇത് latency നേരിട്ട് കൂട്ടുന്നു, കാരണം പ്രോസസ്സ് ചെയ്യാൻ കൂടുതൽ token എന്നാൽ പ്രതികരണം തുടങ്ങാൻ കൂടുതൽ സമയം എന്നാണ്.

### ക്രമ നിയമം

അഭ്യർഥനകൾക്കിടയിൽ ഒരു **പങ്കിട്ട prefix** കണ്ടെത്തിയാണ് prompt caching പ്രവർത്തിക്കുന്നത് — മുൻ വിളിയുമായി byte-to-byte ഒരുപോലെയുള്ള prompt-ന്റെ തുടക്ക ഭാഗം. നിങ്ങൾ എങ്ങനെ prompt ഉണ്ടാക്കണം എന്നതിന് ഇതിന് നേരിട്ടുള്ള ഒരു architecture പ്രത്യാഘാതമുണ്ട്:

- **സ്ഥിരമായ ഉള്ളടക്കം ആദ്യം** — system prompt, ടൂൾ നിർവചനങ്ങൾ, റഫറൻസ്/നയ രേഖകൾ, few-shot ഉദാഹരണങ്ങൾ: വിളികൾക്കിടയിൽ മാറാത്ത എന്തും.
- **മാറുന്ന ഉള്ളടക്കം അവസാനം** — ഉപയോക്താവിന്റെ നിലവിലെ ചോദ്യം, ഈ അഭ്യർഥനയ്ക്ക് മാത്രമുള്ള ഡാറ്റ, ഓരോ വിളിയിലും മാറുന്ന എന്തും.

മാറുന്ന ഉള്ളടക്കം prompt-ൽ നേരത്തേ ഇടകലർന്നാൽ, അത് പങ്കിട്ട prefix തകർക്കുന്നു, ആ ബിന്ദുവിനു ശേഷമുള്ള എല്ലാം cache യോഗ്യത നഷ്ടപ്പെടുത്തുന്നു — prompt-ന്റെ *ബാക്കി* ഭാഗം ഒരുപോലെയാണെങ്കിൽ പോലും. അതിനാൽ ക്രമം ശരിയാക്കുന്നത് ഒരു ചെറിയ മെച്ചപ്പെടുത്തലല്ല; caching പ്രവർത്തിക്കുന്നതും caching നിശ്ശബ്ദമായി ഇടപെടാതിരിക്കുന്നതും തമ്മിലുള്ള വ്യത്യാസമാണ് അത്.

### രൂപകൽപ്പനാ പ്രത്യാഘാതങ്ങൾ

Cache ചെയ്യാവുന്ന prefix പരമാവധിയാക്കാൻ architect-മാർ prompt-കൾ സജീവമായി ഘടനപ്പെടുത്തണം: സ്ഥിരമായ നിർദേശങ്ങളും റഫറൻസ് സാമഗ്രികളും മുകളിൽ ഒരൊറ്റ തുടർച്ചയായ ഭാഗത്തിൽ ഒന്നിപ്പിക്കുക, അഭ്യർഥനയ്ക്ക് മാത്രമുള്ളതെല്ലാം ഏറ്റവും അവസാനത്തേക്ക് തള്ളുക. ഇത് പ്രത്യേകിച്ച് വിലപ്പെട്ടതാണ്:

- ഓരോ turn-ലും അതേ system prompt-ഉം ടൂൾ schema-യും ആവർത്തിക്കുന്ന നീണ്ട agentic loop-കൾക്ക്.
- പല വ്യത്യസ്ത user ചോദ്യങ്ങളിലായി അതേ വലിയ റഫറൻസ് രേഖ വീണ്ടും ഉപയോഗിക്കുന്ന RAG pipeline-കൾക്ക്.
- ഒട്ടേറെ സ്വതന്ത്ര ഇൻപുട്ടുകളിൽ അതേ നിർദേശങ്ങൾ പ്രയോഗിക്കുന്ന വലിയ അളവിലുള്ള batch അഥവാ backend ജോലികൾക്ക്.

> **🌍️ യഥാർഥ ഉദാഹരണം:** ഒരു രേഖാ പരിശോധനാ പ്ലാറ്റ്ഫോം, ദിവസവും പരിശോധിക്കുന്ന ആയിരക്കണക്കിന് കരാർ വ്യവസ്ഥകളിൽ ഓരോന്നിനൊപ്പവും അതേ 6,000 token നയ, രൂപീകരണ ഗൈഡ് അയക്കുന്നു. നയ ഗൈഡ് ഒരു സ്ഥിര prefix ആകുന്ന വിധത്തിലും അവസാനം പ്രത്യേക വ്യവസ്ഥയുടെ ടെക്സ്റ്റ് മാത്രം മാറുന്ന വിധത്തിലും prompt പുനഃക്രമീകരിച്ചതോടെ, ഏതാണ്ട് എല്ലാ വിളിയിലും പ്ലാറ്റ്ഫോമിന് cache hit കിട്ടുന്നു — അടിസ്ഥാന ജോലിയോ മോഡലോ ഒട്ടും മാറ്റാതെ, ഓരോ പരിശോധനയുടെയും ശരാശരി ചെലവും പ്രതികരണ latency-യും ഗണ്യമായി കുറയുന്നു.

> **💡️ നുറുങ്ങ്:** "സ്ഥിരം" എന്ന ഉള്ളടക്കം യഥാർഥത്തിൽ byte-to-byte സ്ഥിരമാണെങ്കിൽ മാത്രമേ prompt caching സഹായിക്കൂ. സ്ഥിരമെന്ന് കരുതുന്ന ഭാഗത്ത് എവിടെയെങ്കിലുമുള്ള ഒരു ചെറിയ മാറ്റം പോലും — ഒരു സമയമുദ്ര, ചലനാത്മകമായി ചേർത്ത ഒരു മൂല്യം — prompt-ൽ അതിനു ശേഷമുള്ള എല്ലാറ്റിന്റെയും cache അസാധുവാക്കും.
