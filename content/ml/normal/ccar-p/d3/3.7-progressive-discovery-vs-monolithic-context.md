## Progressive Discovery vs. Monolithic Context

ഒരു വിജ്ഞാന ശേഖരത്തിലേക്കോ വലിയൊരു കൂട്ടം വിവരങ്ങളിലേക്കോ Claude എങ്ങനെ പ്രവേശിക്കണമെന്ന് രൂപകൽപ്പന ചെയ്യുമ്പോൾ, വിവരം *എപ്പോൾ* context window-യിൽ പ്രവേശിക്കുന്നു എന്നതിനെക്കുറിച്ച് അടിസ്ഥാനപരമായ ഒരു architecture തിരഞ്ഞെടുപ്പ് നിങ്ങൾക്ക് മുന്നിലുണ്ട്: എല്ലാം മുൻകൂട്ടി ലോഡ് ചെയ്യുക, അല്ലെങ്കിൽ വേണ്ടത് മാത്രം ലോഡ് ചെയ്ത് സംഭാഷണം ആവശ്യപ്പെടുന്നതനുസരിച്ച് കൂടുതൽ എടുക്കുക. ഈ തിരഞ്ഞെടുപ്പ് latency, ചെലവ്, context window-യിലെ സമ്മർദം, അടിസ്ഥാന വിജ്ഞാന ശേഖരം വളരുമ്പോൾ സിസ്റ്റം എത്ര നന്നായി വളരുന്നു എന്നിവയെ ബാധിക്കുന്നു.

### Monolithic context

പ്രത്യേക ചോദ്യത്തെക്കുറിച്ച് Claude ചിന്തിച്ചു തുടങ്ങും മുൻപേ, പ്രസക്തമായ മുഴുവൻ രേഖാ ശേഖരവും context window-യിലേക്ക് ലോഡ് ചെയ്യുന്നതാണ് monolithic context. ഇത് നടപ്പാക്കാൻ ലളിതമാണ് — ഉണ്ടാക്കാനോ ക്രമീകരിക്കാനോ retrieval യുക്തിയില്ല — ഒപ്പം generation ഘട്ടത്തിൽ വേഗവുമാണ്, കാരണം ജോലിക്കിടയിൽ ഒരു retrieval വിളി നടത്താൻ Claude നിർത്തേണ്ടതില്ല; ആവശ്യമായേക്കാവുന്നതെല്ലാം ഇതിനകം context-ൽ ഇരിക്കുന്നു. വിട്ടുവീഴ്ച, ഒരു context window-യിൽ സുഖമായി ഒതുങ്ങുന്നത്ര ചെറുതും വ്യക്തമായി നിർവചിച്ചതുമായ വിജ്ഞാന ശേഖരത്തിന് മാത്രമേ ഈ സമീപനം ഫലിക്കൂ എന്നതാണ്; ഒപ്പം പ്രത്യേക ചോദ്യത്തിന് പ്രസക്തമല്ലെന്ന് തെളിയുന്ന ഉള്ളടക്കത്തിന് ഇത് context ഇടവും token-ഉം ചെലവും പാഴാക്കുന്നു, ഇത് യഥാർഥത്തിൽ പ്രധാനപ്പെട്ട ഭാഗങ്ങളിലുള്ള മോഡലിന്റെ ശ്രദ്ധ നേർപ്പിക്കുകയും ചെയ്യാം.

### Progressive discovery

തുടക്കത്തിൽ വേണ്ടത് മാത്രം ലോഡ് ചെയ്ത്, ആവശ്യാനുസരണം കൂടുതൽ വിവരം എടുക്കുന്നതാണ് progressive discovery — പലപ്പോഴും ഒരൊറ്റ agentic ജോലിക്കുള്ളിലെ പല turn-കളിലോ ഘട്ടങ്ങളിലോ ആയി. വലുതോ അതിരില്ലാത്തതോ ആയ വിജ്ഞാന ശേഖരങ്ങളിലേക്ക് ഇത് വളരുന്നു, കാരണം എല്ലാം ഒരൊറ്റ window-യിൽ ഒതുക്കാൻ നിങ്ങൾ ഒരിക്കലും ശ്രമിക്കുന്നില്ല — നിലവിലെ ന്യായവാദ ഘട്ടം ആവശ്യമാണെന്ന് വെളിപ്പെടുത്തുമ്പോൾ മാത്രം അടുത്ത പ്രസക്തമായ ഭാഗം എടുക്കുന്നു. പ്രവചിക്കാനാകാത്ത ചോദ്യ രീതികളും ഇത് നന്നായി കൈകാര്യം ചെയ്യുന്നു, കാരണം ഒരു ഉപയോക്താവ് എന്തിനെക്കുറിച്ച് ചോദിക്കുമെന്ന് മുൻകൂട്ടി കൃത്യമായി പ്രവചിക്കേണ്ടതില്ല; സംഭാഷണത്തിന്റെ യഥാർഥ ആവശ്യങ്ങൾ വ്യക്തമാകുമ്പോൾ സിസ്റ്റത്തിന് കൂടുതൽ എടുക്കാം. വിട്ടുവീഴ്ച architecture സങ്കീർണതയാണ് (ഇപ്പോൾ retrieval യുക്തിയും ഒരുപക്ഷേ പല retrieval റൗണ്ടുകളും വേണം), ഒപ്പം ഓരോ turn-ലും കൂടിയ latency വരാം, കാരണം ഓരോ അധിക retrieval-ഉം ഒരു റൗണ്ട്-ട്രിപ്പ് ആണ്.

### ഇവയിൽ ഏത് തിരഞ്ഞെടുക്കണം

| തന്ത്രം | എന്ത് ചെയ്യുന്നു | എപ്പോൾ ഉപയോഗിക്കണം |
|---|---|---|
| **Progressive discovery** | വേണ്ടത് മാത്രം ലോഡ് ചെയ്യുക, ആവശ്യാനുസരണം കൂടുതൽ എടുക്കുക | വലിയ വിജ്ഞാന ശേഖരങ്ങൾ; പ്രവചിക്കാനാകാത്ത/വൈവിധ്യമുള്ള ചോദ്യ രീതികൾ |
| **Monolithic context** | എല്ലാം മുൻകൂട്ടി context window-യിലേക്ക് ലോഡ് ചെയ്യുക | ചെറുതും വ്യക്തമായി നിർവചിച്ചതുമായ രേഖാ ശേഖരങ്ങൾ; generation സമയത്തെ വേഗതയാണ് ഏറ്റവും പ്രധാനം |

Eager, lazy loading എന്നിവയ്ക്കിടയിൽ സിസ്റ്റം രൂപകൽപ്പനയിൽ മറ്റിടങ്ങളിൽ കാണുന്ന അതേ വലിവാണ് ആശയപരമായി ഇത്: eager (monolithic) ലോഡിങ് ലളിതവും ആവർത്തിച്ചുള്ള റൗണ്ട്-ട്രിപ്പുകൾ ഒഴിവാക്കുന്നതുമാണ്, പക്ഷേ വളരുന്നില്ല, ലോഡ് ചെയ്തതിൽ ഉപയോഗിക്കാത്ത ഭൂരിഭാഗത്തിനും വിഭവങ്ങൾ പാഴാക്കുന്നു; lazy (progressive) ലോഡിങ് ഭംഗിയായി വളരുകയും കാര്യക്ഷമമായി നിൽക്കുകയും ചെയ്യുന്നു, പക്ഷേ സങ്കീർണതയും ഓരോ ഘട്ടത്തിലെ latency-യും കൂട്ടുന്നു. വിജ്ഞാന ശേഖരത്തിന്റെ വലുപ്പവും പ്രവചനീയതയും വിവരിച്ചുകൊണ്ട് ഏതാണ് ഇണങ്ങുന്നതെന്ന് പരീക്ഷ സാധാരണ സൂചിപ്പിക്കുന്നു — ചെറുതും നിശ്ചിതവുമായ ഒരു FAQ രേഖ monolithic-നെ അനുകൂലിക്കുന്നു; പ്രവചിക്കാനാകാത്ത ചോദ്യങ്ങളുള്ള, നിരന്തരം വളരുന്ന ഒരു വിശാല ആന്തരിക wiki progressive discovery-യെ അനുകൂലിക്കുന്നു.

> **🌍️ യഥാർഥ ഉദാഹരണം:** ഒരു കമ്പനി രണ്ട് വ്യത്യസ്ത ആന്തരിക Claude സഹായികൾ ഉണ്ടാക്കുന്നു. ഒന്ന് 10 പേജുള്ള ഒരൊറ്റ onboarding ഹാൻഡ്ബുക്കിനെക്കുറിച്ചുള്ള ചോദ്യങ്ങൾക്ക് ഉത്തരം നൽകുന്നു — ഹാൻഡ്ബുക്ക് മുഴുവൻ ഓരോ തവണയും context-ലേക്ക് ലോഡ് ചെയ്യാനാകുന്നത്ര ചെറുതാണ് (monolithic), ഇത് രൂപകൽപ്പന അതിലളിതവും പ്രതികരണം ഉടനടിയുമാക്കുന്നു. മറ്റൊന്ന് പല ടീമുകളിലായി ആയിരക്കണക്കിന് പേജുകളുള്ള ഒരു മുഴുവൻ എൻജിനീയറിങ് wiki-യിലുടനീളം ഉത്തരം നൽകുന്നു — എല്ലാം ലോഡ് ചെയ്യുന്നത് അസാധ്യവും പാഴുമായതിനാൽ അത് progressive discovery ഉപയോഗിക്കുന്നു, ഓരോ ചോദ്യത്തിനും പ്രസക്തമായ പേജുകൾ മാത്രം എടുക്കുന്നു, ആദ്യ ഉത്തരം പോരാതെ വന്നാൽ മാത്രം കൂടുതൽ എടുക്കുന്നു.
