## Authentication-ഉം Authorization-ഉം

ഈ രണ്ട് പദങ്ങളും പലപ്പോഴും ഒരുമിച്ചും ചിലപ്പോൾ പരസ്പരം മാറ്റിയും സാധാരണ സംഭാഷണത്തിൽ ഉപയോഗിക്കാറുണ്ട്, പക്ഷേ അവ രണ്ട് വ്യത്യസ്ത ചോദ്യങ്ങൾക്കാണ് ഉത്തരം നൽകുന്നത്, അവ വ്യക്തമായി വേർതിരിച്ചു നിർത്താൻ പരീക്ഷ പ്രതീക്ഷിക്കുന്നു. **Authentication** "നിങ്ങൾ ആരാണ്?" എന്നതിന് ഉത്തരം നൽകുന്നു — സാധാരണ ഒരു login, API key, അല്ലെങ്കിൽ token വഴി സ്വത്വം പരിശോധിക്കൽ. **Authorization** "നിങ്ങൾക്ക് എന്ത് ചെയ്യാൻ അനുവാദമുണ്ട്?" എന്നതിന് ഉത്തരം നൽകുന്നു — *അറിയാവുന്ന* ഒരു സ്വത്വത്തിന് ഒരു *പ്രത്യേക* നടപടിക്ക് അനുമതിയുണ്ടോ എന്ന് പരിശോധിക്കൽ. നിങ്ങൾ authenticate ചെയ്യപ്പെട്ടിരിക്കാം (ആരാണ് അഭ്യർഥന നടത്തുന്നതെന്ന് Claude/സിസ്റ്റം ശരിയായി തിരിച്ചറിയുന്നു), എന്നിട്ടും authorize ചെയ്യപ്പെട്ടിരിക്കില്ല (ആ സ്വത്വത്തിന് ഈ പ്രത്യേക പ്രവർത്തനത്തിന് അനുമതിയില്ല).

> **🗣️ ലളിതമായി പറഞ്ഞാൽ:** വാതിൽക്കൽ നിങ്ങളുടെ ഐഡി ബാഡ്ജ് കാണിക്കുന്നതാണ് authentication. നിങ്ങളുടെ ബാഡ്ജ് തുറക്കാൻ ക്രമീകരിച്ചിട്ടുള്ള മുറികളുടെ വാതിൽ മാത്രം തുറക്കുന്നതാണ് authorization.

### Claude architecture-കൾക്ക് ഈ വേർതിരിവ് പ്രധാനമാകുന്നത് എന്തുകൊണ്ട്

ഒരു agentic സിസ്റ്റത്തിൽ, Claude നടത്തുന്ന ഓരോ ടൂൾ വിളിയും ഫലത്തിൽ ഏതെങ്കിലും ബാഹ്യ സിസ്റ്റത്തിനെതിരായ ഒരു അഭ്യർഥനയാണ് — ഒരു ഡാറ്റാബേസ്, ഒരു ആന്തരിക API, ഒരു ഫയൽ സംഭരണി. ആ ഓരോ വിളിക്കും രണ്ട് വ്യത്യസ്ത പരിശോധനകൾ നടക്കണം:

- **Authentication പരിശോധന:** ഈ ടൂൾ വിളി ന്യായമായി authenticate ചെയ്യപ്പെട്ട ഒരു session/agent-ൽ നിന്നാണോ വരുന്നത് (പരിശോധിച്ച API key, സാധുവായ token, പരിശോധിച്ച വിളിക്കുന്നയാളുടെ സ്വത്വം)? Authenticate ചെയ്യപ്പെടാത്ത ഒരു ടൂൾ വിളി ഒരിക്കലും നടപ്പാക്കാൻ അനുവദിക്കരുത്, അത്രതന്നെ.
- **Authorization പരിശോധന:** ഇത് ന്യായമായ, authenticate ചെയ്യപ്പെട്ട ഒരു agent ആണെന്നിരിക്കെ, *ഈ പ്രത്യേക നടപടി* ചെയ്യാൻ അതിന് അനുമതിയുണ്ടോ? വിളിക്കാൻ ഒരു കാര്യവുമില്ലാത്ത ഒരു `delete_record` ടൂൾ വിളിക്കുന്ന, authenticate ചെയ്യപ്പെട്ട ഒരു agent-നെ authorization തലത്തിൽ തടയണം — രൂപകൽപ്പനാ തലത്തിൽ മാത്രമല്ല, നടപ്പാക്കൽ തലത്തിലും പ്രയോഗിച്ച അതേ least privilege ആശയമാണിത്.

ഒരു session-ന്റെ തുടക്കത്തിൽ ഒരിക്കൽ authenticate ചെയ്ത ശേഷം തുടർന്നുള്ള ഓരോ ടൂൾ വിളിയും സ്വയമേവ authorize ചെയ്യപ്പെട്ടതായി പരോക്ഷമായി വിശ്വസിക്കുന്നതാണ് ഒരു സാധാരണ architecture തെറ്റ്. ശരിയായ architecture ഓരോ നടപടിയിലും authorization വീണ്ടും പരിശോധിക്കുന്നു, കാരണം പല turn-കളിലായി ഒരു agent-ന്റെ പദ്ധതി ആരും ഉദ്ദേശിക്കാത്ത നടപടികൾ ആവശ്യപ്പെടുന്നിടത്തേക്ക് വഴിമാറാം.

### അനുബന്ധ ആശയങ്ങൾ

**Least privilege** authorization-മായി നേരിട്ട് ബന്ധപ്പെടുന്നു: authenticate ചെയ്യപ്പെട്ട ഒരു സ്വത്വത്തിന് എന്ത് ചെയ്യാൻ അനുമതി നൽകണം (ഏറ്റവും കുറഞ്ഞത് മാത്രം) എന്ന *നയമാണ്* അത്. **Audit logging** വേറിട്ടതും പൂരകവുമായ ഒരു നിയന്ത്രണമാണ്: ആര് (authentication) എന്ത് (അനുമതിയോടെയോ അല്ലാതെയോ) എപ്പോൾ ചെയ്തു എന്ന് രേഖപ്പെടുത്തൽ. Compliance-നും ഒരു സംഭവത്തിനു ശേഷമുള്ള അന്വേഷണത്തിനും audit logging അത്യാവശ്യമാണ് — പക്ഷേ അത് അടിസ്ഥാനപരമായി പ്രതികരണാത്മകമാണ്. എന്ത് സംഭവിച്ചു എന്ന് അത് പറയുന്നു; എന്തെങ്കിലും സംഭവിക്കുന്നത് അത് തടയുന്നില്ല. മികച്ച audit log-കളുണ്ടെങ്കിലും least-privilege നടപ്പാക്കലില്ലാത്ത ഒരു സിസ്റ്റം, അത് തടയാൻ ഒന്നും ചെയ്യാത്ത ഒരു സുരക്ഷാ സംഭവത്തിന്റെ മനോഹരമായ വിശദ രേഖ ഉണ്ടാക്കും.

| ആശയം | എന്താണ് അർഥം | പരീക്ഷയിലെ പ്രയോഗം |
|---|---|---|
| **Authentication** | നിങ്ങൾ *ആരാണ്* എന്ന് പരിശോധിക്കൽ (login, API key) | പ്രവർത്തിക്കും മുൻപ് ഓരോ ടൂൾ വിളിയും authenticate ചെയ്യണം |
| **Authorization** | നിങ്ങൾക്ക് *എന്ത് ചെയ്യാൻ* അനുവാദമുണ്ടെന്ന് പരിശോധിക്കൽ | Session തുടക്കത്തിൽ മാത്രമല്ല, ഓരോ നടപടിക്കും മുൻപ് അനുമതി പരിശോധിക്കണം |
| **Least privilege** | വേണ്ട ഏറ്റവും കുറഞ്ഞ പ്രവേശനം മാത്രം | ഒരു agent-ന് വേണ്ടാത്ത ടൂളുകളും അനുമതികളും നീക്കുക — authorization-നു പിന്നിലെ നയം |
| **Audit logging** | ആര് എന്ത് എപ്പോൾ ചെയ്തു എന്ന് രേഖപ്പെടുത്തുന്നു | Compliance-ന് ആവശ്യം; കണ്ടെത്തലിനുള്ള നിയന്ത്രണമാണ്, least privilege-ന് പകരമല്ല |

> **🌍️ യഥാർഥ ഉദാഹരണം:** ആരോഗ്യ മേഖലയോട് ചേർന്നുനിൽക്കുന്ന ഒരു Claude agent വരുന്ന ഓരോ അഭ്യർഥനയും ഒപ്പിട്ട ഒരു സേവന token ഉപയോഗിച്ച് authenticate ചെയ്യുന്നു (authentication ✓), പക്ഷേ ഒരു ക്രമീകരണ പിഴവ് കാരണം authenticate ചെയ്യപ്പെട്ട ഏത് ആന്തരിക സേവനത്തിനും role നോക്കാതെ അതിന്റെ `export_patient_records` ടൂൾ വിളിക്കാനാകുന്നു (authorization ✗). അനുമതിയില്ലാത്ത ഓരോ export-ഉം സിസ്റ്റത്തിന്റെ audit log വിശ്വസ്തതയോടെ സംഭവത്തിനു ശേഷം രേഖപ്പെടുത്തുന്നു — ഇത് സംഭവാനന്തര അന്വേഷണത്തെ സഹായിക്കുന്നു, പക്ഷേ ചോർച്ച തടയാൻ ഒന്നും ചെയ്തില്ല. യഥാർഥ പരിഹാരം ആ ടൂളിൽ role അടിസ്ഥാനമാക്കിയ authorization പരിശോധനകൾ നടപ്പാക്കുകയായിരുന്നു, അത് ആര് ഉപയോഗിച്ചെന്ന് ലോഗ് ചെയ്യുക മാത്രമല്ല.
