## RAG — Retrieval-Augmented Generation

ഏതൊരു LLM-നെയും പോലെ Claude-ന് "അറിയാവുന്നത്" അതിന്റെ പരിശീലന ഡാറ്റയിൽ ഉണ്ടായിരുന്നതും inference സമയത്ത് context window-യിൽ വെക്കുന്നതും മാത്രമാണ്. നിങ്ങളുടെ കമ്പനിയുടെ ആന്തരിക wiki-യിലേക്കോ ഉൽപ്പന്നത്തിന്റെ ടിക്കറ്റ് ചരിത്രത്തിലേക്കോ പരിശീലനത്തിനു ശേഷം ഉണ്ടാക്കിയ രേഖകളിലേക്കോ അതിന് തത്സമയ പ്രവേശനമില്ല. Retrieval-Augmented Generation (RAG) ആ വിടവ് നികത്തുന്നു: Claude ഉത്തരം നൽകും മുൻപ്, സിസ്റ്റം ഒരു ബാഹ്യ വിജ്ഞാന ഉറവിടത്തിൽ നിന്ന് പ്രസക്തമായ ഭാഗങ്ങൾ എടുത്ത് prompt-ൽ ചേർക്കുന്നു, അങ്ങനെ Claude-ന്റെ ഉത്തരം പരിശീലനത്തിൽ ഓർത്തുവെച്ചതിനെ മാത്രം ആശ്രയിക്കാതെ യഥാർഥവും കാലികവും സ്വകാര്യവുമായ വിവരത്തിൽ അടിസ്ഥാനപ്പെടുന്നു.

> **🗣️ ലളിതമായി പറഞ്ഞാൽ:** ഉത്തരം നൽകുന്നതിനു തൊട്ടുമുൻപ് Claude-ന് മറിച്ചുനോക്കാൻ ഒരു റഫറൻസ് പുസ്തകം നൽകുന്നതുപോലെയാണ് RAG — എല്ലാം ഓർത്തുവെച്ചിരിക്കണമെന്ന് പ്രതീക്ഷിക്കുന്നതിനു പകരം, ഈ പ്രത്യേക ചോദ്യത്തിന് വേണ്ട പേജുകൾ കൃത്യമായി നിങ്ങൾ കൈമാറുന്നു.

### RAG pipeline, ഘട്ടം ഘട്ടമായി

ഒരു പ്രൊഡക്ഷൻ RAG സിസ്റ്റം രൂപകൽപ്പന ചെയ്യുക എന്നാൽ ആറ് ഘട്ടങ്ങളിൽ ഓരോന്നിലും ബോധപൂർവമായ ഒരു തീരുമാനം എടുക്കുക എന്നാണ് — RAG എന്നത് "വെറും embed ചെയ്ത് തിരയൽ" ആണെന്ന് കരുതുന്നിടത്താണ് മിക്ക യഥാർഥ നടപ്പാക്കലുകളും പരാജയപ്പെടുന്നത്.

1. **Ingestion** — രേഖകൾ സിസ്റ്റത്തിൽ പ്രവേശിക്കുന്നു. *ഏതൊക്കെ* രേഖകൾ പരിധിയിലുണ്ടെന്നും *എത്ര ഇടവിട്ട്* അവ പുതുക്കുന്നുവെന്നും തീരുമാനിക്കുക (പതുക്കെ മാറുന്ന റഫറൻസ് രേഖകൾക്ക് ഒരു രാത്രി batch ജോലി vs. ഒരു സപ്പോർട്ട്-ടിക്കറ്റ് വിജ്ഞാന ശേഖരത്തിന് ഏതാണ്ട് തത്സമയ ingestion).
2. **Chunking** — രേഖകൾ ചെറുതും എടുക്കാവുന്നതുമായ ഭാഗങ്ങളായി വിഭജിക്കുന്നു, കാരണം 50 പേജുള്ള ഒരു PDF മുഴുവൻ ഒരൊറ്റ vector ആയി embed ചെയ്യുന്നത് retrieval-ന് വേണ്ട കൃത്യത നശിപ്പിക്കുന്നു. Chunk-ന്റെ വലുപ്പവും ഇടകലരലും കണ്ണടച്ച് സ്വീകരിക്കേണ്ട സ്ഥിരസ്ഥിതികളല്ല, ബോധപൂർവം ക്രമീകരിക്കേണ്ട പരാമീറ്ററുകളാണ്.
3. **Embedding** — ഓരോ ഭാഗവും അതിന്റെ അർഥം ഉൾക്കൊള്ളുന്ന ഒരു സംഖ്യാ vector ആയി മാറ്റുന്നു. Embedding മോഡലിന്റെയും vector മാനങ്ങളുടെയും തിരഞ്ഞെടുപ്പ് retrieval ഗുണനിലവാരത്തെയും സംഭരണ ചെലവിനെയും ബാധിക്കുന്നു.
4. **Indexing** — Vector-കൾ തിരയാവുന്ന ഒരു ഡാറ്റാബേസിൽ (ഒരു vector store) metadata-യോടൊപ്പം (ഉറവിടം, തീയതി, അനുമതികൾ) സൂക്ഷിക്കുന്നു; ഇത് പിന്നീട് സാമ്യ തിരച്ചിൽ മാത്രമല്ല, ഫിൽട്ടർ ചെയ്യലും സാധ്യമാക്കുന്നു.
5. **Retrieval** — ചോദ്യ സമയത്ത്, ഉപയോക്താവിന്റെ ചോദ്യത്തിന് ഏറ്റവും പ്രസക്തമായ ഭാഗങ്ങൾ സിസ്റ്റം കണ്ടെത്തുന്നു. ഇവിടെയാണ് അർഥാധിഷ്ഠിത, keyword, hybrid തിരച്ചിൽ തന്ത്രങ്ങൾ വരുന്നത് (താഴെ കാണുക).
6. **Generation** — എടുത്ത ഭാഗങ്ങളും ഉപയോക്താവിന്റെ ചോദ്യവും ചേർത്ത് ഒരു prompt ഉണ്ടാക്കി Claude-ന് അയക്കുന്നു. എത്ര ഭാഗങ്ങൾ ഉൾപ്പെടുത്തണം, context-ൽ അവ എവിടെ വെക്കണം എന്നിവ ഇവിടത്തെ തീരുമാനങ്ങളാണ് (ചേർത്ത ഉള്ളടക്കത്തിൽ ഒരു മോഡൽ എത്ര നന്നായി ശ്രദ്ധിക്കുന്നു എന്നതിൽ പുതുമയുടെയും സ്ഥാനത്തിന്റെയും പ്രഭാവങ്ങൾ പ്രധാനമാണ്).

### Chunking തന്ത്രങ്ങൾ

| തന്ത്രം | എങ്ങനെ | ഏറ്റവും ഇണങ്ങുന്നത് |
|---|---|---|
| നിശ്ചിത വലുപ്പം | ഉള്ളടക്കം നോക്കാതെ ഓരോ N token-ലും വിഭജിക്കുക | ലളിതം, വേഗം, ഏകരൂപമായ ഉള്ളടക്കം |
| അർഥാധിഷ്ഠിതം / ഖണ്ഡിക | സ്വാഭാവിക അതിരുകളിൽ വിഭജിക്കുക (ഖണ്ഡികകൾ, വിഭാഗങ്ങൾ) | ആഖ്യാന രേഖകൾ, ലേഖനങ്ങൾ |
| ശ്രേണീബദ്ധം | വലിയ ഭാഗങ്ങൾ + ചെറിയ ഭാഗങ്ങൾ, രണ്ട് തലത്തിലും എടുക്കുക | Context-ഉം *ഒപ്പം* കൃത്യതയും വേണ്ട നീണ്ട രേഖകൾ |
| Sliding window | ആശയങ്ങൾ പാതിവഴിയിൽ മുറിയാതിരിക്കാൻ ഇടകലരുന്ന ഭാഗങ്ങൾ | ഭാഗങ്ങളുടെ അതിരുകളിൽ വിവരം നഷ്ടപ്പെടുന്നത് തടയൽ |

### Retrieval തന്ത്രങ്ങൾ

| തന്ത്രം | എങ്ങനെ പ്രവർത്തിക്കുന്നു | ഏറ്റവും ഇണങ്ങുന്നത് |
|---|---|---|
| അർഥാധിഷ്ഠിത (vector) തിരച്ചിൽ | ചോദ്യത്തോട് സമാനമായ *അർഥ*മുള്ള ഭാഗങ്ങൾ കണ്ടെത്തുന്നു | ആശയപരമായ, "X വിശദീകരിക്കൂ" എന്ന തരം ചോദ്യങ്ങൾ |
| Keyword (BM25) തിരച്ചിൽ | ചോദ്യത്തിലെ കൃത്യമായ വാക്കുകളുള്ള ഭാഗങ്ങൾ കണ്ടെത്തുന്നു | പ്രത്യേക പേരുകൾ, കോഡുകൾ, ഉൽപ്പന്ന ID-കൾ |
| Hybrid തിരച്ചിൽ | അർഥാധിഷ്ഠിത + keyword ഫലങ്ങൾ ചേർക്കുന്നു | മിക്ക പ്രൊഡക്ഷൻ സിസ്റ്റങ്ങളും — രണ്ടിന്റെയും നല്ല വശങ്ങൾ |
| Re-ranking | രണ്ടാമതൊരു മോഡൽ എടുത്ത ഫലങ്ങൾ വീണ്ടും സ്കോർ ചെയ്യുന്നു | കൂടിയ കൃത്യത, പകരം കൂടിയ latency |

സൂക്ഷ്മവും എന്നാൽ പ്രധാനവുമായ ഒരു പരീക്ഷാ കാര്യം: embedding "അർഥം" ഉൾക്കൊള്ളുന്നതിനാൽ, കൃത്യമായ token-കളല്ല, അർഥാധിഷ്ഠിത തിരച്ചിൽ മാത്രം ഒരു കൃത്യമായ ഉൽപ്പന്ന SKU വിട്ടുപോകാം; അതേസമയം keyword തിരച്ചിൽ മാത്രം, ഒരേ വാക്കുകൾ പങ്കിടാത്ത ആശയപരമായി ബന്ധപ്പെട്ട ഒരു ഭാഗം വിട്ടുപോകാം. ആ അസമത്വമാണ് പ്രൊഡക്ഷനിൽ hybrid തിരച്ചിൽ മുന്നിൽ നിൽക്കുന്നതിന്റെ കാരണം.

> **🌍️ യഥാർഥ ഉദാഹരണം:** ഒരു സോഫ്റ്റ്‌വെയർ കമ്പനി അതിന്റെ സഹായ ലേഖനങ്ങൾക്കു മുകളിൽ ഒരു ആന്തരിക സപ്പോർട്ട്-agent ചാറ്റ്ബോട്ട് ഉണ്ടാക്കുന്നു. `ERR_4092` പോലുള്ള കൃത്യമായ പിഴവ് കോഡുകൾ ഉപയോക്താക്കൾ ടൈപ്പ് ചെയ്യുമ്പോൾ ശുദ്ധമായ അർഥാധിഷ്ഠിത തിരച്ചിൽ പരാജയപ്പെട്ടുകൊണ്ടിരുന്നു, കാരണം embedding അതിനെ സാധാരണ ടെക്സ്റ്റായി കണ്ടു. അർഥാധിഷ്ഠിത തിരച്ചിലിനൊപ്പം ഒരു keyword/BM25 തട്ട് ചേർത്തത് (hybrid retrieval) കൃത്യമായ പൊരുത്ത സാഹചര്യങ്ങൾ പരിഹരിച്ചു, ഒപ്പം "എന്റെ export എന്തുകൊണ്ട് കുടുങ്ങിക്കിടക്കുന്നു?" പോലുള്ള അവ്യക്തമായ ആശയപരമായ ചോദ്യങ്ങളിലെ മികച്ച പ്രകടനവും നിലനിർത്തി.
