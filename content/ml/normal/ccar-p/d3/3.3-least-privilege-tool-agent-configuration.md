## Least Privilege — ടൂൾ / Agent ക്രമീകരണം

സുരക്ഷാ എൻജിനീയറിങ്ങിലെ ഏറ്റവും പഴയ ആശയങ്ങളിലൊന്നാണ് least privilege തത്വം, ഇത് Claude agent രൂപകൽപ്പനയിൽ നേരിട്ടും ശക്തമായും ബാധകമാണ്: ഒരു agent-ന് അതിന്റെ യഥാർഥ ജോലി പൂർത്തിയാക്കാൻ വേണ്ട ഏറ്റവും കുറഞ്ഞ ടൂളുകളും അനുമതികളും മാത്രമേ ഉണ്ടാകാവൂ — അതിലധികം ഒന്നുമില്ല. ഒരു agent-ന്റെ ജോലി ഓർഡർ നിലയെക്കുറിച്ചുള്ള ചോദ്യങ്ങൾക്ക് ഉത്തരം നൽകലാണെങ്കിൽ, അതിന് ഓർഡർ റെക്കോർഡുകൾ *വായിക്കാൻ* കഴിയണം; നിങ്ങളുടെ സ്ഥാപനത്തിന്റെ വിശാലമായ ടൂൾ ശേഖരത്തിൽ അവ ഉണ്ടെങ്കിൽപ്പോലും, ഒരു `delete_order` അല്ലെങ്കിൽ `issue_refund` ടൂളിന്റെ ന്യായമായ ആവശ്യം അതിനില്ല.

> **🗣️ ലളിതമായി പറഞ്ഞാൽ:** ഒരു വാതിൽ മാത്രം തുറന്നാൽ മതിയാകുമ്പോൾ Claude-ന് മാസ്റ്റർ താക്കോൽ കൊടുക്കരുത്. എന്തെങ്കിലും നോക്കിയാൽ മാത്രം മതിയെങ്കിൽ, "എന്തെങ്കിലും ആവശ്യം വന്നാലോ" എന്ന് കരുതി മാറ്റാനോ മായ്ക്കാനോ ഉള്ള കഴിവ് കൂടി നൽകരുത്.

### പരമ്പരാഗത സോഫ്റ്റ്‌വെയറിനെക്കാൾ agent-കൾക്ക് ഇത് പ്രധാനമാകുന്നത് എന്തുകൊണ്ട്

പരമ്പരാഗത സോഫ്റ്റ്‌വെയറിൽ, ഇടുങ്ങിയ പരിധിയുള്ള ഒരു ഫങ്ഷനിലെ ബഗ് സാധാരണ ഇടുങ്ങിയ പരിധിയിൽ തന്നെ നിൽക്കും. ഒരു LLM agent-ൽ, ഏത് ടൂൾ വിളിക്കണമെന്ന് തീരുമാനിക്കുന്ന "യുക്തി" ഒരു prompt-നു മേലുള്ള മോഡലിന്റെ സ്വന്തം ന്യായവാദമാണ് — അതായത് അവ്യക്തമായ നിർദേശങ്ങൾ, എതിരായ ഇൻപുട്ടുകൾ (prompt injection), അല്ലെങ്കിൽ ന്യായവാദത്തിലെ അപ്രതീക്ഷിത അതിർത്തി സാഹചര്യങ്ങൾ എന്നിവ അതിനെ സ്വാധീനിക്കുന്നു. ഒരു സപ്പോർട്ട് agent-ന് ഒരു `delete_customer_record` ടൂൾ ലഭ്യമാണെങ്കിൽ, സമർഥമായി എഴുതിയ ഒരു user സന്ദേശമോ, ആശയക്കുഴപ്പമുള്ള ഒരു പല ഘട്ട പദ്ധതിയോ, agent വായിക്കുന്ന ഒരു രേഖയിൽ ഒളിപ്പിച്ച സൂക്ഷ്മമായ ഒരു prompt-injection ആക്രമണമോ ഒരിക്കലും വിളിക്കാൻ പാടില്ലാത്തപ്പോൾ ആ ടൂൾ വിളിക്കപ്പെടാൻ ഇടയാക്കാം. *ഒരേയൊരു* ഭദ്രമായ പ്രതിരോധം, വിളിക്കാൻ ആ ടൂൾ അവിടെ ഇല്ല എന്നതാണ്.

### പരീക്ഷയുടെ പ്രിയപ്പെട്ട കെണി: കഴിവുകളുടെ പെരുപ്പം

കാലക്രമേണ ടൂളുകൾ കൂടിക്കൂടി വന്ന ഒരു agent-നെ വളരെ സാധാരണമായ ഒരു പരീക്ഷാ സാഹചര്യം വിവരിക്കുന്നു — വായന ടൂളുകൾ, എഴുത്ത് ടൂളുകൾ, admin ടൂളുകൾ, മായ്ക്കൽ ടൂളുകൾ — അതിന്റെ യഥാർഥ ജോലിക്ക് വേണ്ടതിലും എത്രയോ കൂടുതൽ. ആ സാഹചര്യത്തിൽ പലപ്പോഴും ആകർഷകമായ *തെറ്റ്* ഉത്തരങ്ങളുണ്ട്: "നാശകരമായ നടപടികൾക്കു മുൻപ് ഒരു സ്ഥിരീകരണ ഘട്ടം ചേർക്കുക," "എന്ത് സംഭവിച്ചെന്ന് അറിയാൻ ലോഗിങ് ചേർക്കുക," "ഒരു human-in-the-loop അനുമതി ചേർക്കുക." പൊതു സുരക്ഷാ രീതിയിൽ ഇവയെല്ലാം യുക്തിസഹമായ *defense-in-depth* നടപടികളാണ്, പക്ഷേ അവ least-privilege പരിഹാരമല്ല; "ഒരു അപകടകരമായ ടൂളിന്റെ നാശ വ്യാപ്തി കുറയ്ക്കുക" എന്നതും "ടൂൾ നീക്കം ചെയ്ത് അപകടം ഇല്ലാതാക്കുക" എന്നതും തമ്മിൽ വേർതിരിക്കാൻ നിങ്ങൾക്ക് കഴിയുമോ എന്നാണ് പരീക്ഷ പരിശോധിക്കുന്നത്. ശരിയായ ഉത്തരം ലഭ്യമാണെങ്കിൽ, അത് മിക്കവാറും എപ്പോഴും ഇതാണ്: **അനാവശ്യ ടൂളുകളും അനുമതികളും പൂർണമായി നീക്കം ചെയ്യുക.**

| സമീപനം | എന്ത് ചെയ്യുന്നു | ഇത് Least Privilege പാലിക്കുന്നുണ്ടോ? |
|---|---|---|
| അനാവശ്യ ടൂളുകൾ നീക്കുക | അപകടകരമായ കഴിവ് വിളിക്കാൻ agent-ന് ഭൗതികമായി കഴിയില്ല | **ഉവ്വ്** — ഇതാണ് യഥാർഥ പരിഹാരം |
| സ്ഥിരീകരണ ചോദ്യങ്ങൾ ചേർക്കുക | അപകടകരമായ നടപടി ഇപ്പോഴും സാധ്യമാണ്, ഒരു ക്ലിക്ക് വേണമെന്ന് മാത്രം | ഇല്ല — അപകടം കുറയ്ക്കുന്നു, പ്രവേശനം ഇല്ലാതാക്കുന്നില്ല |
| Audit ലോഗിങ് ചേർക്കുക | അപകടകരമായ നടപടി നടന്നു എന്ന് സംഭവത്തിനു ശേഷം രേഖപ്പെടുത്തുന്നു | ഇല്ല — കാണാനുള്ള വഴിയാണ്, തടയലല്ല |
| ഒരു മനുഷ്യ അനുമതി ഘട്ടം ചേർക്കുക | അപകടകരമായ നടപടി നടപ്പാക്കും മുൻപ് അനുമതി വേണം | ഇല്ല — സാധ്യത കുറയ്ക്കുന്നു, പക്ഷേ കഴിവ് ഇപ്പോഴും നിലനിൽക്കുന്നു |

ലോഗിങ്, സ്ഥിരീകരണം, അനുമതി ഘട്ടങ്ങൾ വിലപ്പെട്ട *അധിക* നിയന്ത്രണങ്ങളാണ് — പക്ഷേ അപകടകരമായ കഴിവ് ഇപ്പോഴും ഉണ്ടെന്ന് അവ അനുമാനിക്കുന്നു. Least privilege അതിനു മുൻപുള്ള ഒരു ചോദ്യം ചോദിക്കുന്നു: ഈ agent-ന് ആ കഴിവ് *ആവശ്യമുണ്ടോ*? സത്യസന്ധമായ ഉത്തരം ഇല്ല എന്നാണെങ്കിൽ, പരിഹാരം നീക്കം ചെയ്യലാണ് — ആദ്യമേ ഉണ്ടാകാൻ പാടില്ലാത്ത ഒന്നിന് ചുറ്റും ഒരു സുരക്ഷാ വല കെട്ടലല്ല.

> **🌍️ യഥാർഥ ഉദാഹരണം:** ഒരു ആന്തരിക IT-ഹെൽപ്പ്ഡെസ്ക് agent തുടക്കത്തിൽ ഒരൊറ്റ "reset password" ടൂളോടെയാണ് നിർമിച്ചത്, പക്ഷേ കാലക്രമേണ എൻജിനീയർമാർ "disable account," "modify group membership," "delete user" ടൂളുകൾ കൂട്ടിച്ചേർത്തു, "എന്നെങ്കിലും ഉപകാരപ്പെട്ടേക്കാം" എന്ന് കരുതി. സമർഥമായി എഴുതിയ ഒരു ടിക്കറ്റ് വഴി ഏത് അക്കൗണ്ടും പ്രവർത്തനരഹിതമാക്കാൻ agent-നെ കൈകാര്യം ചെയ്യാമെന്ന് ഒരു സുരക്ഷാ പരിശോധന കണ്ടെത്തിയപ്പോൾ, പരിഹാരം ഒരു സ്ഥിരീകരണ ചോദ്യമായിരുന്നില്ല — disable/modify/delete ടൂളുകൾ പൂർണമായി നീക്കി agent-ന് അതിന്റെ യഥാർഥ ജോലിക്ക് വേണ്ട ഒരൊറ്റ ടൂൾ മാത്രം നൽകുകയായിരുന്നു.
