## അപകടസാധ്യത കണ്ടെത്തലും പരാജയ രീതികളും

Guardrail-കൾ ഉണ്ടാക്കും മുൻപ്, *യഥാർഥത്തിൽ എന്തൊക്കെ തെറ്റാം* എന്നതിന്റെ വ്യക്തമായ ഒരു പട്ടിക വേണം. നിഷ്ക്രിയമായി ഓർത്തുവെക്കേണ്ട ഒരു പട്ടികയായല്ല, ഓരോ പുതിയ agentic സിസ്റ്റത്തിനുമെതിരെ പ്രവർത്തിപ്പിക്കേണ്ട ഒരു ചെക്ക്‌ലിസ്റ്റായി architect-മാർ ഇതിനെ കാണണം — ഓരോ പരാജയ രീതിക്കും ചോദിക്കുക: "എന്റെ architecture-ൽ ഇത് എവിടെ സംഭവിക്കാം, ഈ ഡൊമെയ്നിലെ ഏത് guardrail ഇത് പിടിക്കും?"

### ആറ് പരാജയ രീതികളും അവയെ വ്യത്യസ്തമാക്കുന്നതും

**മോഡലിന്റെ സ്വന്തം ന്യായവാദത്തിനുള്ളിൽ** ഉത്ഭവിക്കുന്ന പരാജയങ്ങളും **മോഡൽ പ്രവർത്തിക്കുന്ന സിസ്റ്റത്തിൽ** നിന്ന് ഉണ്ടാകുന്നവയും വേർതിരിക്കുന്നത് സഹായിക്കും.

| ഉത്ഭവം | പരാജയ രീതി | എങ്ങനെ കാണപ്പെടുന്നു |
|---|---|---|
| മോഡൽ തലം | **Hallucination** | Claude വലിയ ആത്മവിശ്വാസത്തോടെ തെറ്റായ ഒന്ന് പറയുന്നു — പുറത്തുനിന്നുള്ള ഒരു ഇൻപുട്ടും ഇതിന് കാരണമായില്ല, മോഡൽ വെറുതെ പിൻബലമില്ലാത്ത ഒരു വാദം ഉണ്ടാക്കി |
| മോഡൽ തലം | **Model drift** | സിസ്റ്റത്തിൽ മറ്റൊന്നും മാറിയിട്ടില്ലെങ്കിലും, ഒരു മോഡൽ version പുതുക്കലിനു ശേഷം പെരുമാറ്റം മാറുന്നു |
| ഇൻപുട്ട് അധിഷ്ഠിതം | **Prompt injection** | User ഇൻപുട്ടിലോ എടുത്ത ഡാറ്റയിലോ ഉള്ള ദുരുദ്ദേശ്യപരമായ ഉള്ളടക്കം സിസ്റ്റം ഉദ്ദേശിച്ച നിർദേശങ്ങളെ മറികടക്കുന്നു |
| ഇൻപുട്ട് അധിഷ്ഠിതം | **Data leakage** | Context-ൽ ഉണ്ടായിരുന്ന സ്വകാര്യമോ സൂക്ഷ്മമോ ആയ ഡാറ്റ ഔട്ട്പുട്ടിൽ പുറത്തുവരുന്നു |
| സിസ്റ്റം തലം | **Cascading failures** | ഒരു agent-ഓ ഘടകമോ പരാജയപ്പെടുന്നു, മറ്റ് ഘടകങ്ങൾ അതിനെ ആശ്രയിക്കുന്നതിനാൽ പരാജയം സിസ്റ്റം മുഴുവൻ പടരുന്നു |
| മാനുഷിക ഘടകം | **Over-reliance** | AI ഫലം സാധാരണ ശരിയായതിനാൽ ഉപയോക്താക്കൾ അത് പരിശോധിക്കാതാകുന്നു, തെറ്റുന്ന സാഹചര്യങ്ങൾ പിടിക്കാതാകുന്നു |

ഈ വിഭജനം പ്രധാനമാണ്, കാരണം ഓരോ വിഭാഗത്തിനും പരിഹാരം വ്യത്യസ്തമാണ്. Hallucination-ൽ നിന്ന് വിശ്വസനീയമായി "prompt വഴി രക്ഷപ്പെടാ"നാകില്ല, പക്ഷേ input validation വഴി prompt injection പിടിക്കാം. മെച്ചപ്പെട്ട prompting വഴി model drift-ഉം പരിഹരിക്കാനാകില്ല — അടിസ്ഥാന മോഡൽ മാറുമ്പോഴെല്ലാം വീണ്ടും വിലയിരുത്തലും regression പരിശോധനയും വേണം. Cascading failures ഒരു മോഡൽ പ്രശ്നത്തെക്കാൾ ഒരു architecture പ്രശ്നമാണ് (isolation, circuit breaker-കൾ, fallback-കൾ). Over-reliance ഒരു മാനുഷിക ഘടക, UX പ്രശ്നമാണ് — മോഡലിലോ pipeline-ലോ ഉള്ള എന്തിനെക്കാളും ഫലം *എങ്ങനെ* അവതരിപ്പിക്കുന്നു എന്നതിലൂടെയാണ് (ആത്മവിശ്വാസ സൂചകങ്ങൾ, സജീവമായ പരിശോധന ആവശ്യപ്പെടൽ) ഇത് പരിഹരിക്കുന്നത്.

### പരാജയ രീതികളെ guardrail-കളുമായി ബന്ധിപ്പിക്കൽ

ഓരോ പരാജയ രീതിയും ഈ ഡൊമെയ്നിൽ മറ്റിടങ്ങളിൽ പറഞ്ഞ പ്രത്യേക guardrail-കളുമായി സ്വാഭാവികമായി ചേരുന്നു:

- **Hallucination** → output filtering, review queue-കൾ (HITL), വിന്യാസത്തിനു മുൻപ് അറിയാവുന്ന ഉത്തരങ്ങളുള്ള ടെസ്റ്റ് സെറ്റുകളുമായി വിലയിരുത്തൽ.
- **Prompt injection** → input validation, ഒപ്പം എടുത്തതോ ബാഹ്യമോ ആയ ഏത് ഉള്ളടക്കത്തെയും user ഇൻപുട്ട് പോലെ വിശ്വസിക്കാനാകാത്തതായി കണക്കാക്കൽ.
- **Data leakage** → PII/സൂക്ഷ്മ മാതൃകകൾക്കായി പ്രത്യേകം output filtering, ഒപ്പം മോഡലിന് എന്ത് context നൽകുന്നു എന്നതിൽ ഡാറ്റ കുറയ്ക്കൽ.
- **Model drift** → ഓരോ മോഡൽ version മാറ്റത്തിനു ശേഷവും, പുതിയ version വ്യാപകമായി വിന്യസിക്കും മുൻപ് വിലയിരുത്തൽ പരിശോധനകൾ വീണ്ടും പ്രവർത്തിപ്പിക്കുക; മോഡൽ പുതുക്കലുകളെ മറ്റേതൊരു അപകടസാധ്യതയുള്ള വിന്യാസം പോലെ കണക്കാക്കുക.
- **Cascading failures** → rate limiting, circuit breaker-കൾ, ഒരു ഘടകത്തിന്റെ പരാജയം ആശ്രിത ഘടകങ്ങളെ തകർക്കാതെ മൃദുവായി താഴ്ത്തുന്ന വിധത്തിൽ agent-കൾ രൂപകൽപ്പന ചെയ്യൽ.
- **Over-reliance** → transparency (AI ഇടപെടലും അനിശ്ചിതത്വവും വെളിപ്പെടുത്തൽ), പ്രത്യാഘാതമുള്ള തീരുമാനങ്ങളിൽ human checkpoint-കൾ, നിഷ്ക്രിയ വിശ്വാസത്തിനു പകരം പരിശോധനയിലേക്ക് സജീവമായി നയിക്കുന്ന UX.

> **🌍️ യഥാർഥ ഉദാഹരണം:** ഒരു multi-agent ഗവേഷണ സഹായി ഒരു ആന്തരിക ഡാറ്റാബേസിൽ നിന്ന് ഡാറ്റ എടുത്ത്, സംഗ്രഹിച്ച്, ക്ലയന്റിന് നൽകുന്ന ഒരു റിപ്പോർട്ട് എഴുതുന്ന drafting agent-ന് സംഗ്രഹം കൈമാറുന്നു. ഒരു ദിവസം: ഡാറ്റാബേസ് agent timeout ആയി നിശ്ശബ്ദമായി ഒരു ഭാഗിക ഫലം നൽകുന്നു (drafting agent അതിനെ പൂർണമായി കണക്കാക്കിയാൽ ഒരു cascading-failure അപകടം); വിടവ് നികത്താൻ drafting agent യുക്തിസഹമെന്ന് തോന്നിക്കുന്ന പക്ഷേ കെട്ടിച്ചമച്ച ഒരു സ്ഥിതിവിവരക്കണക്ക് hallucinate ചെയ്യുന്നു; ഡസൻ കണക്കിന് മുൻ റിപ്പോർട്ടുകളിൽ കുഴപ്പമില്ലാതെ pipeline-ന്റെ ഫലം വിശ്വസിച്ച ക്ലയന്റ് ടീം ആ സംഖ്യ പരിശോധിക്കാതെ റിപ്പോർട്ട് അയക്കുന്നു (over-reliance). പിന്നീടുള്ള ഒരൊറ്റ architecture പരിശോധന, ഒന്നിനുമേൽ ഒന്നായി അടുക്കിയ മൂന്ന് വ്യത്യസ്ത പരാജയ രീതികൾ വെളിപ്പെടുത്തുന്നു — പരിഹാരത്തിന് മൂന്ന് വ്യത്യസ്ത നിയന്ത്രണങ്ങൾ വേണം: മുകൾത്തട്ട് ഡാറ്റ അപൂർണമാണെന്ന് drafting agent അറിയാൻ ഒരു fallback/circuit-breaker, പിൻബലമില്ലാത്ത സംഖ്യാ വാദങ്ങൾ flag ചെയ്യുന്ന ഒരു ഔട്ട്പുട്ട് പരിശോധന, ക്ലയന്റിന് നൽകും മുൻപ് ഏത് റിപ്പോർട്ടിനും ഒരു review-queue നിബന്ധന.

> **⚠️ ശ്രദ്ധിക്കുക:** ഈ പരാജയ രീതികൾ പതിവായി കൂടിച്ചേരുന്നു — മുകളിലെ ഉദാഹരണത്തിലെന്നപോലെ, ഒരൊറ്റ സംഭവ റിപ്പോർട്ട് പലപ്പോഴും രണ്ടോ മൂന്നോ എണ്ണം ഒരുമിച്ച് വെളിപ്പെടുത്തുന്നു. വിവരിച്ച ഒരു സംഭവത്തെ ഒരു കാരണം മാത്രം പറയാതെ അതിന്റെ വ്യത്യസ്ത പരാജയ രീതികളായി വേർതിരിക്കാൻ നിങ്ങൾക്ക് കഴിയുമോ എന്ന് പരീക്ഷ പരിശോധിച്ചേക്കാം.
