Agentic Architecture & Orchestration

How to build systems where Claude works autonomously, uses tools, and coordinates multiple AI agents.

1.1 The Agentic Loop — The Core of Everything

🧠 In Plain English

An "agent" is like giving Claude a job and letting it figure out the steps. Claude doesn't just answer once — it can use tools, see the results, then decide what to do next. This back-and-forth cycle is called the agentic loop.

1. You send a task to Claude
↓
2. Claude thinks and decides what to do next
↓
3. Claude returns a response with a "stop_reason"
↓ (two possible paths)
stop_reason = "tool_use" → Your code runs the tool → Send result back to Claude → LOOP AGAIN
stop_reason = "end_turn" → Claude is done → STOP THE LOOP → Return final answer

The stop_reason Values

ValuePlain English MeaningWhat You Do
tool_useClaude wants to use a toolRun the tool, send result back, loop again
end_turnClaude has finished the taskStop the loop, return the answer
stop_sequenceA custom "stop word" was hitStop per your configuration
max_tokensResponse was cut off — too longHandle as an error — increase token limit or summarise
❌ Anti-patterns — Wrong Ways to Stop the Loop
  • Stopping after N iterations (e.g., "stop after 10 tries") — breaks when tasks need more or fewer steps
  • Parsing text for "done" or "finished" — breaks because Claude's wording varies unpredictably
  • Checking for assistant text as a completion signal — unreliable, not the designed mechanism
✅ The Only Correct Stop Condition
Always stop the loop when and only when stop_reason == "end_turn". Nothing else.

1.2 Multi-Agent Systems — Many Claudes Working Together

🧠 In Plain English

Sometimes one Claude isn't enough. You can have a coordinator Claude (the "manager") that gives tasks to subagent Claudes (the "workers"). Each worker does one specific job, then reports back to the manager.

           ┌─────────────────────┐
           │   COORDINATOR       │  ← The manager Claude
           │   (Orchestrator)    │
           └──────────┬──────────┘
        ┌─────────────┼──────────────┐
        ↓             ↓              ↓
  ┌──────────┐  ┌──────────┐  ┌──────────┐
  │ Subagent │  │ Subagent │  │ Subagent │
  │ (Search) │  │(Analysis)│  │(Writing) │
  └──────────┘  └──────────┘  └──────────┘
  Worker Claude  Worker Claude  Worker Claude

What the Coordinator Does

  • Breaks a big task into smaller pieces
  • Assigns each piece to the right subagent
  • Handles errors when a subagent fails
  • Combines all the results into one final answer
  • Controls what information flows between agents
  • Decides which subagents to use based on the query
⚠️ The Most Important Rule About Subagents
Subagents have NO memory and NO automatic access to the coordinator's information. They only know what the coordinator explicitly sends them in their task prompt. If you forget to include something, the subagent simply won't know it. Ever.

The 3 Multi-Agent Patterns

PatternHow It WorksWhen to Use It
Hub-and-SpokeOne coordinator manages multiple specialist subagentsComplex tasks needing different expertise
PipelineOutput of one agent becomes input to the nextSequential steps where each stage builds on the last
Peer-to-PeerAgents collaborate directly with each otherCollaborative refinement between equal agents

1.3 Spawning Subagents — The Task Tool

🧠 In Plain English

To create a subagent, the coordinator uses the Task tool. This is like the manager sending an assignment to a worker. The coordinator's allowedTools list must include "Task" — otherwise it can't create any workers at all.

Running Subagents in Parallel

If tasks are independent (don't need each other's results), you can run multiple subagents at the same time. The coordinator does this by emitting multiple Task tool calls in a single response — not across separate turns. This saves a lot of time.

💡 What to Always Include in a Subagent's Prompt
  • The complete findings from any previous agents the subagent needs
  • Source information (URLs, document names, page numbers) to preserve where data came from
  • Research goals and quality criteria — not step-by-step instructions (let the subagent decide how)

1.4 Programmatic Enforcement vs. Prompt Instructions

🧠 In Plain English

You can tell Claude what to do in two ways: (1) write it in the instructions (prompt), or (2) write code that forces it. For important business rules, code always wins. Instructions work most of the time, but not 100% — which is unacceptable for things like financial transactions.

Prompt Instruction (Risky)
  • Tells Claude what to do in words
  • Works most of the time
  • Can be ignored or misread
  • Non-zero chance of failure
  • Good for: style, tone, non-critical rules
Programmatic Hook (Safe)
  • Code that intercepts tool calls
  • Works 100% of the time
  • Cannot be overridden
  • Zero chance of failure
  • Good for: money, compliance, safety-critical rules

1.5 Hooks — Intercepting Tool Calls

🧠 In Plain English

Hooks are pieces of code that automatically run before or after Claude uses a tool. You don't have to ask Claude to do anything — hooks run every single time, without fail.

Hook TypeWhen It FiresCommon Use Case
PreToolUseBEFORE the tool runsBlock a refund if it's over $500. Check permissions. Enforce ordering (verify identity BEFORE processing refund).
PostToolUseAFTER the tool runsNormalise the result format. Log to a compliance database. Transform Unix timestamps to readable dates.
📝 Exam Pattern to Remember
When the question says "no exceptions", "must always", "compliance requirement", "financial rule", or "guaranteed to happen" — the answer involves a Hook, not a prompt instruction.

1.6 Task Decomposition — Breaking Big Work Into Small Work

🧠 In Plain English

How you split a big task into subtasks determines everything. The coordinator must be careful to assign ALL parts of a topic — not just some. If the coordinator only assigns "visual art" subtasks, music and writing will be missing from the final report, even if every subagent did its job perfectly.

PatternWhen to Use ItExample
Fixed Sequential (Prompt Chaining)Steps are predictable and always the sameReview each file → then do a cross-file check
Dynamic AdaptiveSteps change based on what you find along the wayExplore a legacy codebase — next steps depend on what you discover

1.7 Session State, Resumption, and Forking

FeatureWhat It DoesWhen to Use It
--resume <name>Continue a named previous sessionLong investigations across multiple work sessions
fork_sessionCreate an independent copy of the current sessionExplore two different approaches without affecting the main session
Fresh session + summaryStart new with a structured summary injectedWhen old tool results are stale after code changes
💡 When to Resume vs. When to Start Fresh
Resume when the old context is still valid. Start fresh when code has changed — old tool results would be stale and misleading. When starting fresh, inject a structured summary of what was found before.

Tool Design & MCP Integration

How to design the tools Claude uses, and how to connect Claude to your backend systems via MCP.

2.1 What is MCP?

🧠 In Plain English

MCP (Model Context Protocol) is like a plug-in system for Claude. It lets you connect Claude to external tools and data sources in a standardised way. Instead of building a custom integration for each tool, MCP gives them all the same "shape" so Claude can use them consistently.

MCP ConceptPlain EnglishExample
MCP ServerA service that exposes tools to ClaudeA server that wraps your company's database
ToolAn action Claude can performprocess_refund, lookup_order
ResourceRead-only data Claude can look atDocumentation, database schemas, issue summaries
isError flagSignals that a tool call failedisError: true when a database times out

2.2 Writing Good Tool Descriptions — Most Important in This Domain

🧠 In Plain English

Claude reads tool descriptions to decide which tool to use. If your descriptions are vague or too similar to each other, Claude will pick the wrong one. This is the #1 cause of tool selection errors.

Bad Descriptions (Causes Wrong Tool Picks)
  • get_customer — "Retrieves customer information"
  • lookup_order — "Retrieves order details"
  • Result: Claude picks get_customer for order questions 45% of the time
Good Descriptions (Precise and Different)
  • get_customer — "Gets customer profile (name, tier, contact). Use when query is about WHO the customer IS. Input: customer email or ID."
  • lookup_order — "Gets order history, status, items. Use when query is about what they BOUGHT or ORDER STATUS. Input: order number."

What Makes a Good Tool Description

  • Clear purpose — what the tool does in one sentence
  • Input format — what parameters it expects
  • Example queries that should trigger this tool
  • Edge cases — when NOT to use it
  • How it differs from similar tools
📝 Exam Rule — Fix Descriptions First
If tool selection is wrong, the exam always expects you to fix the tool descriptions first before building complex routing logic or classifiers. Descriptions are the root cause. Fix the root cause.

2.3 Structured Error Responses

🧠 In Plain English

When a tool fails, don't just return an empty result or a generic "failed" message. Return a structured error that tells Claude exactly what went wrong, whether to retry, and what alternatives exist.

Error TypePlain EnglishisRetryable?Claude's Action
TransientTemporary (timeout, server down)✅ YesRetry with backoff
ValidationBad input (wrong format, missing field)❌ NoFix the input, don't retry same way
BusinessPolicy violation (refund too large)❌ NoExplain to user, escalate
PermissionNot allowed to do this❌ NoEscalate or report
// Good structured error response
{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "message": "Database timeout after 30s",
  "retryAfterSeconds": 5
}

// Bad — Claude cannot decide what to do
{ "status": "failed" }

2.4 Too Many Tools = Worse Performance

🧠 In Plain English

Giving Claude 18 tools when it only needs 4 makes it confused. The more tools Claude has to choose from, the more likely it is to pick the wrong one. Each subagent should only have the tools it actually needs for its job.

tool_choice OptionWhat It MeansWhen to Use
"auto"Claude decides whether to use a tool or just respondGeneral conversations where tool use is optional
"any"Claude MUST call at least one tool (but can choose which)When you always need structured output — no prose allowed
{"type":"tool","name":"X"}Claude MUST call this specific toolWhen you need a specific tool to run first (e.g., metadata extraction before enrichment)

Claude Code Configuration & Workflows

How to set up Claude Code for your team using configuration files, custom commands, and rules.

3.1 CLAUDE.md — The Main Configuration File

🧠 In Plain English

CLAUDE.md is a file you write that tells Claude about your project — your coding rules, what NOT to do, what tools to use, etc. Claude reads this file every time a session starts. Think of it as a permanent briefing document.

The 3-Level Configuration Hierarchy

Level 1: User Level (Personal)       → ~/.claude/CLAUDE.md
          Only applies to YOU. Not shared with teammates. Not in git.

Level 2: Project Level (Team)        → ./CLAUDE.md  or  .claude/CLAUDE.md
          Applies to EVERYONE on the team. Shared via git. ← Most important

Level 3: Directory Level (Specific)  → any subfolder's CLAUDE.md
          Applies only when working in that specific folder.
✅ The Golden Rule
Team rules belong in the project-level CLAUDE.md. If a new developer joins and doesn't get the rules, it's because someone put them in the user-level file instead of the project-level file.

Keeping CLAUDE.md Organised — @import and .claude/rules/

MethodWhat It DoesUse When
@import filename.mdPulls in another file's contentSplitting standards into separate files per topic
.claude/rules/ folderSeparate rule files per topicWhen CLAUDE.md is too long (500+ lines)
Path scoping with glob patternsRules only load for matching filese.g., test rules only load for *.test.tsx files

3.2 Path-Specific Rules — Conditional Loading

🧠 In Plain English

You can write rules that only activate when Claude is editing certain types of files. For example, testing rules only load when Claude is editing a test file. This keeps the context clean and avoids confusing Claude with irrelevant rules.

# File: .claude/rules/testing.md
---
paths: ["**/*.test.tsx", "**/*.spec.ts"]   ← Only loads for test files
---

All tests must follow the AAA pattern (Arrange, Act, Assert).
Every function must have at least one unit test.
Use describe() for groups and it() for individual tests.
💡 Use Glob Patterns for Files Spread Across the Codebase
Use .claude/rules/ with glob patterns (like **/*.test.tsx) when your conventions apply to files that are spread across many folders. Directory-level CLAUDE.md files can't handle this case well.

3.3 Custom Slash Commands & Skills

🧠 In Plain English

Slash commands are shortcuts your team can type to run a pre-defined workflow. For example, /project:review-pr could run your entire code review checklist automatically. Skills are similar but more powerful — they run in their own isolated context and have extra configuration options.

TypeLocationWho Can Use ItGood For
Project Command.claude/commands/Everyone on team (in git)Shared workflows like PR reviews, deployments
Personal Command~/.claude/commands/Only youPersonal shortcuts
Project Skill.claude/skills/Everyone on teamComplex workflows with isolation needed
Personal Skill~/.claude/skills/Only youPersonal variants that don't affect teammates

Skill Frontmatter Options (in SKILL.md)

OptionWhat It Does
context: forkRuns the skill in its own isolated sub-session. Output doesn't pollute your main conversation. Use for verbose analysis skills.
allowed-tools: [Read, Write]Limits which tools the skill can use. Prevents destructive actions.
argument-hint: "PR number"Prompts the developer to provide required parameters when invoking the skill without arguments.

3.4 Plan Mode vs. Direct Execution

🧠 In Plain English

Plan mode: Claude first shows you a plan of what it's going to do, waits for your approval, then executes. Like a contractor showing blueprints before construction.
Direct execution: Claude just does it immediately. Like a contractor fixing a dripping tap without blueprints.

Use Plan Mode When…Use Direct Execution When…
Large-scale changes (45+ files)Simple, single-file bug fix
Architectural decisionsAdding a date validation check
Multiple valid approaches existThe fix is obvious and well-understood
Library migrationRenaming a variable
Microservice restructuringFixing a typo in documentation

3.6 Claude Code in CI/CD Pipelines

🧠 In Plain English

CI/CD pipelines are automated systems that run when code is pushed (checking quality, running tests, etc.). Claude Code can be part of this — but it needs special flags to work in an automated environment where there's no human to answer prompts.

Flag / FeatureWhat It DoesWhy It Matters for CI/CD
-p or --printNon-interactive mode — runs and exits without waiting for inputWithout this, the pipeline hangs forever waiting for a human
--output-format jsonReturns output as JSON instead of textMachines can parse JSON; plain text is hard to process automatically

💡 Independent Review Instances
The same Claude session that generated code is less effective at reviewing that same code. It remembers its own reasoning and is less likely to question its own decisions. Use a separate, independent Claude instance for reviews — it hasn't seen the generation context and will catch more issues.

Prompt Engineering & Structured Output

How to write instructions that get reliable, well-structured results from Claude every time.

4.1 Explicit Criteria vs. Vague Instructions

🧠 In Plain English

Vague instructions like "be conservative" or "only report high-confidence issues" do NOT work. Claude doesn't know what "conservative" means in your context. You need to spell out exactly what to report and what to skip.

Vague (Doesn't Work)
  • "Check that comments are accurate"
  • "Only report high-confidence findings"
  • "Be conservative in your review"
  • Result: too many false positives, developers stop trusting it
Specific (Works)
  • "Flag ONLY when claimed behavior contradicts actual code behavior"
  • "Skip minor style and local patterns"
  • "Report bugs and security issues. Ignore formatting."
  • Result: accurate, trusted findings

4.2 Few-Shot Prompting — Teaching by Example

🧠 In Plain English

Few-shot prompting means giving Claude 2–4 examples of exactly what you want before asking it to do the real task. It's the single most effective way to get consistent, correctly formatted output when descriptions alone aren't enough.

Extract issue severity from the code comment below.

EXAMPLE 1:
Code: "TODO: fix null check here or app crashes"
Output: {"severity": "high", "type": "bug", "location": "null_check"}

EXAMPLE 2:
Code: "// might want to refactor this later"
Output: {"severity": "low", "type": "style", "location": "general"}

NOW DO THIS:
Code: "WARNING: race condition possible under concurrent load"
Output: ???

When Few-Shot Examples Work Best

  • Ambiguous cases where the right answer isn't obvious
  • Specific output format that's hard to describe in words
  • Reducing false positives by showing what to SKIP
  • Documents with varied structures (inline citations vs bibliographies)
  • When you need Claude to generalise to patterns you haven't specified

4.3 Enforcing Structured Output — tool_use + JSON Schema

🧠 In Plain English

The most reliable way to get structured data from Claude (like JSON) is to use tool_use with a JSON schema. This is better than just asking Claude to "respond in JSON" — it guarantees the format is correct every time.

✅ The Key Distinction — Structure vs. Meaning

JSON schema guarantees structure (correct field names, correct types, no missing braces). It does NOT guarantee meaning (that numbers add up, that dates are logical, that the content is accurate). A response can be syntactically valid JSON and still contain wrong data.

Schema Design — Required, Optional, and Enums

{
  "type": "object",
  "properties": {
    "invoice_number": { "type": "string" },          // Required field
    "total_amount":   { "type": "number" },           // Required field
    "discount_code":  { "type": ["string", "null"] }, // Optional — null if not found
    "status": {
      "type": "string",
      "enum": ["pending", "paid", "overdue", "other"] // Must be one of these values
    },
    "status_detail": { "type": "string" }             // Used when status = "other"
  },
  "required": ["invoice_number", "total_amount", "status"]
}
💡 Use Nullable Fields to Prevent Hallucination
If a field might not exist in the source document, make it nullable (["string", "null"]). This way Claude returns null when it's not found, instead of making up a plausible-sounding answer. Required fields + absent data = hallucination risk.

4.4 Validation, Retry, and Feedback Loops

🧠 In Plain English

When Claude's output fails validation, don't just try again with the same prompt. Send back the specific error so Claude knows what to fix. This retry-with-feedback approach is much more effective than blind retrying.

# First attempt fails validation:
# Error: "calculated_total (£485) does not match sum of line_items (£510)"

# Second attempt — include the error in the prompt:
prompt = f"""
Original document: {document}
Your previous extraction: {failed_extraction}
Validation error: calculated_total (£485) does not match sum of line_items (£510)
Please correct the extraction.
"""
⚠️ Retries Won't Help When Information Is Missing
If the required information simply doesn't exist in the document (e.g., the document references a figure from an external table you didn't provide), no amount of retrying will fix it. Retries only help for format errors and structural mistakes.

4.6 Multi-Pass Review Architecture

🧠 In Plain English

When reviewing 14 files all at once, Claude pays full attention to some files and barely notices others. The fix is to review one file at a time (for local issues), then do a separate pass looking at how all the files interact (for cross-file issues).

PassWhat It ReviewsOutput
Pass 1: Per-fileEach file individually — local bugs, style, logic errorsFile-specific findings
Pass 2: IntegrationHow all files interact — data flow, shared state, API contractsCross-file findings

Context Management & Reliability

How to handle long conversations, manage errors gracefully, and build reliable production systems.

5.1 The Lost-in-the-Middle Effect

🧠 In Plain English

Claude pays more attention to the beginning and end of long documents. Information in the middle of a very long input tends to get missed or forgotten. This is called the "lost-in-the-middle" effect.

FixDoes It Work?Why
Move key findings to the TOP of the document✅ Yes — Best fixClaude reliably reads the beginning
Add clear section headers throughout✅ YesHeaders act as navigation anchors Claude can follow
Use a larger context window model❌ NoBigger window doesn't fix where info is positioned inside it
Summarise the whole document first❌ RiskyLoses exact numbers, dates, and specific values
Run Claude multiple times, average results❌ NoStructural problem — doesn't fix where info sits

Trimming Verbose Tool Outputs

🧠 In Plain English

If a tool returns 40 fields but you only need 5, all 40 fields take up space in Claude's context window. Trim the output to only the relevant fields before passing it to Claude. This saves tokens and keeps context clean.

5.2 Escalation — When to Hand Off to a Human

🧠 In Plain English

Not every issue should be handed to a human. Escalating too often wastes resources; not escalating enough leads to errors. You need clear, specific rules about when to escalate.

Escalation TriggerReliable?Why
Customer explicitly asks for a human✅ YesUnambiguous. Always honour it immediately.
Policy gap — situation not covered by policy✅ YesAgent cannot make a policy judgement it doesn't have authority for
Agent cannot make progress after retries✅ YesObjective evidence of failure — no guessing needed
Multiple customer matches — needs clarification✅ YesShould ask for more identifiers, not guess which customer
Sentiment analysis detects frustration❌ NoInaccurate signal. Frustration ≠ case complexity.
Claude self-reports low confidence❌ NoModels are poorly calibrated at rating their own confidence
A classifier flags the message❌ NoAdds another failure point on top of the first
📝 Exam Pattern — Escalation Scenarios
The exam will offer sentiment analysis and confidence scores as attractive-sounding options. These are always wrong. Always choose explicit policy-based triggers.

5.3 Error Propagation in Multi-Agent Systems

🧠 In Plain English

When a subagent fails, it must report back to the coordinator with enough detail for the coordinator to make a smart decision. A generic "failed" message is useless. A structured error message with what was tried and what's available is valuable.

ApproachProblem
Return empty result as success❌ Coordinator thinks it succeeded — makes decisions on missing data
Stop the entire workflow on one failure❌ Wastes all the work done by other agents
Return generic "search unavailable"❌ Coordinator can't decide whether to retry, find alternative, or skip
Return structured error with failure type, what was tried, partial results, alternatives✅ Coordinator can make an intelligent recovery decision

5.4 Managing Context in Long Codebase Exploration

🧠 In Plain English

In very long sessions, Claude starts to "forget" specific details it found earlier and begins referencing "typical patterns" instead of actual code it saw. This is called context degradation.

  • Scratchpad files — save key findings to a file; reference it in future questions
  • Subagent delegation — spawn subagents for verbose exploration; main agent keeps high-level coordination
  • /compact command — summarises and compresses the session context to free up space
  • Structured state exports — each agent saves its state to a file; coordinator loads it on resume (crash recovery)

5.5 Human Review Workflows & Confidence Calibration

🧠 In Plain English

Don't trust a single "97% accuracy" number. That might mean it's 100% accurate on common documents but terrible on rare document types. Check accuracy by document type and by individual field before reducing human review.

  • Stratified sampling — regularly check a sample of "high confidence" extractions to catch new error patterns
  • Field-level confidence scores — Claude rates confidence for each field separately, not just overall
  • Calibrate with labeled data — compare Claude's confidence ratings to actual correct/incorrect answers to set the right routing thresholds
  • Route ambiguous cases to humans — when source document has conflicting information, send to human instead of guessing

5.6 Information Provenance — Keeping Track of Where Data Came From

🧠 In Plain English

When multiple agents summarise and combine information, it's easy to lose track of which claim came from which source. Good systems preserve this "provenance" — the trail from claim back to original source.

ProblemSolution
Two sources give different statisticsReport BOTH values with source attribution — don't pick one
Sources have different dates (temporal conflict)Include publication dates in structured outputs — not a real conflict if from different years
Source attribution lost during summarisationSubagents must output structured claim-source mappings that downstream agents must preserve
Financial data and narrative mixed in one outputFinancial data → tables; News → prose; Technical findings → structured lists. Don't convert everything to one format.

Scenario A: Customer Support Agent

Q1 · Domain 1 — Agentic Architecture
Production data shows that in 12% of cases, your agent skips get_customer entirely and calls lookup_order using only the customer's stated name — occasionally leading to misidentified accounts and incorrect refunds. What change would most effectively address this reliability issue?
  • A. Add a programmatic prerequisite that blocks lookup_order and process_refund calls until get_customer has returned a verified customer ID.
  • B. Enhance the system prompt to state that customer verification is mandatory before any order operations.
  • C. Add few-shot examples showing the agent always calling get_customer first.
  • D. Implement a routing classifier that enables only the right tools per request type.
✅ Why A: When a tool sequence is required for critical business logic (identity verification before refunds), you need programmatic enforcement — code that blocks the next tool until the first one completes. B and C rely on Claude following instructions probabilistically — which means sometimes it won't. Financial errors have real consequences, so "sometimes" is not acceptable. D addresses tool availability, not tool ordering, which is the actual problem.
Q2 · Domain 2 — Tool Design & MCP
Production logs show the agent frequently calls get_customer when users ask about orders (e.g., "check my order #12345"), instead of calling lookup_order. Both tools have minimal descriptions. What's the most effective first step?
  • A. Add 5-8 few-shot examples showing correct tool selection patterns.
  • B. Expand each tool's description to include input formats, example queries, edge cases, and boundaries explaining when to use it versus similar tools.
  • C. Implement a routing layer that parses user input and pre-selects the tool based on keywords.
  • D. Consolidate both tools into one lookup_entity tool.
✅ Why B: Tool descriptions are the primary mechanism Claude uses to pick a tool. Minimal descriptions are the root cause. Fix the root first — it's low effort and high impact. A adds token overhead without fixing the underlying issue. C builds routing infrastructure on top of a broken foundation. D is a valid architectural choice but too heavy for a "first step" fix.
Q3 · Domain 5 — Context Management & Reliability
Your agent achieves 55% first-contact resolution (target: 80%). Logs show it escalates straightforward cases while attempting to handle complex ones autonomously. What's the most effective fix?
  • A. Add explicit escalation criteria to your system prompt with few-shot examples showing when to escalate vs. resolve autonomously.
  • B. Have the agent self-report a confidence score (1-10) and escalate when below a threshold.
  • C. Deploy a separate classifier trained on historical tickets to predict escalation before the agent starts.
  • D. Implement sentiment analysis to detect frustration and escalate above a threshold.
✅ Why A: The root cause is unclear decision boundaries — the agent doesn't know which cases to escalate. Explicit criteria + few-shot examples directly fixes this. B fails because LLM self-reported confidence is poorly calibrated. C is over-engineered — try prompting first. D solves a completely different problem (frustration ≠ complexity).

Scenario B: Code Generation with Claude Code

Q4 · Domain 3 — Claude Code
You want to create a custom /review slash command that runs your team's standard code review checklist. It should be available to every developer when they clone the repository. Where should you create this command file?
  • A. In the .claude/commands/ directory in the project repository
  • B. In ~/.claude/commands/ in each developer's home directory
  • C. In the CLAUDE.md file at the project root
  • D. In a .claude/config.json file with a commands array
✅ Why A: Project-scoped commands in .claude/commands/ are version-controlled and automatically available to all developers on clone or pull. B is personal — not shared. C is for instructions, not command definitions. D doesn't exist.
Q5 · Domain 3 — Claude Code
You've been assigned to restructure a monolithic application into microservices — changes across dozens of files, decisions about service boundaries and dependencies. Which approach should you take?
  • A. Enter plan mode to explore the codebase, understand dependencies, and design an implementation approach before making changes.
  • B. Start with direct execution and make changes incrementally, letting implementation reveal natural service boundaries.
  • C. Use direct execution with comprehensive upfront instructions detailing exactly how each service should be structured.
  • D. Begin in direct execution and only switch to plan mode if you encounter unexpected complexity.
✅ Why A: Plan mode is designed for large-scale changes with architectural decisions and multiple valid approaches — exactly this scenario. B risks costly rework when dependencies are discovered late. C assumes you already know the right structure. D ignores that the complexity is already stated in the task.
Q6 · Domain 3 — Claude Code
Your codebase has React components (functional style), API handlers (async/await error handling), and database models (repository pattern). Test files are spread throughout (e.g., Button.test.tsx next to Button.tsx). What's the most maintainable way to ensure Claude applies the right conventions per file type automatically?
  • A. Create rule files in .claude/rules/ with YAML frontmatter specifying glob patterns to conditionally apply conventions based on file paths
  • B. Consolidate all conventions in root CLAUDE.md under headers for each area, relying on Claude to infer which section applies

✅ Why A: Glob patterns like **/*.test.tsx work regardless of directory location — essential for test files spread across the codebase. B relies on inference — unreliable. Scenario C: Multi-Agent Research System

Q7 · Domain 1 — Agentic Architecture
After running the system on "impact of AI on creative industries," each subagent completes successfully. However, the final reports cover only visual arts — missing music, writing, and film. Coordinator logs show it decomposed the topic into: "AI in digital art," "AI in graphic design," "AI in photography." What is the most likely root cause?
  • A. The synthesis agent lacks instructions for identifying coverage gaps.
  • B. The coordinator agent's task decomposition is too narrow — subagent assignments don't cover all relevant domains.
  • C. The web search agent's queries aren't comprehensive enough.
  • D. The document analysis agent is filtering out non-visual sources.
✅ Why B: The coordinator's logs prove the root cause — it only assigned visual arts subtasks. Subagents did exactly what they were assigned. The problem is what they were assigned. A, C, D blame downstream agents that performed correctly within their scope.
Q8 · Domain 5 — Context & Reliability
The web search subagent times out while researching a complex topic. How should this failure flow back to the coordinator to enable intelligent recovery?
  • A. Return structured error context to the coordinator including failure type, attempted query, any partial results, and potential alternative approaches.
  • B. Automatic retry with exponential backoff within the subagent, then return generic "search unavailable" after all retries.
  • C. Catch the timeout and return an empty result set marked as successful.
  • D. Propagate the timeout exception to a top-level handler that terminates the entire research workflow.
✅ Why A: Structured error context gives the coordinator what it needs to decide: retry with different query? Try alternative? Proceed with partial results? B hides valuable context behind a generic message. C marks failure as success — coordinator will proceed with missing data. D kills the entire job over one subagent failure.
Q9 · Domain 2 — Tool Design & MCP
The synthesis agent frequently returns control to the coordinator for simple fact verifications (dates, names, statistics), adding 2-3 round trips per task (40% extra latency). 85% are simple checks; 15% require deeper investigation. What's the most effective approach?
  • A. Give the synthesis agent a scoped verify_fact tool for simple lookups, while complex verifications continue delegating through the coordinator.
  • B. Have the synthesis agent accumulate all verification needs and send them as a batch to the coordinator at the end.
  • C. Give the synthesis agent access to all web search tools.
  • D. Have the web search agent cache extra context proactively, anticipating what the synthesis agent might need.
✅ Why A: Least privilege — give synthesis only what it needs for the 85% common case. Coordinator handles the 15% complex cases. B creates blocking dependencies since synthesis steps may depend on earlier verified facts. C over-provisions synthesis, violating separation of concerns. D is speculative caching that can't reliably predict what will be needed.

Scenario D: Claude Code for CI/CD

Q10 · Domain 3 — Claude Code
Your pipeline script runs claude "Analyse this pull request for security issues" but the job hangs indefinitely. Logs show Claude Code is waiting for interactive input. What's the correct fix?
  • A. Add the -p flag: claude -p "Analyse this pull request for security issues"
  • B. Set the environment variable CLAUDE_HEADLESS=true before running
  • C. Redirect stdin from /dev/null
  • D. Add the --batch flag
✅ Why A: The -p (or --print) flag is the documented way to run Claude Code in non-interactive mode. It processes the prompt and exits without waiting for user input. B, C, and D reference non-existent features or Unix workarounds that don't properly address this.
Q11 · Domain 4 — Prompt Engineering
Your manager proposes switching both (1) a blocking pre-merge check and (2) an overnight technical debt report to the Message Batches API for 50% cost savings. How do you evaluate this?
  • A. Use batch processing for technical debt reports only; keep real-time calls for pre-merge checks.
  • B. Switch both to batch with status polling.
  • C. Keep real-time calls for both to avoid batch ordering issues.
  • D. Switch both to batch with a timeout fallback to real-time.
✅ Why A: Batches take up to 24 hours — unacceptable for blocking pre-merge checks where developers wait. For overnight reports, 24-hour processing is fine. Match each workflow to the right API. B relies on "often faster" which isn't acceptable for blocking flows. C is wrong — batch results are correlated via custom_id. D adds unnecessary complexity.
Q12 · Domain 4 — Prompt Engineering
A PR modifies 14 files. Single-pass review gives inconsistent results: detailed for some files, superficial for others, missed obvious bugs, and contradictory feedback — flagging a pattern in one file while approving identical code elsewhere. How should you restructure?
  • A. Split into focused passes: analyse each file individually for local issues, then run a separate integration-focused pass examining cross-file data flow.
  • B. Require developers to split large PRs into smaller submissions of 3-4 files.
  • C. Switch to a higher-tier model with a larger context window.
  • D. Run three independent passes on the full PR and only flag issues appearing in at least two of three runs.
✅ Why A: File-by-file analysis ensures consistent depth. A separate integration pass catches cross-file issues. This directly fixes attention dilution. B shifts burden to developers without improving the system. C misunderstands that bigger context windows don't solve attention quality issues. D would suppress detection of real bugs by requiring consensus.

The 12 Rules You Must Know Cold

  • Stop the agentic loop ONLY on stop_reason == "end_turn". Never on iteration count or text parsing.
  • Subagents know ONLY what the coordinator explicitly passes in their task prompt. No automatic inheritance. Ever.
  • Incomplete output from a multi-agent system → coordinator's task decomposition was too narrow.
  • High-stakes rules (financial, compliance, safety) → use hooks, not prompt instructions.
  • PreToolUse hooks = block before execution. PostToolUse hooks = log/transform after execution.
  • CLAUDE.md at project root = team-shared (in git). ~/.claude/CLAUDE.md = personal only (not in git).
  • Project commands (.claude/commands/) = shared. Personal commands (~/.claude/commands/) = local.
  • JSON schema guarantees structure, not truth. Numbers can be syntactically valid and logically wrong.
  • Put critical content at the TOP of long documents. Lost-in-middle effect = middle content gets missed.
  • Fix tool descriptions before building routing infrastructure. Descriptions are always the root cause.
  • Message Batches API (50% cheaper, up to 24hr) = for non-blocking jobs only. Never for pre-merge checks.
  • Use -p flag for Claude Code in CI/CD pipelines. Without it, the pipeline hangs waiting for human input.

The 6 Exam Traps — Wrong Answers That Look Right

  • "Add a system prompt instruction" — wrong when the rule requires guaranteed compliance. Use a hook instead.
  • "Sentiment analysis for escalation" — wrong. Frustration ≠ complexity. Never a reliable escalation trigger.
  • "Model self-reported confidence score" — wrong. LLMs are poorly calibrated at rating their own confidence.
  • "Larger context window" — wrong for lost-in-middle. Bigger window doesn't fix where content is placed.
  • "Run multiple times and average" — wrong. Doesn't fix structural problems; just adds cost and latency.
  • "Stop after N iterations" — wrong loop termination. Always stop on stop_reason == "end_turn".
