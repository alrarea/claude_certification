Solution Design & Architecture

Turning a business problem into the right Claude-based architecture — and justifying every decision.

What this domain is really about

Imagine a company comes to you and says: "We want to use AI to improve our customer service." Your job is to figure out: What kind of system should we build? Which parts should use Claude? How do we connect everything? What are the trade-offs? This domain tests that thinking.

1.1 Translating Business Problems into AI Solutions

Before writing any code, a professional architect must understand what the business actually needs. The exam tests whether you can identify the right solution — not just the most technically impressive one.

The Business Value Pillars

PillarWhat It MeansExample
EfficiencyDo the same work faster or with fewer peopleAuto-draft email replies for support team
TransformationDo entirely new things that were not possible beforeAI that analyses legal contracts in seconds
ProductivityHelp people do their existing jobs betterCode review assistant for developers
Cost ReductionReduce spending through automationReplace manual data entry with AI extraction
Performance SLAsMeet speed and reliability targetsResponse under 2 seconds for 99% of queries

1.2 Architectural Patterns — Which to Choose

PatternWhat It IsUse When
WorkflowFixed sequence of steps; Claude is one componentSteps are known in advance; predictable process
AgenticClaude decides steps dynamically; uses tools in a loopSteps depend on intermediate results; unpredictable task
Augmented LLMClaude + retrieval + tools but without full autonomyNeed grounded answers from documents/databases
Exam Decision Rule
The exam often asks: "Which pattern is appropriate?" Rule of thumb: if the steps are known → workflow. If Claude needs to figure out the steps → agentic. If you need accurate, grounded answers from a knowledge base → augmented LLM (RAG).

1.3 Multi-Agent System Design

Complex tasks are split across multiple specialised agents. The architect must design how they communicate, how errors propagate, and how results are combined.

Key Design Decisions for Multi-Agent Systems

  • Topology: Hub-and-spoke vs. pipeline vs. peer-to-peer
  • Context isolation: what each agent knows vs. needs to know
  • Error propagation: does one failure stop the whole system?
  • Result aggregation: how does the final answer get assembled?
  • Human checkpoints: where should a human approve before continuing?

1.4 Decomposition Techniques

Large, complex problems must be broken into smaller, manageable tasks. Poor decomposition is the #1 cause of missing or wrong output in multi-agent systems.

TechniqueHow It Works
Functional decompositionSplit by what each part does (research, write, review)
Data decompositionSplit by the data being processed (one agent per document)
Domain decompositionSplit by business domain (legal agent, finance agent, HR agent)

1.5 End-to-End Architecture Design

A complete architecture must specify all stages:

The Full Loop
Input (user query / data source) → Processing (Claude + tools + retrieval) → Output (response / action) → Feedback Loop (evaluation → improvement) → back to design refinement

Claude Models, Prompting & Context Engineering

Choosing the right model, engineering effective prompts, and managing tokens efficiently.

What this domain is really about

Not all Claude models are the same. Some are faster, some are smarter, some cost more. This domain tests whether you can pick the right model for the job, write prompts that work reliably, and use the context window efficiently so you don't waste money or slow things down.

2.1 Model Selection Trade-offs

FactorSmaller / Faster ModelLarger / Smarter Model
Latency✅ Faster response❌ Slower response
Cost per token✅ Cheaper❌ More expensive
Complex reasoning❌ May struggle✅ Handles better
Simple classification✅ Usually sufficient❌ Overkill
Long documents❌ Smaller context✅ Larger context window
Exam Decision Rule
The exam presents a scenario and asks which model tier is appropriate. Key signals: "latency-sensitive" → smaller model. "Complex multi-step reasoning" → larger model. "High volume, low complexity" → smallest model + caching.

2.2 Prompt Engineering Techniques

TechniqueWhat It IsUse When
Zero-shotGive the task only, no examplesSimple, well-defined tasks
Few-shotGive the task + 2–5 examples of good answersEdge cases, specific output format, ambiguous tasks
Chain-of-thoughtAsk Claude to reason step-by-step before answeringComplex reasoning, maths, multi-step decisions

2.3 System Prompt Design

The system prompt is the most authoritative instruction Claude receives. It sets the agent's identity, constraints, and behaviour. It cannot be overridden by user messages.

What a Good System Prompt Contains

  • Role definition — who Claude is in this context
  • Task boundaries — what it should and should not do
  • Output format — how responses should be structured
  • Guardrails — safety and policy constraints
  • Tone — formal, friendly, technical, etc.

2.4 Prompt Caching — Cost and Latency Optimisation

Simple Explanation

If you send the same 8,000-token system prompt on every API call, you are paying to process those same 8,000 tokens every single time. Prompt caching lets Claude reuse the processing from the first call — saving both time and money on every subsequent call.

The Rule
Always put STATIC content (system prompt, policy documents, reference material) FIRST in the request. Put DYNAMIC content (user's question, variable data) LAST. This maximises the cacheable prefix and gives the biggest savings.

2.5 Context Window Management

StrategyHow It WorksTrade-off
Progressive summarisationSummarise older turns to free spaceLoses exact wording
External memoryStore details in DB, retrieve on demandAdds retrieval latency
Modular prompts / SkillsOnly load relevant prompt sectionsRequires upfront organisation
Prompt cachingCache static prefix across callsContent must be truly static

2.6 Token Usage Optimisation

  • Remove filler words and repetition from prompts
  • Use structured formats (JSON, XML) instead of prose for data
  • Set appropriate max_tokens to avoid over-generation
  • Use stop sequences to end generation early when possible
  • Cache static system prompts — biggest single saving

Integration

Connecting Claude to real-world systems — the largest and most diverse domain in this exam.

What this domain is really about

Claude does not exist alone. It connects to databases, APIs, tools, and other systems. This domain tests whether you can design those connections securely and correctly — choosing the right integration method, avoiding security gaps, and making sure the system is observable and debuggable in production.

3.1 Integration Protocol Selection

Three main ways to integrate Claude with external systems. The exam tests which one to choose.

ProtocolWhat It IsChoose When
MCP (Model Context Protocol)Standardised protocol for exposing tools and resources to ClaudeYou want a reusable, standardised tool layer; team-shared tooling
API / CLIDirect API calls from your code to Claude or to external servicesCustom integrations; tight control over request/response; simple pipelines
Agent-to-AgentOne Claude agent communicates with another Claude agentMulti-agent systems; task delegation; specialised subagents

3.2 RAG — Retrieval-Augmented Generation

What is RAG? (Very simple)

Imagine Claude is very smart but doesn't know your company's internal documents. RAG solves this: before answering a question, Claude first searches your documents to find relevant information, then uses that information to give an accurate answer. It's like giving Claude a reference book to look up before speaking.

RAG Pipeline — Full Design

StageWhat HappensKey Decisions
1. IngestionDocuments are loaded into the systemWhich documents? How often to update?
2. ChunkingDocuments split into smaller piecesChunk size, overlap, boundary strategy
3. EmbeddingEach chunk converted to a vector (number array)Which embedding model? Dimensions?
4. IndexingVectors stored in a searchable databaseVector DB choice, metadata, indexing method
5. RetrievalUser query → find most relevant chunksSemantic search, keyword, hybrid?
6. GenerationRetrieved chunks + query sent to ClaudeHow many chunks? Where in context?

Chunking Strategies

StrategyHowBest For
Fixed-sizeSplit every N tokens regardless of contentSimple, fast — works for uniform content
Semantic / paragraphSplit at natural boundaries (paragraphs, sections)Narrative documents, articles
HierarchicalLarge chunks + small chunks; retrieve at both levelsLong documents needing both context and precision
Sliding windowOverlapping chunks to avoid cutting mid-ideaPrevents information loss at boundaries

Retrieval Strategies

StrategyHow It WorksBest For
Semantic (vector) searchFind chunks with similar meaning to queryConceptual questions; "explain X" queries
Keyword (BM25) searchFind chunks containing exact query wordsSpecific names, codes, product IDs
Hybrid searchCombine semantic + keyword resultsBest of both — most production systems use this
Re-rankingUse a second model to re-score retrieved resultsHigher accuracy, adds latency

3.3 Least Privilege — Tool / Agent Configuration

What is least privilege?

Only give Claude (or any agent) the minimum tools and permissions it actually needs to do its job. If an agent only needs to read data, do not give it permission to delete data. This limits damage if something goes wrong.

Exam Pattern — Capability Bloat
The exam frequently presents agents with too many tools. The correct answer is almost always: remove the unnecessary tools entirely — not add logging, not add confirmation prompts. Removal is the only true least-privilege fix.

3.4 Authentication & Authorization

ConceptWhat It MeansExam Application
AuthenticationVerifying WHO you are (login, API key)Ensure every tool call is authenticated
AuthorizationVerifying WHAT you are allowed to doCheck permissions before every action
Least privilegeOnly the minimum access neededRemove tools agents don't need
Audit loggingRecord who did what and whenRequired for compliance; not a substitute for least privilege

3.5 Accuracy-Latency Trade-offs

Optimise ForWhat to DoWhat You Sacrifice
Speed (low latency)Smaller model, fewer retrieved chunks, no re-ranking, cachingSome accuracy
AccuracyLarger model, more chunks, re-ranking, chain-of-thoughtHigher cost, slower response
CostSmallest suitable model, caching, batch processingMay reduce quality or speed

3.6 Observability & Monitoring

Simple Explanation

Observability means being able to see what your system is doing — so when something goes wrong, you can figure out why. Without good observability, debugging an AI system in production is almost impossible.

Key Observability Components

  • Request/response logging with timestamps
  • Token usage tracking per request
  • Latency measurement end-to-end and per stage
  • Error rate monitoring and alerting
  • Retrieval quality metrics (for RAG systems)
  • Prompt version tracking (which prompt was used?)

3.7 Progressive Discovery vs. Monolithic Context

StrategyWhat It DoesUse When
Progressive discoveryLoad only what's needed, retrieve more as requiredLarge knowledge bases; unknown query patterns
Monolithic contextLoad everything upfront into context windowSmall, well-defined document sets; speed matters

Evaluation, Testing & Optimization

Measuring quality, catching failures, and systematically improving Claude-based systems.

What this domain is really about

How do you know if your AI system is actually working well? This domain covers how to measure, test, and improve Claude-based systems. It's not enough to try it and think "it seems okay" — in production you need metrics, test datasets, and a systematic process for finding and fixing problems.

4.1 Evaluation Metrics

MetricWhat It MeasuresHow to Measure
AccuracyAre the answers correct?Compare against ground truth; human evaluation
LatencyHow fast does the system respond?Time from request to response; p50, p95, p99
CostHow much does each response cost?Token count × model pricing
SafetyDoes it produce harmful outputs?Red-teaming, adversarial testing
SecurityCan it be manipulated or exploited?Prompt injection tests, jailbreak attempts
Hallucination rateHow often does it invent false facts?Fact-checking against source documents

4.2 Evaluation Dataset Design

A good test dataset is essential. Without it, you cannot know if your system is improving or getting worse.

What Makes a Good Evaluation Dataset?

  • Covers all common use cases (not just easy ones)
  • Includes edge cases and difficult inputs
  • Has a mix of question types
  • Includes known good answers (ground truth)
  • Large enough to detect small improvements statistically

Mixed Evaluation Methodology

MethodWhat It IsUse For
Automated metricsCode that scores outputs automaticallyFast, scalable — catches regression
Human evaluationPeople rate outputs qualityNuanced quality; catch subtle errors
LLM-as-judgeAnother Claude instance rates outputsScalable; needs calibration against human
Red-teamingDeliberately try to break the systemSafety and security testing

4.3 A/B Testing and Iterative Improvement

What is A/B testing?

You have two versions of something (Version A: your current system; Version B: your improved version). You run both on the same test cases and compare which one scores better. This is how you know if a change actually improved things — instead of guessing.

A/B Testing Process

StepWhat to Do
1. Define what you are testingOne change at a time (model, prompt, chunking strategy, etc.)
2. Define your metricWhat counts as "better"? Accuracy? Latency? Cost?
3. Run both versionsOn the same evaluation dataset
4. Compare resultsIs the difference statistically significant?
5. Ship or discardShip Version B if it's better; discard if not

4.4 Diagnosing System Issues

SymptomMost Likely Root CauseWhere to Look First
Confident but wrong answersRetrieval returning irrelevant chunksCheck indexing, embedding quality, chunking
Answers after document refreshRe-indexing failed or mismatched embeddingsVerify re-index completed successfully
Prompt failure / wrong formatPrompt changed or model version changedCheck prompt version; test with previous version
Hallucinations on specific topicsNo relevant documents in knowledge baseCheck if topic is covered in your documents
Sudden latency increaseMore tokens being processed; network; model versionCheck token counts; check retrieval stage timing

Governance, Safety & Risk Management

Keeping AI systems safe, legal, ethical, and trustworthy.

What this domain is really about

When AI systems make mistakes, real people can be harmed. This domain covers how to prevent those mistakes: by building safety controls into the system, following laws like GDPR and HIPAA, thinking about fairness and bias, and knowing when to require a human to approve an AI decision.

5.1 Guardrails and Safety Controls

Guardrail TypeWhat It DoesExample
Input validationCheck user input before sending to ClaudeBlock prompt injection attempts
Output filteringCheck Claude's response before showing to userBlock personally identifiable information in output
PreToolUse hooksBlock dangerous tool calls before they executePrevent deletion of files above a certain size
Rate limitingLimit how many actions can happen per time periodMaximum 10 refunds per hour per agent
Human checkpointsRequire human approval before high-risk actionsApprove before publishing to production

5.2 Compliance Regulations

If you are not familiar with these laws

These are legal frameworks that protect people's data and rights. If your AI system handles personal data or operates in regulated industries, you must know and follow these rules. The exam tests whether you know which rules apply and how to build systems that comply.

RegulationWhat It CoversKey Requirements for AI Systems
GDPRPersonal data of people in the EUData minimisation, right to deletion, consent, data residency
HIPAAMedical / health information in the USAEncrypt health data, audit logs, access control, breach notification
FedRAMPCloud services used by US federal governmentSecurity controls, continuous monitoring, authorisation process

GDPR Key Principles for AI Systems

  • Data minimisation — only collect what you need
  • Purpose limitation — use data only for stated purpose
  • Right to erasure — users can request their data be deleted
  • Transparency — explain how AI makes decisions
  • Data residency — some data must stay within EU borders

5.3 Human-in-the-Loop (HITL) Validation

HITL PatternHow It WorksUse When
Approval gateAI drafts; human approves before action executesHigh-risk actions (publish, delete, send email)
Review queueAI processes; human reviews output before deliveryLegal documents, medical summaries
Escalation triggerAI handles routine cases; human gets edge casesCustomer service, complaint handling
Audit trailAI acts; human reviews logs periodicallyLow-risk but regulated activities

5.4 Ethical AI — Bias, Fairness, Transparency

ConceptWhat It MeansHow to Address It
BiasSystem produces unfair results for certain groupsEvaluate outputs across demographic groups; diverse test data
FairnessSystem treats all users equitablyDefine fairness metrics; test for disparate impact
TransparencyUsers understand how the AI made a decisionExplainability features; disclose AI involvement
AccountabilityClear ownership when AI causes harmAudit logs; defined escalation paths; human oversight

5.5 Risk Identification and Failure Modes

  • Hallucination — confident but false answers
  • Prompt injection — malicious input overrides instructions
  • Data leakage — private data appears in output
  • Model drift — behaviour changes after model updates
  • Cascading failures — one agent failure breaks entire system
  • Over-reliance — users trust AI output without verification

6.3 Managing Stakeholder Expectations — SLAs

What is an SLA?

SLA = Service Level Agreement. It is a formal commitment about how well the system will perform. For example: "The AI will respond within 3 seconds for 99% of requests." If the system doesn't meet this, there are consequences. The architect must design the system to meet the SLA.

SLA DimensionExample TargetDesign Implication

Availability99.9% uptimeRedundancy; fallback models; circuit breakers
AccuracyAt least 90% correct on benchmarkLarger model; RAG; evaluation framework
Cost per queryUnder $0.01Smaller model; caching; batch processing

Official Sample Questions

Sample Questions from the Exam Guide

These are the three official sample questions from the CCAR-P exam guide (PDF). Study the reasoning carefully — the exam tests decision-making, not just recall.

Sample 1 · Domain 3 — Integration
A team exposes a customer-support agent that can read tickets, draft replies, issue refunds, and delete user accounts. Support staff only ever need to read tickets and draft replies. Applying least-privilege principles, which change best reduces risk?
  • A. Add logging to the refund and delete tools so misuse can be audited later.
  • B. Remove the refund and delete tools from the agent's configuration entirely.
  • C. Keep all tools but add a confirmation prompt before refunds and deletions.
  • D. Replace the agent with a larger model that follows instructions more reliably.
  • ✅ Correct Answer: B — Remove the tools entirely.
Why B? Least privilege means removing capabilities that the role does not require — eliminating the attack surface rather than monitoring or guarding it. Logging (A) and confirmation prompts (C) are "detective" controls — they help after the fact, but the tools still exist and can still be misused. Model size (D) has nothing to do with authorisation scope.
Sample 2 · Domain 2 — Models, Prompting & Context
An application sends the same 8,000-token system prompt and policy document on every request, followed by a short, varying user message. Latency and cost are both concerns. Which optimisation most directly addresses both?
  • A. Truncate the policy document to the first 1,000 tokens.
  • B. Switch to the smallest available model regardless of task fit.
  • ✅ Correct Answer: C — Place static content first and enable prompt caching.
  • D. Move the policy document into a few-shot example block.
Why C? Ordering stable content first and enabling prompt caching lets the repeated prefix be reused — reducing both time-to-first-token AND per-request cost on every subsequent call. Truncation (A) loses needed policy content. Downsizing blindly (B) risks quality degradation. Moving to few-shot (D) does not create a cacheable, reusable prefix and doesn't address the core problem.
Sample 3 · Domain 4 — Evaluation & Optimisation
A RAG system suddenly returns confident but incorrect answers after a document refresh, while latency and model version are unchanged. What is the most likely first place to investigate?
  • A. The model weights have silently changed.
  • ✅ Correct Answer: B — The retrieval / indexing step is returning irrelevant or stale chunks.
  • C. The temperature setting is too low.
  • D. The context window has shrunk.
Why B? Confident-but-wrong answers following a document refresh — with model version and latency unchanged — points directly to retrieval feeding the model poor context. A broken re-index or mismatched embeddings would cause exactly this symptom. Options A, C, and D would not be specifically triggered by a document refresh event.

  • Human-in-the-loop = approval gate for high-risk irreversible actions; review queue for sensitive content.
  • SLA design drives model choice: latency SLA → smaller model + caching; accuracy SLA → larger model + RAG.
  • Observability: log every request/response + token count + latency + retrieval results.
  • Confident but wrong answers = retrieval problem (wrong chunks), not a model problem.
  • Hybrid retrieval (semantic + keyword) outperforms either alone in most production systems.
  • Stakeholder communication: always tie trade-off decisions to business value, not technical preference.

Domain Revision Checklist

D1 — Solution Design (17%)

  • I can identify the right architectural pattern for a given business problem
  • I know the 5 business value pillars and can map a use case to them
  • I can design a multi-agent system topology for a complex task
  • I understand decomposition strategies: functional, data, domain
  • I can design the full input→processing→output→feedback loop

D2 — Models, Prompting & Context (13%)

  • I know trade-offs between model sizes: speed vs. accuracy vs. cost
  • I know zero-shot, few-shot, and chain-of-thought and when to use each
  • I understand prompt caching: static first, dynamic last
  • I know context window management strategies and their trade-offs
  • I can design a system prompt with role, boundaries, format, and guardrails

D3 — Integration (19%)

  • I know when to use MCP vs. direct API vs. agent-to-agent integration
  • I can design a complete RAG pipeline (ingest → chunk → embed → index → retrieve → generate)
  • I know chunking strategies and when to use each
  • I know retrieval strategies: semantic, keyword, hybrid, re-ranking
  • I understand least privilege and can apply it to tool/agent configuration
  • I know what observability looks like in a production AI system
  • I understand accuracy-latency-cost trade-offs and how to justify decisions

D4 — Evaluation (16%)

  • I know the key evaluation metrics: accuracy, latency, cost, safety, hallucination rate
  • I can design an evaluation dataset with edge cases and ground truth
  • I understand A/B testing process and when results are statistically meaningful
  • I can diagnose system issues from symptoms (confident wrong answers → retrieval)
  • I know cost optimisation levers: caching, model sizing, batch API, max_tokens

D5 — Governance (14%)

  • I know GDPR, HIPAA, and FedRAMP key requirements
  • I can design guardrails: input validation, output filtering, PreToolUse hooks
  • I know HITL patterns: approval gate, review queue, escalation trigger
  • I understand bias, fairness, transparency, and how to test for them
  • I can identify AI failure modes: hallucination, injection, data leakage, model drift

D6 — Stakeholders (14%)

  • I can conduct structured discovery and define success criteria
  • I can communicate architectural trade-offs to non-technical stakeholders
  • I know how to design SLAs and what architectural choices they drive
  • I understand the full lifecycle: discovery → design → handoff → monitoring → iteration

D7 — Developer Productivity (7%)

  • I know Claude Code config hierarchy (review from Foundations)
  • I can describe team-level workflows: slash commands, CI/CD integration
  • I can diagnose common operational issues from symptoms
